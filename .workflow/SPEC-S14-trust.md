Running the host repository's code on the machine running `showroom` only when the person running it allows it. From the discussion of 2026-11-17 on recorded C# showcases (_`S15`_, _`S16`_ (SPEC.md)), where the user raised the risk: "a user who has cloned a 3rd party repository running `showroom` which they trusts on a repository they do not - they don't expect to run the repo's code, and the "opt-in" is inherited from the repo code via the `showroom.json`. The repo code could do anything on their machine and they didn't explicitly dedcide to run it, they were just interested in viewing it's deocumentation in a more friendly way ...". The agent's review found that `showroom` already runs host code without asking (_`K24`_ (SPEC-pitfalls.md)). Its choices were settled as _`D693`_–_`D704`_, and its zero-context review of 2026-11-17 as _`D720`_–_`D727`_.

## Decisions

- _`D677`_ (`live`, refined by _`D698`_, _`D720`_; the user, quoted above): **Running the host repository's code is allowed by the person running `showroom`, never by the host repository.** No setting in `showroom.json`, or anywhere else in the host repository, can allow it, as the repository would be allowing itself. Rejected: an opt-in in `showroom.json`.
- _`D678`_ (`live`, changed by _`D744`_ (PLAN-P19-trust.md) until _`P19.2`_, refined by _`D693`_, _`D694`_, _`D695`_, _`D697`_, _`D699`_, _`D724`_, _`D763`_ (PLAN-P19-trust.md); the user: "I like #1 and #3, I would drop #2. For any run, not just serve, you are prompted about trusting the host repo and are explicitly warned about what the implications are. Alternative is you pass the `--trust` flag."): **The person running `showroom` allows it by passing `--trust`, or by answering a prompt**, on any command (`check`, `serve`, `build`), not only `serve`. The prompt explicitly warns what trusting the host repository means: its code runs on this machine, with the user's rights. Rejected: trust remembered per host repository (as `direnv allow` or `mise trust` do, in the user's configuration folder, tied to a hash of `showroom.json`).
- _`D679`_ (`live`, changed by _`D721`_ (for `serve`), _`D740`_ (every showcase), refined by _`D702`_, _`D722`_, _`D723`_; the agent's proposal, the user: "Agree with the rest ..."): **One gate, covering everything that runs host code on the machine running `showroom`**:
  - loading custom showcase adapters (`customShowcaseAdapters`), which every `check` does today, `--showcases` or not;
  - loading the host's own compilers and tools from the host repository: TypeScript for the `ts` and `react` showcase adapters' type checks; Angular's compiler, Linker and Babel for the `angular` showcase adapter;
  - building and recording a recorded showcase (_`S15`_), e.g. the .NET SDK evaluating the host's MSBuild files, then the showcase's own code (_`S16`_).
- _`D680`_ (`live`, changed by _`D721`_, _`D740`_, _`D741`_, refined by _`D742`_ (re-pointed from the replaced _`D696`_), _`D700`_, _`D701`_; the agent's proposal, the user: "Agree with the rest ..."): **Without trust, `showroom` degrades rather than fails**: documentation files, links, linked files and `html` showcases work as before; a showcase that would need host code is not built (shown as "Not built"), with a notice saying how to allow it; `check` reports it as skipped, not failed. How `check --showcases` and `build` treat skipped showcases is _`D696`_.
- _`D681`_ (`live`, refined by _`D727`_; the agent's proposal, the user: "Agree with the rest ..."): **Trust is not a sandbox**: it decides whether host code runs, not what it can do once it does. What limits a recorded showcase's run is _`D690`_ (SPEC-S15-recorded-showcases.md); `README.md` says plainly that trusting a host repository means running its code.
- _`D682`_ (`live`, changed by _`D727`_, _`D741`_ (they see their showcases' sources, not "Not built"); the agent's proposal, the user: "Agree with the rest ..."): **The change is a breaking one, accepted while `showroom` is an alpha**: existing users see "Not built" until they pass `--trust` or answer the prompt; `CHANGELOG.md` says so. This repository's own uses pass `--trust`: `ci:showroom`, `.github/workflows/showroom.yml`, and `README.md` › Publishing to GitHub Pages' example.

### The draft's choices

- _`D693`_ (`live`, refined by _`D789`_ (PLAN-P20-recorded.md), refined by _`D722`_, _`D763`_ (PLAN-P19-trust.md), changed by _`D740`_; refines _`D678`_; Q1 (a), the user: "Agreed with all your points!"): **The prompt is shown only when the run would run host code.** `showroom` first reads `showroom.json` and scans the documentation files (plain parsing, no host code), and prompts only if something under the gate (_`D679`_) would run, naming it: the custom showcase adapter modules, by path; the host's compilers and tools it would load; how many showcases would be built, and how many recorded. A host repository with only `html` showcases is never asked. Rejected: a prompt on every run (asking where nothing runs teaches people to say yes).
- _`D694`_ (`live`, refined by _`D762`_ (PLAN-P19-trust.md), _`D763`_ (PLAN-P19-trust.md); refines _`D678`_; Q2 (a), the user: "Agreed with all your points!"): **The prompt's default is no** (`[y/N]`): only `y` or `yes` allows it; Ctrl-C ends the command. Rejected: no default.
- _`D695`_ (`live`, refined by _`D724`_, changed by _`D744`_ (PLAN-P19-trust.md) until _`P19.2`_; refines _`D678`_; Q3 (a), the user: "Agreed with all your points!"): **With no terminal and no `--trust`** (CI, a pipe), `showroom` never prompts: it runs without trust, with a warning saying so and how to allow it. Rejected: an error until `--trust` or `--no-trust` is given.
- _`D696`_ (`replaced by` _`D742`_, refined by _`D726`_; refines _`D680`_; Q4 (a), the user: "Agreed with all your points!"): **A showcase skipped for lack of trust is an error in `check --showcases` and `build`**, which ask for every showcase to be built (CI fails rather than passing while checking nothing); plain `check` and `serve` warn. Rejected: a warning everywhere.
- _`D697`_ (`live`, refined by _`D725`_, _`D753`_; refines _`D678`_; Q5 (a), the user: "Agreed with all your points!"): **In `serve`, one answer holds for the session**, given at its start: a yes covers custom showcase adapters and showcases added while it runs; a no holds too. Rejected: prompting again when a change brings new host code (a prompt in the middle of `serve`'s output).
- _`D698`_ (`live`, refined by _`D724`_, _`D748`_ (PLAN-P19-trust.md), _`D761`_ (PLAN-P19-trust.md); refines _`D677`_; Q6 (a), the user: "Agreed with all your points!"): **The library never prompts**: `check()` (and the internal `buildShowcases()`) take a `trust` option, `false` by default, set by their caller; `main()` prompts on the command line's behalf, through an injectable input (as `CliOutput` is injected), so the prompt is tested without a terminal. Rejected: `trust` defaulting to `true` in the library.
- _`D699`_ (`live`; refines _`D678`_; Q7 (a), the user: "Agreed with all your points!"): **`--no-trust`** runs without trust and never prompts, for scripts run in a terminal. Rejected: no explicit no (redirecting the input instead).
- _`D700`_ (`live`, refined by _`D726`_, _`D749`_ (PLAN-P19-trust.md), changed by _`D741`_ (shown with their `source` view); refines _`D680`_; Q8 (a), the user: "Agreed with all your points!"): **Without trust, custom showcase adapters are not loaded at all**: their showcases are not validated (their options unchecked) and not built ("Not built"), shown with the views of their marker or `showcaseViews`, else `demo`; `showcaseViews` naming one is no error; `check` warns once that they were skipped. Rejected: an error.
- _`D701`_ (`live`, refined by _`D740`_; refines _`D680`_; Q9 (a), the user: "Agreed with all your points!"): **Without trust, no showcase that needs anything from the host is built**, `ts` and `react` included, although `showroom`'s own Vite bundles them (Vite may still load host packages, e.g. `sass` for a `.scss` import): one rule. Rejected: building them without their type check.
- _`D702`_ (`live`, changed by _`D721`_, _`D740`_, _`D743`_ (a showcase's code in the browser is under the gate); refines _`D679`_; Q10 (a), the user: "Agreed with all your points!"): **Code that runs only in the reader's browser is outside the gate**: a showcase frame's code runs in the browser's sandbox, as any web page's. What `serve` exposes on `localhost` to a same-origin showcase frame stays _`K25`_ (SPEC-pitfalls.md), settled in planning (e.g. a `sandbox` attribute, or showcase frames on another origin). Rejected: no showcase frame at all without trust, `html` included.
- _`D703`_ (`live`; Q24 (a), the user: "Agreed with all your points!"): **_`S14`_, _`S15`_ and _`S16`_ are three specification segments, planned and implemented in that order**: _`S14`_ first, as it closes _`K24`_ (SPEC-pitfalls.md) in the published release on its own. Rejected: _`S15`_ and _`S16`_ as one segment.
- _`D704`_ (`live`, changed by _`D726`_, _`D743`_; Q23 (a), the user: "Agreed with all your points!"): **"Trust" is a Glossary term** (`CONTRIBUTE.md`): the permission the person running `showroom` gives it, for one run, to run the host repository's code on their machine. Added with _`S14`_'s implementation.

### The zero-context review of 2026-11-17

- _`D720`_ (`live`, refined by _`D863`_; refines _`D677`_; review T1, option chosen: "Outside only (Rec.)"): **The gate protects only a `showroom` that comes from outside the host repository**: a global install, or one run from another folder with `--root <host>`. A `showroom` the host repository installs (a devDependency, or `npx showroom` run in it, which prefers its own `node_modules/.bin/showroom`), its `.npmrc` (another registry) and its npm scripts are the host's code already. `README.md` gives the recipe for reading a repository you don't trust. Rejected: protecting a `showroom` installed inside the host repository (not achievable: the repository controls that program).
- _`D721`_ (`live`, refined by _`D752`_, changed by _`D740`_ (`check` and `build` no longer build `html` showcases without trust); changes _`D680`_, _`D702`_; review T2, the user: "If this is a problem only for serve, maybe we gate serve entirely by repo needing to be trusted?", then option chosen: "No frames untrusted (Rec.)"): **Without trust, `serve` builds no showcase frame at all, `html` included**: it shows the documentation, and every showcase as not built, so no host code reaches the dev server's origin (its `/__open-in-editor`, `/@fs/` and HMR endpoints, the showroom's own page, _`K25`_ (SPEC-pitfalls.md)). With trust, `serve` builds showcase frames as before: the host's code is trusted, so showcase frames need no isolation from the showroom. `check` and `build` without trust still build `html` showcases (a published showroom is its owner's site, visited as any other); `README.md` says that a showroom published on GitHub Pages (`<user>.github.io/<repo>`) shares its origin with its owner's other project pages. Rejected: `serve` refusing to start without trust (reading a repository you don't trust in the showroom would no longer be possible).
- _`D722`_ (`live`, refined by _`D750`_ (PLAN-P19-trust.md) (its executables are _`S15`_'s); changes _`D102`_ (SPEC-S6-showcases.md); refines _`D679`_, _`D693`_; review F4, option chosen: "Apply all (Rec.)"): **Host checks run under the gate**: without trust, the host check (`ShowcaseAdapter.check?()`) of a showcase adapter that loads or runs host code doesn't run, and custom showcase adapters are not loaded (_`D700`_). The order is fixed: `showroom.json` is read and the documentation files scanned (no host code); then trust is decided (the prompt, _`D693`_); only then do host checks run, custom showcase adapters load, and the host copy is made. _`D679`_'s gate covers every process `showroom` starts in the host repository or the host copy, host checks included, and every executable it starts is resolved to an absolute path from the `PATH`, leaving out the host repository and the host copy (so a program committed in the host repository never runs in its place). The prompt names each tool it would load by its resolved absolute path, which may be outside the host repository (packages resolve as Node does, walking up past its root).
- _`D723`_ (`live`, refined by _`D745`_ (PLAN-P19-trust.md); refines _`D679`_; review F5, option chosen: "Apply all (Rec.)"): **The gate covers host packages the bundler loads**: Vite resolves CSS preprocessors (`sass`, `sass-embedded`, `less`, `stylus`) from the host repository before its own, and loads them in `showroom`'s process; the prompt names them too. Whether to pin them to `showroom`'s own copies, or refuse them, is _`O112`_.
- _`D724`_ (`live`, refined by _`D764`_ (PLAN-P19-trust.md); refines _`D678`_, _`D695`_, _`D698`_; review F6, option chosen: "Apply all (Rec.)"): **Consent comes only from the person at the terminal**: the answer is read only from a terminal on standard input (`yes | showroom …` or a here-document never answers it); the prompt is written to standard error; no environment variable grants trust (a host's `.envrc` or CI configuration could set it); `main()` with no input injected reads the terminal on standard input, and runs without trust where there is none. Every string from the host repository that `showroom` writes to the terminal (in the prompt and its notices, issues, and recorded output, _`D706`_ (SPEC-S15-recorded-showcases.md)) has its control characters escaped, shown visibly (e.g. `\x1b`), so no escape sequence can rewrite the warning.
- _`D725`_ (`live`, refined by _`D765`_ (PLAN-P19-trust.md); refines _`D697`_; review F7, option chosen: "Apply all (Rec.)"): **A yes in `serve` also covers host code added while it runs**, never named by the prompt (_`D693`_); `serve` prints a notice whenever host code first runs under it (a custom showcase adapter module, by its path; a recorded showcase).
- _`D726`_ (`live`, changed by _`D742`_ (its errors become warnings), refined by _`D749`_ (PLAN-P19-trust.md), _`D753`_; refines _`D696`_, _`D700`_, changes _`D704`_; review F8, option chosen: "Apply all (Rec.)"): **Under `check --showcases` and `build`, every showcase skipped for lack of trust is an error**, a custom showcase adapter's included (_`D696`_ over _`D700`_); plain `check` warns once about the skipped custom showcase adapters. **Trust holds for one command** (one invocation of `showroom`, a whole `serve` session included), not one of `serve`'s runs.
- _`D727`_ (`live`, refined by _`D755`_, _`D863`_; refines _`D681`_, changes _`D682`_; review F9, option chosen: "Apply all (Rec.)"): **`README.md` says how to run a trusted `showroom` in CI**: with no secrets in the step's environment; with `actions/checkout`'s `persist-credentials: false` (or the token stays readable in `.git/config`); and never with `--trust` on `pull_request_target` or for pull requests from forks. This repository's `.github/workflows/showroom.yml` follows it.

### Planning _`P19`_ (2026-11-17)

### The zero-context review of _`P19`_'s draft (2026-11-17)

- _`D752`_ (`live`; refines _`D721`_, _`D741`_; review R1 (security blocker: without trust, linked `.html` and `.svg` files still ran on the dev server's origin, opened in a new tab), option chosen: "Serve as text"; rejected: a `Content-Security-Policy: sandbox` header (the agent's recommendation), leaving them out of `build`): **Without trust, `serve` sends linked files of active types (`.html`, `.htm`, `.svg`, `.xml`, `.xhtml`) as `text/plain`**, with `X-Content-Type-Options: nosniff` (on every linked file, trusted or not), so a new tab shows their source. `build` copies them as today: a published showroom is its owner's site (_`D721`_), and static hosting sends no headers; `README.md` says so.

- _`D754`_ (`live`; changes _`D741`_; review R4, option chosen: "Shown only; keep md (Rec.)"; rejected: strictly `source` only, `check` rewriting the views): **The `source` override is the shown host information's**: `check()`'s `HostInformation` keeps every showcase's resolved views (a custom showcase adapter's not loaded: its marker's, else `showcaseViews`', else `demo`, _`D700`_), and the shown host information carries a top-level `trusted` flag. - _`D756`_ (`live`; refines _`D740`_; review R2, option chosen: "Any showcase, always"; rejected: deciding per command, plain `check` asking only for custom showcase adapters and host checks (the agent's recommendation)): **Every command, plain `check` included, has something to trust whenever the host repository has a showcase or lists a custom showcase adapter**: one rule, whatever each command would run.
