## Goals

- The build half of the showcase adapter interface (_`D127`_, PLAN-P4.1-markers-and-checks.md) implemented: `showroom` builds every showcase with its showcase adapter, built-in or custom, and adds its frame script to each showcase frame (_`D96`_, _`D105`_).
- The frame script and its `postMessage` contract (_`D77`_, SPEC-S6-showcases.md): the showcase frame reports its size, and the showroom tells it the theme.
- The `html` showcase adapter's build (_`D97`_, SPEC-S6-showcases.md; _`D128`_).
- `build` builds the showcase frames into the output folder, and the showroom places each right before its entry point (_`D93`_), sized and themed; `build` fails on a showcase that doesn't build (_`D102`_).
- `check --showcases` builds every showcase and throws the result away (_`D102`_).
- The open point _`K14`_ (SPEC-pitfalls.md), as far as the `html` showcase adapter and custom showcase adapters go.

Not in _`P4.2`_: showcases in `serve` (_`P4.3`_), the `ts`, `react` and `angular` showcase adapters (later segments).

## Decisions

### Showcase adapters

- _`D134`_ (`live`, refined by _`D150`_, changed by _`D169`_ (PLAN-P4.4-html-resources.md); Q1, _`K14`_): **An `html` showcase is self-contained**: its build is its entry point alone (the page, or the wrapped fragment, _`D135`_); relative references in it (`<script src>`, `<link href>`, `<img src>`) are neither resolved nor copied, so showcase resources are of no use to it. _`K14`_ doesn't arise for it, and custom showcase adapters receive the virtual files in memory (_`D127`_) and put them before their own tooling; _`K14`_ stays open for the Vite-based showcase adapters (`ts`, `react`), whose segment plans a Vite plugin resolving virtual files. Rejected: building the `html` page with Vite and a plugin resolving virtual files (front-loads _`K14`_ for `ts`, but needs a spike on virtual HTML entries, and more than `html` needs); copying the files the page references.
- _`D135`_ (`live`, refined by _`D164`_; Q2): **An `html` entry point is a page when it starts, after whitespace and comments, with `<!doctype` or `<html`** (case-insensitive); anything else is a fragment, wrapped into `<!doctype html><html><head><meta charset="utf-8"><meta name="viewport" content="width=device-width, initial-scale=1"></head><body>…</body></html>`. A linked entry point is read from disk as UTF-8. The build's `reads` is the documentation file (inline) or the linked file.
- _`D136`_ (`live`, refined by _`D165`_; Q3): **Build results are checked** before use: `page` must be among `files`; every file path relative, POSIX-style, without `.` or `..` segments, and unique; a page given as bytes is decoded as UTF-8. A result that breaks these, or a `build()` that throws, is a build error of that showcase.

### Building showcases

- _`D137`_ (`live`, changed by _`D149`_, _`D187`_ (PLAN-P4.3-serve.md), refined by _`D159`_; Q4): **A new internal module, `src/showcases/`** (Node, never re-exported): `buildShowcases()` builds every showcase of the host information with its showcase adapter (built-in, or custom, loaded again), sequentially, each in a sub-folder of one scratch folder per run (`mkdtemp` in the OS temp folder, removed afterwards, _`D105`_), adds the frame script, calls every adapter's `close()`, and returns the showcase frames in memory (by showcase id) or every build error. `check --showcases` and `build` use it; `serve` will, in _`P4.3`_. Rejected: building inside `check()` and handing its adapters on to `build`.
- _`D138`_ (`live`, refined by _`D163`_; Q5): **Build errors are reported where they are in the documentation**: an error in a virtual file becomes its documentation file and line (the fence's line, plus the error's line within the block); an error without a path, the documentation file and the entry point's line; an error in a real file stays there. Every error names its showcase (`Showcase <id>: …`).

### The frame script

- _`D139`_ (`live`, refined by _`D153`_, _`D154`_; Q6): **The frame script is browser code in a new `src/frame/` module** (Node-free, never re-exported): the message types and constants, which the showroom imports too, and a self-contained function that `src/showcases/` inlines into each showcase frame page as `<script>(<function>)()</script>`, right after the `<head>` tag (or the `<html>` tag, or at the start, when the page has none). Rejected: a shared `.js` file in the output folder, referenced from every page (paths depend on the showcase frame's depth, and it is a few hundred bytes).
- _`D140`_ (`live`, refined by _`D152`_, changed by _`D155`_, _`D189`_ (PLAN-P4.3-serve.md); Q7): **The `postMessage` contract** (_`D77`_):
  - showcase frame → showroom: `{ source: 'showroom-frame', type: 'ready' }` once loaded, and `{ source: 'showroom-frame', type: 'resize', height }` whenever the height of `<html>` changes (a `ResizeObserver`, rounded up to whole pixels);
  - showroom → showcase frame: `{ source: 'showroom', type: 'theme', theme: 'light' | 'dark' }`, on `ready` and on every theme change;
  - the frame script sets the theme as `data-showroom-theme` and the CSS `color-scheme` of `<html>`, so a showcase can follow it with `[data-showroom-theme=dark]` selectors or `light-dark()`; the initial theme also comes in the showcase frame's URL (`#theme=dark`), so it applies before the first message, without a flash;
  - each side only listens to the other's window (`event.source`), and posts with the target origin `*`, as showcase frames may be served from another origin by `serve` (_`P4.3`_).

### The showroom

- _`D141`_ (`live`, refined by _`D161`_; Q8): **Showcase frames go into `showcases/<documentation file's path>/<n>/`** in the output folder (e.g. `showcases/docs/guide.md/2/index.html`), `<n>` being the showcase's position in its documentation file (_`D125`_'s id); the showroom loads a showcase frame by that relative URL (its `page`), so it works under any path (_`K4`_).
- _`D142`_ (`live`, refined by _`D159`_, _`D162`_; Q9): **The shown host information gains `showcases`**: per showcase, its documentation file, its entry point's offset and its showcase frame's URL, from the host information, not found again by parsing in the browser. A remark plugin in the showroom's Markdown rendering inserts the showcase frame right before the block holding the entry point (_`D93`_): the fence itself; for a link, its paragraph; for a link outside a paragraph (a heading, a table cell), the top-level block holding it.
- _`D143`_ (`live`, refined by _`D152`_, _`D155`_, _`D168`_; Q10): **The showcase frame's iframe**: an iframe the width of the text, its height following the `resize` messages (150 px until the first), a 1 px FluentUI stroke border with medium rounded corners, a transparent background (the showcase frame's `color-scheme` matches the showroom's), `title="Showcase <n> of <documentation file>"`, `loading="lazy"`, and no `sandbox` (the showcase is the host repository's own code; _`D76`_'s isolation is about styles and globals). Rejected: `sandbox="allow-scripts …"` (no `localStorage` or cookies in showcases).
- _`D144`_ (`replaced by _`D183`_ (PLAN-P4.3-serve.md)`, refined by _`D159`_; Q11): **`serve` shows no showcases until _`P4.3`_**: its shown host information has an empty `showcases` list, so it shows the documentation files as today.

### Commands

- _`D145`_ (`live`, refined by _`D160`_; Q12): **`build`**: the check, then `buildShowcases()` (any error: every error reported, exit 1, the output folder untouched), then Vite's build of the showroom, with a plugin in `src/vite/` emitting the showcase frames' files into the bundle (so `emptyOutDir` and the marker cover them; _`P4.3`_'s `serve` serves them from the same plugin), then the marker.
- _`D146`_ (`live`, refined by _`D167`_; Q13): **`check --showcases`** (and `check(root, { showcases: true })`, `CheckOptions.showcases`): after the static check, and only when it found no errors, builds every showcase with `buildShowcases()` and throws the showcase frames away; each build error is an error issue (_`D138`_). `--showcases` is an error on `serve` and `build` (`build` always builds them).

### Testing and documentation

- _`D147`_ (`live`, changed by _`D151`_, refined by _`D156`_, _`D157`_, _`D158`_; Q14): **Tests**:
  - unit: the frame script (stubbed `window`, `ResizeObserver` and `postMessage`), the script's insertion and the result checks (_`D136`_), error positions (_`D138`_), showcase frame paths, the `html` build, the remark plugin and the showcase frame's component (server-rendered), the Vite plugin's emitted files, the command line's `--showcases`;
  - integration (`*.integration.test.ts`): `buildShowcases()` and `check --showcases` on fixtures with `html` and custom showcases (passing, and failing builds of a custom showcase adapter);
  - e2e: `build` on fixture copies, Vite included: showcase frames written, the shown host information placing them, a failing showcase leaving the output folder untouched. The e2e project's `globalSetup` compiles the showroom once per run into a scratch folder (`tsc -p tsconfig.build.json --outDir`, plus `index.html`), passed as `appDir`, so the tests never depend on, or write to, `dist/` (_`D132`_'s open question);
  - the `integration`, `e2e` and `serve` projects set `TMPDIR`, `TMP` and `TEMP` to a folder under `node_modules/.cache/showroom-tests/`, so the temporary folders `showroom` makes (Vite's `cacheDir`, the build's scratch folder) stay inside the repository (_`D106`_).
- _`D148`_ (`live`, refined by _`D166`_; Q15): **Documentation and Glossary**: `README.md` (`# Usage`: showcases now shown by `build` and not yet by `serve`; the `html` showcase adapter (self-contained, fragments wrapped); following the theme in a showcase; `check --showcases` and `CheckOptions.showcases`; `build` failing on a showcase; the build half of custom showcase adapters, experimental; `# Development`: the e2e `globalSetup`), `AGENTS.md` (Layout: `src/showcases/`, `src/frame/`; Testing; Exports; gotchas), `CONTRIBUTE.md` (project structure; Glossary: new term "Frame script", and "Shown host information" extended with the showcases' placement).

### From the browser check (2026-11-12)

- _`D168`_ (`live`; changes _`D152`_; refines _`D143`_): **The measured height**: the larger of `<body>`'s own bottom plus its bottom margin (text directly in `<body>`, which _`D152`_'s children leave out), and the lowest child's bottom plus that child's bottom margin (which may collapse through `<body>`'s) plus `<body>`'s bottom padding and border; the showcase frame's iframe is as high as the reported height plus its own border (`border-box`). Found in the trial build: every short showcase frame was 8–10 px too short, with a scrollbar, and a custom showcase adapter's text-only page about 30 px high. Unit tests cover text directly in `<body>` and a collapsing margin.

## Steps

1. `src/frame/`: the message types, constants and the frame script (_`D152`_, _`D154`_). Unit tests.
2. `src/showcases/`: `buildShowcases()` (_`D159`_), the frame script's insertion (_`D153`_), result checks (_`D165`_), error positions (_`D163`_), showcase frame paths (_`D161`_); the `html` showcase adapter's build (_`D164`_); custom showcase adapters as factories (_`D149`_). Fixtures (_`D158`_). Unit and integration tests; the shared `globalSetup` and temporary folders (_`D156`_).
3. `check --showcases` (`CheckOptions.showcases`, `main()`, `USAGE`; _`D167`_). Unit, integration and end-to-end tests.
4. The shown host information's `showcases` (`getShownHostInformation(host, frames?)`), and the showroom: the remark plugin (_`D162`_), the showcase frame's component, the theme context (_`D155`_). Unit tests.
5. `build`: the order of _`D160`_, the Vite plugin emitting the showcase frames; `serve`'s empty `showcases`. The e2e compile (_`D157`_) and end-to-end tests calling `build()` (_`D151`_). A trial build on a copy, checked by the user in a browser.
6. Documentation (_`D148`_, _`D166`_).
