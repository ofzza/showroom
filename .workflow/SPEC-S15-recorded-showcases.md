# _`S15`_ Recorded showcases

approved 2026-11-17 (option chosen: "Approve and commit (Rec.)"), after its zero-context review; wording fixes 2026-11-17 (references to the draft's questions replaced by the decisions that settled them; _`D683`_'s references); revised 2026-11-17 (_`R57`_), re-approved 2026-11-17 with _`P20`_ (option chosen: "Approve and commit (Rec.)")

- _`R57`_ 2026-11-17: the run folder lives in a cache folder only the user can write to, not the temporary folder (_`D709`_), caused by _`D782`_ (PLAN-P20-recorded.md); `--pass-env` reaches build steps only (_`D729`_), caused by _`D783`_ (PLAN-P20-recorded.md); absolute symbolic links inside the root are rewritten to relative ones in the host copy (_`D735`_), caused by _`D788`_ (PLAN-P20-recorded.md).

Showcases whose code can't run in the browser, run by their showcase adapter when it builds them, on the machine running `showroom`, with their console output and exit code recorded and shown in the showroom. From the discussion of 2026-11-17 on building and running C# examples with .NET's file-based apps (the user: "I'm thinking (and for now only thinking) about introducing a way for a ShowcaseAdapter to "run" an example at build time (on the server) when it is not possible to run it at runtime (in the browser), but still provide compilation and (a version of) runtime checks ..."). The first showcase adapter using it is _`S16`_'s (SPEC.md). Running host code needs trust (_`S14`_ (SPEC.md)). Its choices were settled as _`D705`_–_`D711`_, _`D719`_, and its zero-context review of 2026-11-17 as _`D728`_–_`D736`_.

## Decisions

### Recording

- _`D683`_ (`live`, refined by _`D705`_, _`D707`_, _`D710`_; the user: "I prefer (B). It is cleaner, and will scale to other languages. We already have decided to make showcase frame errors and console output transfer over to the host application for purposes of clean separation of concerns; we can add recorded console output and exit code to ShowcaseBuildResult to achieve the same here."): **A showcase adapter can record a showcase**: its `ShowcaseBuildResult` carries the showcase's recorded console output and exit code, which the shown host information carries to the showroom, where they are shown as a showcase frame's console is (_`D499`_, _`D505`_–_`D507`_ (SPEC-S12-showcase-views.md)). The mechanism is the showroom's, not a language's, so later showcase adapters (Python, Rust, Go, …) use it as is. Rejected: (A) a showcase frame page replaying the recorded lines through `console.log` (no interface change, but a workaround, and nothing tells a recorded line from a live one).
- _`D684`_ (`live`; the user: 'I would just refer to this as "recorded" as opposed to "running"'): **Such a showcase is called recorded**, never "running": its output was recorded once, when it was built, not produced while the reader watches. The Glossary term is _`D711`_.
- _`D685`_ (`live`; the user: "Speed is a valid concern, but for now let's not worry about it. Once we're working we can worry about speed."): **Speed is left for later**: building and recording each showcase may take seconds (a cold `dotnet` build and restore), in `check --showcases`, `build`, and each of `serve`'s runs; measured and improved once recorded showcases work.

### The host copy

- _`D686`_ (`live`, changed by _`D735`_, refined by _`D709`_; the user: "How about we copy the entire repo into a temp location and add the examples to the root where they naturally "belong"? This isn't writing to the host repo, but also doesn't require rewriting and rewiring imports and other context ..."): **A recorded showcase is built and recorded in a copy of the host repository**, in a temporary folder, with its virtual files written into the copy at their own paths (beside their documentation file), so everything around them resolves as it would in the host repository itself (relative references, the host's build configuration). The host repository is never written to. Rejected: building in an empty temporary folder (the host's configuration is lost); rewriting the showcase's references to the host repository (fragile, and what is built isn't what is shown).
- _`D687`_ (`live`, refined by _`D710`_, _`D735`_; the agent's proposals, the user: "Agreed", "Awesome!"): **The host copy is a service of `showroom`'s**, not of a showcase adapter, so every showcase adapter that needs it shares it: made once per run, shared by every showcase of the run; in `serve`, kept current by copying the files that changed, rather than copied again (the user: "We could maintain our copy of the repository with detected files that have changed. The same "copy as showroom service" implementation could take care of this so it works for any future language."); copied with copy-on-write clones where the file system has them (Node's `fs.cp` with `COPYFILE_FICLONE`), and plainly elsewhere.
- _`D688`_ (`live`, changed by _`D730`_; the agent's proposals, the user: "Agree with the rest ...", "Agreed"): **The host copy leaves out what the host repository ignores** (_`D10`_ (SPEC.md): the stack adapter's ignore patterns and the configuration's), the output folder, and `.git`. A stack adapter whose hosts need `.git` (e.g. .NET versioning from git tags, _`K26`_ (SPEC-pitfalls.md)) may keep it, or link it to the host's (the user: "Possibly if StackAdapter really needed `.git` it could not exclude it, or could link it from the host").
- _`D689`_ (`live`; the user: "Document, but we can live with this. Only works on self-contained repositories"): **Recorded showcases work in self-contained host repositories only**: a reference from inside the host repository to a file outside it (e.g. a `Directory.Build.props` importing `../../shared.props`) doesn't resolve in the host copy. `README.md` says so.

### Running host code

- _`D690`_ (`live`, changed by _`D729`_, _`D733`_, _`D734`_; the agent's proposals, the user: "Agree with the rest ..."): **A recorded showcase is only built and recorded with trust** (_`S14`_ (SPEC.md)), and its run is limited, as far as `showroom` can without dependencies on the host: its environment is cleaned (only an allowed list of variables is passed, so a CI's secrets never reach it), its standard input is closed, its working folder is in the host copy, it has a time limit after which its whole process tree is killed, and its output is capped. `README.md` says plainly that this isn't a sandbox: the showcase's code can still reach anything the user can. Rejected: a sandbox when one is available (e.g. `bwrap` on Linux, `sandbox-exec` on macOS), as the same showroom would then be isolated on one machine and not on another, without anyone noticing; containers, and compiling to WebAssembly (a dependency to install on the host).

### The draft's choices

- _`D705`_ (`live`, changed by _`D728`_, _`D731`_, refined by _`D706`_, _`D708`_; refines _`D683`_; Q11 (a), the user: "Agreed with all your points!"): **`ShowcaseBuildResult` gains an optional `recording`**: its console lines, in the frame script's own format and within its limits (`CONSOLE_MAX_LINES`, `CONSOLE_MAX_LINE_LENGTH`, the number of dropped lines, and how many of them were warnings and errors); its exit code; and whether the time limit ended it. A result may have a recording and no showcase frame (no `page` and `files`), which the contract forbade until now. The showroom feeds a recording to the same console state as a showcase frame's messages (`updateConsole()`), so the `console` view and the `runtime` status mark are one code path. Rejected: a separate result type with a console view of its own.
- _`D706`_ (`live`; refines _`D705`_; Q12 (a), the user: "Agreed with all your points!"): **Standard output's lines are recorded as `log` lines, standard error's as `error` lines**, in the order they arrive; across the two pipes, the order is approximate (documented). Rejected: standard error as `warn` (uncaught exceptions are written there).
- _`D707`_ (`live`, changed by _`D728`_; refines _`D683`_; Q13 (a), the user: "Agreed with all your points!"): **A failed recording is an error**, of a `runtime` check: a non-zero exit code, the time limit, or a crash fails `check --showcases` and `build`, unlike a showcase frame's run-time errors, which only the reader's browser sees. A marker option for a showcase that is meant to fail is left for later. Rejected: a warning.
- _`D708`_ (`live`, refined by _`D732`_; refines _`D705`_, _`D495`_ (SPEC-S12-showcase-views.md); Q14 (a), the user: "Agreed with all your points!"): **A showcase adapter declares that its showcases have no showcase frame**; `view=demo` on such a showcase is a `check` error, as other misused views are, and its default views never hold `demo`. Rejected: a `demo` view showing the recorded output as text.
- _`D709`_ (`live`, changed by _`D782`_ (PLAN-P20-recorded.md), refined by _`D734`_; refines _`D686`_; Q15 (a), the user: "Agreed with all your points!"): **The host copy lives in a fresh temporary folder** (`mkdtemp`, as Vite's `cacheDir` does), removed when the command ends; the tests' `TMPDIR` keeps it inside this repository. Rejected: a cache folder kept between runs.
- _`D710`_ (`live`, refined by _`D719`_; refines _`D683`_, _`D687`_; the user, on _`S16`_: "The presentation part of the CS Showcase adapter should be implemented reusably - I would expect other upcomming adapters that run on teh backend and record output will want to use it."): **Everything about a recorded showcase that isn't its language's is shared by every showcase adapter that records**, built once as part of _`S15`_, never inside _`S16`_'s C# showcase adapter: the host copy (_`D687`_); running a command in it under _`D690`_'s limits (the cleaned environment, the closed input, the time limit and killing the process tree, the output cap); turning its output into a recording (_`D705`_, _`D706`_) and a failed one into its `runtime` issue (_`D707`_); the showcases with no showcase frame (_`D708`_); and the showroom's whole presentation of a recording (the `console` view, the `runtime` status mark, the issue list, _`O102`_). A showcase adapter that records supplies only its language's part: how to build the showcase (e.g. `dotnet build`), how to read its tool's errors and warnings, and the command that runs it. Custom showcase adapters can use it too (_`D719`_).
- _`D711`_ (`live`, refined by _`D736`_; Q23 (a), the user: "Agreed with all your points!"): **"Recorded showcase" and "Host copy" are Glossary terms** (`CONTRIBUTE.md`): a recorded showcase is a showcase that its showcase adapter builds and runs on the machine running `showroom`, recording its console output and exit code, which the showroom shows in place of a showcase frame's console; the host copy is `showroom`'s copy of the host repository, with virtual files written where they belong, in which showcase adapters build and record. Added with _`S15`_'s implementation.
- _`D719`_ (`live`; refines _`D710`_; Q25, option chosen: "Custom too (Rec.)"): **Custom showcase adapters can record too**: `ShowcaseBuildRequest` hands every showcase adapter the host copy, and a way to run a command in it under _`D690`_'s limits that returns the recording; a custom showcase adapter's `recording` is shown as a built-in one's. A user can then add a language `showroom` doesn't ship (Python, Go, …) with a custom showcase adapter; the interface stays experimental. Rejected: built-in showcase adapters only, for now.

### The zero-context review of 2026-11-17

- _`D728`_ (`live`; changes _`D705`_, _`D707`_, _`D507`_, _`D523`_ (SPEC-S12-showcase-views.md); review T3, the user: "In JS we make any `console.error`s show as "failed" runtime. I would do the same here - non-zero exit code or any `stderr` are both "failed" recording."): **A recorded showcase has one `runtime` status mark, and a recording fails when its exit code isn't 0, the time limit ends it, it crashes, or it wrote anything to standard error**, as a `console.error` makes a showcase frame's `runtime` ✗ (_`D523`_). A failed recording is an error of the `runtime` check, failing `check --showcases` and `build` (_`D707`_); a recording that doesn't fail is `runtime ✓`. `runtime` is listed among the result's `checks` whenever the recording ran to its end, the time limit included (_`D537`_ (SPEC-S12-showcase-views.md)). Rejected: standard error making `runtime` ⚠ only; the exit code alone deciding.
- _`D729`_ (`live`, refined by _`D783`_ (PLAN-P20-recorded.md); changes _`D690`_; review T4, option chosen: "Same limits (Rec.)"): **A recording showcase adapter's build runs under the same limits as its recording** (restoring and building run host code: MSBuild evaluates the host's files and packages' targets), with a time limit of its own, longer than the run's. Environment variables are passed on by their exact names only, never by a prefix (`DOTNET_*` would pass `NUGET_AUTH_TOKEN`); more can only be named by the person running `showroom`, on the command line (e.g. a private feed's credentials), never in `showroom.json` (_`D677`_ (SPEC-S14-trust.md)). Rejected: limiting only the run.
- _`D730`_ (`live`; changes _`D688`_; review T6, the user: "Copy on requst. I would want every adapter that uses to common copy mechanism to have to specify what is copied and what is ignored - it can or doesn't have to ignore `.git`."): **Every showcase adapter that uses the host copy says what is copied and what is left out**, `.git` included or not; `.git` is always copied, never linked. The stack adapter has no say in it, and the configuration's `ignore` (which decides documentation and code files, _`D10`_ (SPEC.md)) doesn't apply. Rejected: linking `.git` to the host's (writable through the link).
- _`D731`_ (`live`; changes _`D705`_, _`D508`_, _`D499`_, _`D500`_, _`D530`_ (SPEC-S12-showcase-views.md), _`D96`_ (SPEC-S6-showcases.md); review F2, option chosen: "Apply all (Rec.)"): **A built showcase has either a showcase frame or a recording, never both**. With a recording, no showcase frame is no build failure: `build` is ✓ when the build reports no error. Its `console` view shows the recording, with no showcase frame loaded behind it (_`D500`_); it is replaced when a new build brings a new recording (in `serve`), never cleared by a reload (_`D499`_, _`D530`_), and has no pending state.
- _`D732`_ (`live`; changes _`D523`_ (SPEC-S12-showcase-views.md); refines _`D708`_; review F3, option chosen: "Apply all (Rec.)"): **A showcase adapter whose showcases have no showcase frame must declare its `defaultViews`**, without `demo` (_`D523`_'s `demo` fallback doesn't apply to it). The `view=demo` check (_`D708`_) is skipped for the showcases of a custom showcase adapter that isn't loaded (_`D700`_ (SPEC-S14-trust.md)).
- _`D733`_ (`live`; changes _`D690`_; review F9, option chosen: "Apply all (Rec.)"): **The cleaned environment only protects the recording showcase adapter's own processes**: host code that runs inside `showroom`'s process (custom showcase adapters, the host's compilers) sees its whole environment, and every process, cleaned or not, can read the files the user can (e.g. `~/.nuget/NuGet/NuGet.Config`, `~/.npmrc`). `README.md` says so, rather than promising that a CI's secrets never reach it (_`D727`_ (SPEC-S14-trust.md)).
- _`D734`_ (`live`; changes _`D690`_, refines _`D709`_; review F10, option chosen: "Apply all (Rec.)"): **The limits are best effort**: a process can escape a process group (`setsid`, double forks), and Node has no Windows job objects, so killing the whole process tree is attempted, not guaranteed. Every process runs in a session of its own, with no controlling terminal (standard input, output and error are pipes or ignored), so it can neither prompt on nor read from the user's terminal. The output cap applies while the output streams in (bytes per line and in all), before it is split into lines. The host copy is removed on `SIGINT` and `SIGTERM` too; `README.md` says that a crash can leave one behind in the temporary folder.
- _`D735`_ (`live`, changed by _`D788`_ (PLAN-P20-recorded.md); changes _`D686`_, refines _`D687`_; review F11, option chosen: "Apply all (Rec.)"): **`showroom` itself never writes to the host repository; trusted code can** (_`D681`_ (SPEC-S14-trust.md)). The host copy keeps symbolic links as they are (never rewritten to absolute paths into the host repository), and leaves out a link whose real path leads outside the host repository's root, as `check` does for linked files; `showroom` never writes a virtual file through a link. The host copy is only made when a showcase adapter that uses it has showcases to build.
- _`D736`_ (`live`; refines _`D711`_; review F13, option chosen: "Apply all (Rec.)"): **The Glossary's existing terms are proposed for change with _`S15`_**, as recordings make them too narrow: **Showcase adapter** (builds a showcase into a showcase frame or a recording), **Console panel** and **Status mark** (`runtime` from a showcase frame's page or a recording), **Host check** (under trust, _`D722`_ (SPEC-S14-trust.md)), **Custom showcase adapter** (may record, _`D719`_). Their wording is proposed with _`S15`_'s plan.
