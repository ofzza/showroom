# _`P10.3`_ The new keys

approved 2026-11-13 (option chosen: "Approve and commit (Rec.)"), after its zero-context review (2026-11-13: 15 findings; _`D395`_–_`D401`_ and 11 fixes to the steps)

## Goals

_`D357`_–_`D365`_, _`D374`_, _`D375`_, _`D378`_ and _`D380`_ (SPEC-S10-presentation.md): the markers' `inline`, `block` and `include=` keys, in the marker grammar, `check`'s errors, the host information (`Showcase`), the linked files and the `html` build; included files among the files `serve` watches. Takes _`O62`_'s part on how included files reach the showroom, and _`O65`_ for this segment.

Not in _`P10.3`_: the code pane, a linked showcase shown as a block replacing its paragraph, and the modal's tabs (_`P10.4`_): until then, the showroom shows a linked showcase shown as a block as it shows one shown inline (its showcase frame before its paragraph), and shows no included file; the cheat-sheet (_`D370`_) and this repository's own documentation following the new presentation (_`D381`_) are _`P10.4`_'s too.

Facts found while planning (2026-11-13):

- `parseShowcaseMarker()` (`src/markdown/`) knows the keys `file` and `anchor` (reserved); a repeated key and an unknown key are errors already. `scanMarkdown()` visits the syntax tree without parents.
- `check()` (`src/cli/check/`) checks a linked showcase's entry point (`_checkShowcases()`), then collects the linked files (`_collectLinkedFiles()`) from links, images and linked showcases' entry points, warning (not failing) about one in the output folder or outside the root through a symbolic link.
- A showcase adapter's `validate()` gets the `Showcase`; its `build()` gets the `Showcase`, its folder's virtual files and every virtual file (`hostVirtualFiles`), and returns its `reads`, which `buildShowcases()` (`src/showcases/`) gathers into `watched`.
- The `html` showcase adapter copies every resource of its documentation file's folder next to its page, by name; a linked showcase's page is read from disk.

## Steps

1. **The grammar** (`src/markdown/`): `ShowcaseMarker` gains `display` and `include`; `parseShowcaseMarker()` takes `inline`, `block` (no value; `block=…` an error) and `include=<path>,<path>` (_`D380`_): an empty path (`include=`, `a,,b`, a trailing comma), `?`, `#` and a leading `/` are errors judged on the raw text, as `splitLink()` does, then each path is URL-decoded, one that can't be an error. `scanMarkdown()` visits with ancestors: a link shown as a block must have a paragraph for its parent, whose other children are only whitespace text, wherever the paragraph sits (a list item, a blockquote, nested), except in a footnote definition (_`D399`_); emphasis or a link text around it is an error (_`D360`_). `inline` with `block`, either on a fence (_`D359`_), and `include=` on a resource (_`D361`_) are errors; `anchor=` with `block` is covered by the reserved-key error for now, with no test of its own. Each include is resolved against the documentation file's folder (`resolvePath()`): outside the root, or a folder (a trailing `/`, `.`, `..`), an error; the entry point itself, and a file listed twice after resolving (_`D380`_), are errors here, as they need nothing from the disk.
2. **The host information** (`src/host/`): `Showcase` gains `display` and `include` (_`D365`_, _`D392`_); every hand-written `Showcase` (about 18 literals in 8 files under `src/`, `src/app/`'s tests among them) and `README.md`'s `check --json` example gain them.
3. **`check`** (`src/cli/check/`): included files checked in a pass of their own (`_checkIncludes()`), each error at the showcase's line: a virtual file (any, _`D375`_, _`D396`_) looked up first, by its exact path, and never looked for on disk; then a documentation file (_`D395`_), by its exact path; then a real file: missing, a folder, in the output folder, or outside the root through its real path (_`D378`_), and its path matched exactly on every OS, through its folders' entries as `_checkVirtualFiles()` does (_`D400`_). Only included real files that pass join the linked files (_`D393`_); a file both linked and included is collected once, and its included-file errors stand instead of the link's warnings.
4. **The `html` showcase adapter** (`src/adapters/showcase/html/`): `validate()` rejects an included file outside the entry point's folder, or at the page's own name, judged case-insensitively as the resource check is (_`D374`_); `build()` copies each included file next to the page, at its path relative to the entry point's folder (a real file or a documentation file read from disk, as bytes; a virtual one from `hostVirtualFiles`), an included resource of the documentation file's own folder once, not twice; an included file landing where a resource of the documentation file's folder does is a build error naming both (_`D397`_); an included file that can't be read is a build error with its path, as the entry point is. Its `reads` list each included real or documentation file, and an included virtual file's documentation file, never a virtual path (_`D363`_). Its module header follows.
5. **Watching** (`src/showcases/`): `buildShowcases()` adds every showcase's included files to `watched` (an included virtual file's documentation file, never its virtual path) before any of its early exits (a showcase adapter not available, a build that throws or returns an invalid result), whatever its showcase adapter and whether it builds (_`D363`_).
6. **Fixtures and tests**: the `showcases` fixture gains valid uses (`inline`, `block` in a list item and a blockquote, `include=` of a real file, a binary file, a documentation file, a code block showcase's entry point, and a virtual file of another folder on its custom `demo` showcase adapter, as an `html` showcase can't include outside its entry point's folder), `showcase-errors` every new error (an `html` showcase including another folder's file among them; emphasis around a `block` link; a `block` link in a footnote; a case slip in an included path), `showcase-frames` an `html` showcase including files (a real CSS file, a virtual one, one in a sub-folder) and a linked showcase in another folder; tests in `src/markdown/` (the grammar and the scan), `src/cli/check/` (the errors, the linked files), `src/adapters/showcase/html/` (validation, the build's files and reads), `src/showcases/` (`watched`), the `integration` builds of `showcase-frames`, and `e2e`'s `build` copying an included file and its linked file.
7. **Documentation**: `README.md` (`# Usage`: the keys in the marker grammar, without sections or live showcases of their own, which are _`P10.4`_'s (_`D398`_); `Showcase`'s new fields; `check --json`'s example; the `html` showcase adapter's included files; Linked files: included real files are linked files, with errors where links get warnings; Custom showcase adapters: `display` and `include`), `src/host/`'s `LinkedFile` JSDoc, `AGENTS.md` (Testing's fixtures, Exports, the linked files gotcha), `CONTRIBUTE.md` (the Glossary's "Linked file", _`D401`_; the architecture, if it names the marker keys). Markdown formatted.

## Decisions

- _`D392`_ (`live`; refines _`D365`_ (SPEC-S10-presentation.md); Q1, option chosen: "Always present (Rec.)"): **`Showcase` gains two fields, always present**: `display: 'inline' | 'block'`, how it is shown (`block` for every code block showcase; for a linked showcase, `inline` unless its marker says `block`), and `include: string[]`, its included files' paths, POSIX-style, relative to the root, resolved, in the marker's order (empty when it has none). Rejected: optional fields only where they apply (`display?` on links, `include?` when not empty).
- _`D393`_ (`live`; resolves _`O62`_'s part on included real files; Q2, option chosen: "As linked files (Rec.)"): **Included real files are linked files**: `check` adds each to `linkedFiles`, so it is copied to `files/<path>`, served and watched as linked files are (_`S9`_ (SPEC.md)), and _`P10.4`_'s tabs fetch it as the modal does; a binary one, or one over 1 MB, is a linked file with `text: false` (_`D378`_ (SPEC-S10-presentation.md)). Unlike a link's target, an included file in the output folder or outside the root through its real path is an error, not a warning (_`D378`_). Included virtual files aren't copied: their content reaches the showroom with the shown host information (_`P10.4`_, _`D394`_). Rejected: a list and an output folder of their own.
- _`D394`_ (`live`; changes _`D382`_ (PLAN-P10-presentation.md), _`R27`_; Q3, option chosen: "Move to P10.4 (Rec.)"): **What the shown host information gains is _`P10.4`_'s**, with the code pane that uses it: _`P10.3`_ changes the host information only (`Showcase`, `linkedFiles`), so nothing unused reaches the showroom. Rejected: adding the shown fields in _`P10.3`_.
- _`D395`_ (`live`; review 2026-11-13 #3, Q1, the user: "I would just allow including Q1 and Q2 cases"): **A showcase can include a documentation file**: not a linked file (`check` collects documentation files as such), the `html` build reads it from disk, and _`P10.4`_ takes its tab's content from the documentation files the shown host information already holds. Rejected: an error.
- _`D396`_ (`live`; refines _`D375`_ (SPEC-S10-presentation.md); review 2026-11-13 #5, Q2, the user, as for _`D395`_): **A showcase can include any virtual file, a code block showcase's entry point too** (`README.showcase-2.html`), whose generated name changes when a showcase is added above it; `README.md` says so. Rejected: resources only.
- _`D397`_ (`live`; review 2026-11-13 #1, Q3, "Everything else I agree"): **An `html` showcase's included file landing where a resource of its documentation file's folder does is a build error naming both**, as a resource named like the page is today (`validate()` sees no virtual files). Rejected: the included file winning.
- _`D398`_ (`live`; changes _`D382`_ (PLAN-P10-presentation.md), _`R28`_; review 2026-11-13 #10, Q4, as _`D397`_): **`README.md`'s sections on `block` and `include=`, with their live showcases, are _`P10.4`_'s**, with the cheat-sheet, so this repository's showroom never shows them before the code pane does; _`P10.3`_ only adds the keys to `# Usage`'s marker grammar. Rejected: writing them in _`P10.3`_.
- _`D399`_ (`live`; refines _`D360`_ (SPEC-S10-presentation.md); review 2026-11-13 #11, Q5, as _`D397`_): **A linked showcase shown as a block can't be in a footnote definition**: a `check` error. Rejected: allowing it.
- _`D400`_ (`live`; refines _`D380`_ (SPEC-S10-presentation.md); review 2026-11-13 #5, Q6, as _`D397`_): **An included real file's path is matched exactly on every OS**, through its folders' entries, so a case slip fails on macOS and Windows as it does on Linux. Rejected: leaving it to the file system, as for links.
- _`D401`_ (`live`; review 2026-11-13 #8, Q7, as _`D397`_): **Glossary change, applied with _`P10.3`_'s implementation**: "Linked file" (`CONTRIBUTE.md`) becomes "A file in the host repository that isn't a documentation file, which a documentation file links to by a relative path (or shows as an image), or a showcase includes (an included file); copied into the showroom, …" (the rest unchanged).
