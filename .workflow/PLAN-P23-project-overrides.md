# _`P23`_ Project overrides

approved 2026-11-23 (option chosen: "Approve and commit (Rec.)"), after its zero-context review (_`D890`_–_`D893`_); implemented 2026-11-23 (checkpoint option chosen: "Approve and commit (Rec.)"; the merge as three functions, `getProjectSettings()`, `mergeProjectInformation()` and `getShowcaseProject()`; no host check at all without a merged project, tested on scratch copies of `project-overrides`; and `installFixture()` refreshing a kept install's fixture files, kept: "Keep, same commit (Rec.)")

_`S18`_ (SPEC.md), as revised by _`R64`_ (_`D877`_–_`D882`_): `showroom.json`'s `project` becomes an object only, holding the project file's `path`, the project information, `sourceRoot`, `ignore`, `code` and `documentation`; `stack` alone decides whether a stack adapter runs, and `project`'s fields override what it gives, `null` unsetting one; showcase adapters get the merged project. A breaking change of `showroom.json` and of the exported types. One segment, with no child segments.

## Decisions

- _`D883`_ (`live`, refined by _`D892`_, _`D893`_; Q1, option chosen: "After the merge (Rec.)"): **`name` is required once, after the merge.** `StackAdapter.readProject()` returns the project information with `name` optional (the `typescript` stack adapter no longer throws on a `package.json` without one; the `dotnet` stack adapter always has one, its project file's name at least), and `check()` requires `name` once `project`'s fields are applied, with one error naming both places (e.g. `The project has no name: package.json gives none, and showroom.json's "project" gives none`). A missing or invalid project file is still the stack adapter's error (_`D880`_ (SPEC.md)). `StackAdapter`'s documented semantics change; stack adapters stay built-in (_`D868`_ (SPEC.md)). Rejected: the stack adapter requiring `name`, as now.
- _`D884`_ (`live`; Q2, option chosen: "ProjectConfiguration / ShowcaseProject (Rec.)"): **Two new exported types.** `ProjectConfiguration` (`src/configuration/`): `Configuration.project`'s type, every field optional: `path`, the project information's fields and `sourceRoot` as `string | null`, `ignore`, `code` and `documentation` as `string[] | null`. `ShowcaseProject` (`src/adapters/showcase/`, experimental): `ProjectInformation` with `path?`, `sourceRoot`, `ignore`, `code` and `documentation` (`string[]`), the type of `ShowcaseBuildRequest.project` and `ShowcaseCheckContext.project`, now always given. Rejected: `ProjectOverrides` / `ResolvedProject` (nothing is overridden without a stack adapter).
- _`D885`_ (`live`, refined by _`D892`_; changes _`D871`_ (PLAN-P22-stackless.md); Q3, option chosen: "Pure function + defaultProject (Rec.)"): **The merged project is computed by pure functions in `src/adapters/stack/resolve/`.** `resolveStack(configuration)` returns the stack adapter only when `stack` names a built-in one exactly, and no longer fails (_`D877`_ (SPEC.md)); `getShowcaseProject(configuration, information)` (its signature changes) gives the `ShowcaseProject` from the configuration, the stack's defaults and the merged project information, reading no file, so `check()` (the host check context) and `buildShowcases()` (from `host.project`) both call it. `StackAdapter` gets an optional `defaultProject` (`package.json` for `typescript`, none for `dotnet`), so `path` is known when it is the default. Rejected: a new `HostInformation` field carrying the merged project.
- _`D886`_ (`live`, refined by _`D892`_; Q4, option chosen: "All that apply, minus outDir (Rec.)"): **`ShowcaseProject`'s lists hold every pattern that applies, without the output folder**: `documentation` the built-in patterns, then the stack adapter's (unless `null`), then the configured ones; `ignore` and `code` the stack adapter's (unless `null`), then the configured ones. The output folder is no project setting (`--out-dir` changes it per run), so it isn't in `ignore`. Rejected: adding the output folder; leaving out the built-in documentation patterns.
- _`D887`_ (`live`, changed by _`D891`_; Q5, option chosen: "Two fixtures + unit tests (Rec.)"): **Two new fixtures, and unit tests on hand-written values.** `test/fixtures/project-overrides/` (`typescript`: a `package.json` without a `name`; `project` giving `name`, `version: null`, a `sourceRoot`, `ignore: null` with patterns of its own) and `test/fixtures/project-overrides-dotnet/` (a `.csproj` by `path`, with overrides), each with a custom showcase adapter whose host check reports the `ShowcaseProject` it is given as a warning, as `stackless`'s `reporter` does; unit tests of the validation and of `getShowcaseProject()` on hand-written configurations. The 39 fixtures' `showroom.json` files using the moved keys or a string `project`, and this repository's own, are migrated: the keys, and the string as `path`, into the object. Rejected: scratch copies of existing fixtures only; a `typescript` fixture only.
- _`D888`_ (`live`, refined by _`D893`_; changes _`D870`_, _`D876`_ (PLAN-P22-stackless.md)): **`validateConfiguration()` checks every rule it can without reading a file** (as _`D870`_ (PLAN-P22-stackless.md) did): `project` an object (a string is an error saying the path is now `project.path`); each field's type (`null` allowed for every field; strings non-empty); an unknown key in the object (a top-level key's name, e.g. `outDir`, adding that it belongs at the top level, as now); and, when `stack` names no stack adapter (exactly), `path` given and `name` missing or `null` are errors, each saying that `stack` names no stack adapter and listing them, or that `stack` is left out (so a missing `stack` and `project` give the missing `name`'s error); a built-in name in another case is refused (_`D874`_ (PLAN-P22-stackless.md)). `sourceRoot`, `ignore`, `code` and `documentation` at the top level are unknown keys (_`D878`_ (SPEC.md)). `check()`'s unknown stack error goes, as `resolveStack()` no longer fails.
- _`D889`_ (`live`, refined by _`D890`_, _`D892`_): **`check()` merges in one place**: with a stack adapter, it reads the project information (`project.path`, inside the host repository, or the stack adapter's default), then applies the project information's fields (`null` dropping one), then requires `name` (_`D883`_); without one, it takes the fields given. `sourceRoot` is `project.sourceRoot`, else the stack adapter's (`.` when `null`, or without one); the ignore, code and documentation matchers take the stack's patterns unless the list is `null`, then the configured ones (`createIgnoreMatcher()` and `readIgnoreMatcher()` likewise). The host information's `project` is the merged project information only (_`D882`_ (SPEC.md)).
