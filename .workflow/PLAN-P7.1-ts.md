## _`P7.1.1`_ Building `ts` showcases

implemented 2026-11-13 (checkpoint option chosen: "Approve and commit"; _`D271`_ and _`D272`_ decided at its checkpoint); approved 2026-11-13 (option chosen: "Approve and commit (Rec.)"); choices _`D247`_–_`D260`_ decided 2026-11-13 (Q1–Q9 and Q11 of the planning discussion as recommended, in a batch; Q10, Q13 and Q14 discussed; Q12 settled by a spike; each decision names its question); zero-context review 2026-11-13 (one agent, "approve with fixes"), its outcomes in _`D261`_–_`D270`_ and the steps, documentation and tests below

### Goals

The `ts` showcase adapter builds `ts` showcases into showcase frames (_`D97`_, _`D233`_, _`D235`_, _`D236`_ (SPEC-S6-showcases.md); _`D244`_ (PLAN-P7-ts-react.md)), in `check --showcases`, `build` and `serve` (_`D82`_, _`D102`_ (SPEC-S6-showcases.md), _`D243`_ (PLAN-P7-ts-react.md)), and `serve` watches the ignored files showcases depend on (_`D256`_). Type checking is _`P7.1.2`_'s.

### Steps

1. **The showcase adapter interface** (`src/adapters/showcase/`): `hostVirtualFiles` (_`D251`_) and `mode` (_`D260`_) in `ShowcaseBuildRequest`, and `warnings` in `ShowcaseBuildResult` (_`D270`_). `buildShowcases()` (`src/showcases/`) passes both (its `mode` an option, `production` by default), reports warnings, and returns `watched` (_`D264`_).
2. **The `ts` showcase adapter's static half** (`src/adapters/showcase/ts/`): `validate()` (_`D247`_, _`D248`_); registered as a built-in showcase adapter, and dropped from `PLANNED_SHOWCASE_ADAPTER_NAMES` (`src/adapters/showcase/registry/`); no host requirements (`check?` left out until _`P7.1.2`_).
3. **The console panel** (`src/adapters/showcase/ts/console/`, Node-free): the self-contained script (_`D250`_), and the page around it: the showcase frame root, the console panel in its shadow root, themed, with its maximum height (_`D249`_, _`D268`_); the frame script not counting the panel's growth (_`D268`_, `src/frame/`).
4. **The build**: Vite loaded with `import()` inside `build()` (`check`, and so `src/index.ts`, reaches the registry); _`D244`_'s inline configuration (`configFile: false`, `envDir: false`, `publicDir: false`, `cacheDir` in the build's scratch folder, `write: false`, `logLevel: 'silent'`), with `base` and `root` pinned (_`D262`_), the empty PostCSS configuration (_`D253`_) and the request's mode pinned in the configuration (_`D254`_, _`D261`_); warnings collected (_`D270`_); the entry point as the input; the page written by the adapter (the showcase frame root, the console panel's script, the module and its CSS), not by Vite's HTML pipeline; the bundle's chunks and assets as the showcase frame's files.
5. **Its plugins**: virtual files resolved as if on disk (_`D252`_), and reads recorded as modules load (_`D256`_).
6. **Build errors and warnings**: Vite's errors and warnings mapped to `ShowcaseBuildError`s as _`D263`_ says, with the virtual file's path and its line in the code block, or the real file's path and line, which `getBuildErrorIssue()` already places in documentation files (_`D102`_ (SPEC-S6-showcases.md)).
7. **`serve`** (`src/cli/serve/`): its runs build in development mode; the watcher's `ignored` function lets through the latest run's `watched` paths and the folders leading to them, and the host watcher adds and removes them in Vite's watcher after each run (_`D256`_, _`D264`_, _`D265`_).
8. **Measuring** (_`D255`_): an `integration` fixture with 10 `ts` showcases (committed), timing one `buildShowcases()` run, reported at the checkpoint.

### Decisions

- _`D247`_ (`live`; Q1; resolves _`O43`_ (SPEC-S6-showcases.md)): **A `ts` entry point is TypeScript or JavaScript**: a ` ```ts ` or ` ```js ` code block (or ` ```typescript `, ` ```javascript `), or a linked `.ts`, `.mts`, `.js` or `.mjs` file; anything else, `tsx` and `jsx` included, is a `check` error, which names the `react` showcase adapter for `tsx` and `jsx`. Rejected: `ts` only (a plain JavaScript demo has to be renamed); also `tsx`/`jsx` without React (blurs the line with `react`).
- _`D248`_ (`live`; Q2): **The `ts` showcase adapter's only option is `typeCheck`**, a boolean, `true` by default (_`D103`_, _`D234`_ (SPEC-S6-showcases.md)); any other key, or a value that isn't a boolean, is a `check` error. Until _`P7.1.2`_, it is accepted and has no effect, and `README.md` says type checking is coming; _`P7.1.2`_ replaces that sentence. Rejected: rejecting `typeCheck` until _`P7.1.2`_ (showcases written meanwhile break when it lands); keeping `ts` unavailable until _`P7.1.2`_ (no live example to check in between).
- _`D249`_ (`live`; Q3; refines _`D233`_ (SPEC-S6-showcases.md)): **The showcase frame root and the console panel**: the `ts` showcase frame's page holds `<div id="root"></div>`, the showcase frame root, which the showcase may write to (and which _`P7.2`_'s mount module renders into); the console panel is a separate element after it, inside a shadow root, so the showcase's CSS and the panel's styles never mix; it follows the theme the frame script sets on `<html>` (_`D77`_). `README.md` documents `#root`. Rejected: the showcase owning `document.body`, with the panel as a fixed overlay (`body.innerHTML = …` wipes the panel); a `showroom`-specific id (less familiar than `#root`).
- _`D250`_ (`live`; Q4): **The console panel's script is self-contained and inlined** into the page as its source text, before the showcase's module, like the frame script (_`frameScript()`_, `src/frame/`), and tested the same way, on a stubbed `window`. It lives in a Node-free `src/adapters/showcase/ts/console/`, never re-exported. It wraps `console.log`, `info`, `warn`, `error` and `debug` (still calling the originals), and listens to `error` and `unhandledrejection`. Values: strings as they are; objects and arrays as indented JSON; an `Error` as its stack; a fallback for the rest (`String()`, `[Circular]` for cycles). Rejected: an asset file the build emits (one more request, and a name that could clash with the showcase's own).
- _`D251`_ (`live`; Q5): **A build gets every virtual file of the host repository**: `ShowcaseBuildRequest` gains `hostVirtualFiles`, and `virtualFiles` keeps holding those of the documentation file's folder, so a virtual file in another folder is reachable by a relative path (_`D91`_ (SPEC-S6-showcases.md)). Additive to the experimental interface (_`D133`_ (SPEC-S6-showcases.md)); `README.md` › `# Usage` and `AGENTS.md` › Exports are updated. Rejected: `virtualFiles` holding every virtual file (changes its meaning for existing custom showcase adapters); no virtual files from other folders (narrowing _`D91`_).
- _`D252`_ (`live`; Q6; with _`D251`_, resolves _`O36`_ (PLAN-P7-ts-react.md)): **Imports reach virtual files as if they were on disk**: a Vite plugin resolves every relative import, from any importer (a virtual or a real file), against the virtual files' absolute paths; an import without an extension tries Vite's extensions in order, at each the virtual file before the real one. A virtual and a real file of the same name never reach a build, as `check` reports the collision (_`D91`_). Each case of _`O36`_ gets a test. Rejected: exact relative paths only (`import './util'` would fail where the same file on disk works).
- _`D253`_ (`live`; Q7; resolves _`O32`_ (PLAN-P7-ts-react.md)): **The host's PostCSS configuration is ignored; its tsconfig applies as Vite reads it**: the build pins an empty inline PostCSS configuration, so a host's `postcss.config.*` never loads (_`D236`_ (SPEC-S6-showcases.md) excludes the host's bundler configuration); what Vite's transform reads from the nearest `tsconfig.json` (e.g. `experimentalDecorators`, `useDefineForClassFields`, the JSX settings) applies, matching what type checking reads (_`D234`_ (SPEC-S6-showcases.md)), and a test covers that lookup for virtual modules. Rejected: loading the host's PostCSS configuration (unbounded, _`K11`_); ignoring tsconfig too (decorators would compile differently from the host's own code).
- _`D254`_ (`live`; Q8; resolves _`O38`_ (PLAN-P7-ts-react.md)): **`serve` builds showcases in development mode**: unminified, with inline source maps, and `process.env.NODE_ENV` and `import.meta.env` set for development; `build` and `check --showcases` build for production: minified, without source maps. Rejected: production everywhere (no development warnings in `serve`, e.g. React's in _`P7.2`_); development mode without source maps.
- _`D255`_ (`live`; Q9; resolves _`O34`_ (PLAN-P7-ts-react.md)): **One Vite build per showcase, one after another**, so errors stay per showcase, as in `buildShowcases()` today. The implementation measures one `serve` rerun on a fixture with 10 `ts` showcases and reports it at the checkpoint; above 2 s, _`O28`_ (PLAN-P4.3-serve.md) is taken up, in a segment of its own after _`P7`_; otherwise it stays open. Rejected: one Vite build per run with every `ts` showcase as an input (one failure can mask others, and shared chunks need splitting per showcase frame); taking up _`O28`_ before measuring.
- _`D256`_ (`live`, refined by _`D272`_; Q10; replaces _`D206`_ (PLAN-P4.3-serve.md); resolves _`O35`_ (PLAN-P7-ts-react.md)): **`serve` watches the ignored files showcases depend on** (option chosen: "B + custom modules (Rec.)"): the reads of every showcase built in the latest run, by any showcase adapter and failed builds included, and the custom showcase adapter modules listed in `showroom.json`, are watched even under ignored folders (never under `node_modules` or `.git`, which Vite's watcher always ignores). The watcher's `ignored` function lets them, and the folders leading to them, through; reads newly under an ignored folder are added to the watcher after the run; each run's set replaces the previous one. A change to one reruns the check and every showcase build, as any watched change does (_`D184`_ (PLAN-P4.3-serve.md)). Ignored files still never become documentation or code files. A `ts` build records its reads with a Vite plugin, as modules load (so a failed build has them too): virtual files as their documentation files, and real files under the host root outside `node_modules`; `buildShowcases()` keeps failed builds' reads. Rejected: keeping _`D206`_ and documenting the limitation (the host's own package, through its `dist/`, is the usual way a library demos itself, _`D236`_ (SPEC-S6-showcases.md)); watching only the files reached through the host's own package (needs tracking which reads came that way); watching reads without the custom showcase adapter modules (a module built into `dist/` would never rerun).
- _`D257`_ (`live`; Q11; resolves the `ts` part of _`O19`_ (SPEC-S6-showcases.md)): **No per-host setup for `ts` showcases**, as for React (_`D231`_ (SPEC-S6-showcases.md)): a showcase imports what it needs (global styles, polyfills) itself. Where a `ts` showcase's editable parts are found is left to the playground (_`D85`_, _`D101`_ (SPEC-S6-showcases.md)), as _`O16`_ left it for React. Rejected: a host-wide setup module loaded before every `ts` showcase.
- _`D258`_ (`live`; Q13; resolves the _`P7.1.1`_ part of _`O42`_ (PLAN-P7-ts-react.md)): **Two Glossary terms**, added to `CONTRIBUTE.md` with the code that introduces them: **Console panel**: the part of a `ts` or `react` showcase frame listing what the showcase writes to the browser's console, its uncaught errors and its rejected promises; hidden while nothing has been logged. **Showcase frame root**: the empty element (`#root`) in a showcase frame's page that a `ts` showcase may write to, and that the `react` showcase adapter renders the showcase into; above the console panel. Rejected: "page container" (doesn't say which page: the showcase frame's, the showroom's, or where the showcase frame is placed); "frame root" and "showcase root" (less tied to the showcase frame); "showcase frame console" for the console panel (longer, and the showroom has no other console panel).

The package's name and its `./extra` subpath resolve, from the virtual module and from a real file it imports, with and without `resolve.preserveSymlinks`, and the chunk's `moduleIds` list every file read; a subpath `exports` doesn't list fails the build.
- _`D260`_ (`live`; Q14): **The build mode is in the request**: `ShowcaseBuildRequest` gains `mode`, `'development'` or `'production'` (_`D254`_); `buildShowcases()` takes it as an option, which `serve` sets to `'development'`. - _`D262`_ (`live`; refines _`D244`_ (PLAN-P7-ts-react.md) for `ts`; from review 2026-11-13 #2): **`base: './'` and `root` (the host repository's root) are pinned too**, so asset URLs, the preload helper and dynamic chunks' CSS stay relative to the showcase frame's folder (`showcases/<…>/`, and GitHub Pages sub-paths), and nothing depends on the working directory. Each error shape gets a unit test.
- _`D264`_ (`live`, refined by _`D272`_; refines _`D256`_; from review 2026-11-13 #5, #8): **Where the watched files are kept**: `BuildShowcasesResult` gains `watched`, the root-relative paths of every showcase's reads (successful and failed builds) and of the custom showcase adapter modules listed in `showroom.json`; `serve`'s state carries it, and the host watcher takes a `watch(paths)` option, which `serve` wires to Vite's watcher. No automated test edits watched files (_`D190`_ (PLAN-P4.3-serve.md)), so the checkpoint asks the user to check by hand: `tsc --watch` alongside `serve` on a host importing itself by name, then a clean rebuild of its `dist/`.
- _`D266`_ (`live`; refines _`D252`_; from review 2026-11-13 #9): **Two more resolution cases, as on disk**: a `.js` specifier naming a `.ts` virtual file (TypeScript's convention, which Vite follows for real files), and a folder import reaching a virtual `index.ts` (or another extension); both tested.

- _`D268`_ (`live`; refines _`D249`_, _`D250`_; from review 2026-11-13 #4; option chosen: "Both"): **The console panel and the frame script's growth guard**: the console panel has a maximum height (about 12 lines) and scrolls inside it, following the newest line; and the frame script doesn't count the console panel's own growth towards `MAX_REPEATED_GROWTHS` (`src/frame/`): the console script tells it about each growth of the panel (e.g. a window event whose name reaches the frame script through its constants argument, as it must stay self-contained), and a growth matching it is not a repeated growth. - _`D270`_ (`live`; from review 2026-11-13 #11; option chosen: "Add it now"): **Build warnings reach the host**: `ShowcaseBuildResult` gains an optional `warnings` (`ShowcaseBuildError`s: a message, and optionally a path and line), on either outcome; `checkBuildResult()` validates it, and `buildShowcases()` reports each as a warning issue at its place (as `getBuildErrorIssue()` places errors), which `check --showcases` and `build` print and `serve` shows in its issues bar, without failing anything. Additive to the experimental interface (_`D133`_ (SPEC-S6-showcases.md)), documented in `README.md` › `# Usage`. Rejected: an open point, decided with _`P7.1.2`_'s interface change (_`O33`_ (PLAN-P7-ts-react.md)).

## _`P7.1.2`_ Type checking `ts` showcases

approved 2026-11-13 (option chosen: "Approve and commit (Rec.)"); choices _`D273`_–_`D287`_ decided 2026-11-13 (after the _`K16`_ spike; Q1–Q14 of the planning discussion, the user's words or chosen options named in each decision); zero-context review 2026-11-13 (one agent, "approve with fixes", 17 findings), its outcomes in _`D288`_–_`D299`_ (with Q16–Q18) and the steps, documentation and tests below

### Goals

The `ts` showcase adapter type checks its showcases with the host repository's own TypeScript and the nearest `tsconfig.json` (_`D103`_, _`D234`_ (SPEC-S6-showcases.md)), unless `typeCheck` is `false` (_`D248`_), reporting type errors at their lines as build errors (_`D102`_ (SPEC-S6-showcases.md)), with `typescript` a host requirement only where some showcase type checks (_`O33`_ (PLAN-P7-ts-react.md)). TypeScript 7 is left for later (_`L12`_ (PLAN.md)).

### Steps

1. **The showcase adapter interface** (`src/adapters/showcase/`): `check?(root, showcases)` (_`D277`_) returning `{ errors, warnings }` (_`D286`_), as a new exported type (e.g. `ShowcaseHostCheck`); `check()` (`src/cli/check/`) passes each showcase adapter the showcases using it whose validation passed, with their validated options (_`D296`_), validates the returned shape (as `checkBuildResult()` does for builds), and reports errors and warnings as issues, both prefixed `Showcase adapter "<name>":`, with a hint on the breaking change when a custom showcase adapter returns an array. Every test adapter implementing `check` moves to the new shape: `test/fixtures/showcase-adapters/adapters/good.js` and `good.mjs`, `test/fixtures/showcases/adapters/demo.js`, `test/fixtures/showcase-errors/adapters/needy.js`, and the registry test's inline module.
2. **Finding the host's TypeScript** (`src/adapters/showcase/ts/typecheck/`, Node code, never re-exported): `typescript` resolved as Node resolves it from a documentation file's folder (_`D276`_, _`D295`_), its version read from `typescript/package.json` and judged (_`D275`_: ≥ 5.0 and < 7; 7 and later skipped, _`D274`_); loaded with `createRequire`, once per resolved path for the process (Node caches it); `showroom`'s own `typescript` only through `import type`. The `ts` showcase adapter's `check()` uses it per documentation folder of the showcases that type check: an error where `typescript` is missing or older than 5.0, a warning where it is 7 or later, each naming the folder and the version found (_`D274`_, _`D296`_).
3. **The compiler options and roots** (_`D280`_, _`D281`_, _`D283`_, _`D288`_, _`D290`_, _`D291`_): the nearest `tsconfig.json` from the documentation file's folder up to the host root, parsed with its `extends` followed; its `files`, `include` and `exclude` as roots, with the entry point added; `noEmit` forced, and _`D288`_'s emit options dropped; `allowJs` for a `js` or `mjs` entry point, or when the showcase sets `allowJs`; TypeScript's own defaults, and the entry point the only root, when there is no tsconfig. The tsconfig's own errors are reported at its path and line (_`D291`_).
4. **The program** (_`D273`_, _`D284`_, _`D293`_, _`D294`_): a compiler host serving the request's `hostVirtualFiles` from memory (`fileExists`, `readFile`, `getSourceFile`), with paths normalised (`ts.normalizePath()`, `getCanonicalFileName()`, _`D292`_) and `getCurrentDirectory()` pinned to the documentation file's folder (_`D293`_); parsed source files shared between the run's showcases, keyed by the TypeScript install and the full compiler options (_`D294`_), released in `close()`.
5. **Type errors** (_`D289`_, _`D292`_): the diagnostics of the files the showcase reaches (the entry point and, transitively, every file it imports or references), except in `node_modules` (judged on the root-relative path, as `getHostPath()` does) and TypeScript's default library files, plus the program's global and option diagnostics; each mapped to a `ShowcaseBuildError`: `TS<code>: <the flattened message chain>`, with absolute paths in the message made root-relative (virtual files by their virtual path), a virtual file's virtual path or a real file's root-relative path, and its line; an error without a file, or in a file outside the host root, gets no path, so it is placed at the showcase.
6. **In `build()`** (_`D278`_, _`D285`_, _`D294`_, _`D297`_): after a successful bundle, when `typeCheck` is on, TypeScript is found again (this is another showcase adapter object than `check()`'s) and, when it is supported, the showcase is type checked; when it is missing or unsupported, type checking is skipped silently (`check` reported it). Type errors fail the build, keeping the bundle's warnings; the type checker's reads (the program's source files and the tsconfig chain, under the host root, outside `node_modules`) are added to `reads`.
7. **Measuring** (_`D284`_, _`D293`_): `showcase-ts-many`'s 10 showcases, now type checked (its tsconfig with explicit `types`), timed again as _`D255`_ did, and reported at the checkpoint.
