## _`P7.1.1`_ Building `ts` showcases

approved 2026-11-13 (option chosen: "Approve and commit (Rec.)"); choices _`D247`_–_`D260`_ decided 2026-11-13 (Q1–Q9 and Q11 of the planning discussion as recommended, in a batch; Q10, Q13 and Q14 discussed; Q12 settled by a spike; each decision names its question); zero-context review 2026-11-13 (one agent, "approve with fixes"), its outcomes in _`D261`_–_`D270`_ and the steps, documentation and tests below

### Goals

The `ts` showcase adapter builds `ts` showcases into showcase frames (_`D97`_, _`D233`_, _`D235`_, _`D236`_ (SPEC-S6-showcases.md); _`D244`_ (PLAN-P7-ts-react.md)), in `check --showcases`, `build` and `serve` (_`D82`_, _`D102`_ (SPEC-S6-showcases.md), _`D243`_ (PLAN-P7-ts-react.md)), and `serve` watches the ignored files showcases depend on (_`D256`_). Type checking is _`P7.1.2`_'s.

### Steps

1. **The showcase adapter interface** (`src/adapters/showcase/`): `hostVirtualFiles` (_`D251`_) and `mode` (_`D260`_) in `ShowcaseBuildRequest`, and `warnings` in `ShowcaseBuildResult` (_`D270`_). `buildShowcases()` (`src/showcases/`) passes both (its `mode` an option, `production` by default), reports warnings, and returns `watched` (_`D264`_).
2. **The `ts` showcase adapter's static half** (`src/adapters/showcase/ts/`): `validate()` (_`D247`_, _`D248`_); registered as a built-in showcase adapter, and dropped from `PLANNED_SHOWCASE_ADAPTER_NAMES` (`src/adapters/showcase/registry/`); no host requirements (`check?` left out until _`P7.1.2`_).
3. **The console panel** (`src/adapters/showcase/ts/console/`, Node-free): the self-contained script (_`D250`_), and the page around it: the showcase frame root, the console panel in its shadow root, themed, with its maximum height (_`D249`_, _`D268`_); the frame script not counting the panel's growth (_`D268`_, `src/frame/`).
4. **The build**: Vite loaded with `import()` inside `build()` (`check`, and so `src/index.ts`, reaches the registry); _`D244`_'s inline configuration (`configFile: false`, `envDir: false`, `publicDir: false`, `cacheDir` in the build's scratch folder, `write: false`, `logLevel: 'silent'`), with `base` and `root` pinned (_`D262`_), the empty PostCSS configuration (_`D253`_) and the request's mode pinned in the configuration (_`D254`_, _`D261`_); warnings collected (_`D270`_); the entry point as the input; the page written by the adapter (the showcase frame root, the console panel's script, the module and its CSS), not by Vite's HTML pipeline; the bundle's chunks and assets as the showcase frame's files.
5. **Its plugins**: virtual files resolved as if on disk (_`D252`_), and reads recorded as modules load (_`D256`_).
6. **Build errors and warnings**: Vite's errors and warnings mapped to `ShowcaseBuildError`s as _`D263`_ says, with the virtual file's path and its line in the code block, or the real file's path and line, which `getBuildErrorIssue()` already places in documentation files (_`D102`_ (SPEC-S6-showcases.md)).
7. **`serve`** (`src/cli/serve/`): its runs build in development mode; the watcher's `ignored` function lets through the latest run's `watched` paths and the folders leading to them, and the host watcher adds and removes them in Vite's watcher after each run (_`D256`_, _`D264`_, _`D265`_).
8. **Measuring** (_`D255`_): an `integration` fixture with 10 `ts` showcases (committed), timing one `buildShowcases()` run, reported at the checkpoint.

### Decisions

- _`D247`_ (`live`; Q1; resolves _`O43`_ (SPEC-S6-showcases.md)): **A `ts` entry point is TypeScript or JavaScript**: a ` ```ts ` or ` ```js ` code block (or ` ```typescript `, ` ```javascript `), or a linked `.ts`, `.mts`, `.js` or `.mjs` file; anything else, `tsx` and `jsx` included, is a `check` error, which names the `react` showcase adapter for `tsx` and `jsx`. Rejected: `ts` only (a plain JavaScript demo has to be renamed); also `tsx`/`jsx` without React (blurs the line with `react`).
- _`D248`_ (`live`; Q2): **The `ts` showcase adapter's only option is `typeCheck`**, a boolean, `true` by default (_`D103`_, _`D234`_ (SPEC-S6-showcases.md)); any other key, or a value that isn't a boolean, is a `check` error. Until _`P7.1.2`_, it is accepted and has no effect, and `README.md` says type checking is coming; _`P7.1.2`_ replaces that sentence. Rejected: rejecting `typeCheck` until _`P7.1.2`_ (showcases written meanwhile break when it lands); keeping `ts` unavailable until _`P7.1.2`_ (no live example to check in between).
- _`D249`_ (`live`; Q3; refines _`D233`_ (SPEC-S6-showcases.md)): **The showcase frame root and the console panel**: the `ts` showcase frame's page holds `<div id="root"></div>`, the showcase frame root, which the showcase may write to (and which _`P7.2`_'s mount module renders into); the console panel is a separate element after it, inside a shadow root, so the showcase's CSS and the panel's styles never mix; it follows the theme the frame script sets on `<html>` (_`D77`_). `README.md` documents `#root`. Rejected: the showcase owning `document.body`, with the panel as a fixed overlay (`body.innerHTML = …` wipes the panel); a `showroom`-specific id (less familiar than `#root`).
- _`D250`_ (`live`; Q4): **The console panel's script is self-contained and inlined** into the page as its source text, before the showcase's module, like the frame script (_`frameScript()`_, `src/frame/`), and tested the same way, on a stubbed `window`. It lives in a Node-free `src/adapters/showcase/ts/console/`, never re-exported. It wraps `console.log`, `info`, `warn`, `error` and `debug` (still calling the originals), and listens to `error` and `unhandledrejection`. Values: strings as they are; objects and arrays as indented JSON; an `Error` as its stack; a fallback for the rest (`String()`, `[Circular]` for cycles). Rejected: an asset file the build emits (one more request, and a name that could clash with the showcase's own).
- _`D251`_ (`live`; Q5): **A build gets every virtual file of the host repository**: `ShowcaseBuildRequest` gains `hostVirtualFiles`, and `virtualFiles` keeps holding those of the documentation file's folder, so a virtual file in another folder is reachable by a relative path (_`D91`_ (SPEC-S6-showcases.md)). Additive to the experimental interface (_`D133`_ (SPEC-S6-showcases.md)); `README.md` › `# Usage` and `AGENTS.md` › Exports are updated. Rejected: `virtualFiles` holding every virtual file (changes its meaning for existing custom showcase adapters); no virtual files from other folders (narrowing _`D91`_).
- _`D252`_ (`live`; Q6; with _`D251`_, resolves _`O36`_ (PLAN-P7-ts-react.md)): **Imports reach virtual files as if they were on disk**: a Vite plugin resolves every relative import, from any importer (a virtual or a real file), against the virtual files' absolute paths; an import without an extension tries Vite's extensions in order, at each the virtual file before the real one. A virtual and a real file of the same name never reach a build, as `check` reports the collision (_`D91`_). Each case of _`O36`_ gets a test. Rejected: exact relative paths only (`import './util'` would fail where the same file on disk works).
- _`D253`_ (`live`; Q7; resolves _`O32`_ (PLAN-P7-ts-react.md)): **The host's PostCSS configuration is ignored; its tsconfig applies as Vite reads it**: the build pins an empty inline PostCSS configuration, so a host's `postcss.config.*` never loads (_`D236`_ (SPEC-S6-showcases.md) excludes the host's bundler configuration); what Vite's transform reads from the nearest `tsconfig.json` (e.g. `experimentalDecorators`, `useDefineForClassFields`, the JSX settings) applies, matching what type checking reads (_`D234`_ (SPEC-S6-showcases.md)), and a test covers that lookup for virtual modules. Rejected: loading the host's PostCSS configuration (unbounded, _`K11`_); ignoring tsconfig too (decorators would compile differently from the host's own code).
- _`D254`_ (`live`; Q8; resolves _`O38`_ (PLAN-P7-ts-react.md)): **`serve` builds showcases in development mode**: unminified, with inline source maps, and `process.env.NODE_ENV` and `import.meta.env` set for development; `build` and `check --showcases` build for production: minified, without source maps. Rejected: production everywhere (no development warnings in `serve`, e.g. React's in _`P7.2`_); development mode without source maps.
- _`D255`_ (`live`; Q9; resolves _`O34`_ (PLAN-P7-ts-react.md)): **One Vite build per showcase, one after another**, so errors stay per showcase, as in `buildShowcases()` today. The implementation measures one `serve` rerun on a fixture with 10 `ts` showcases and reports it at the checkpoint; above 2 s, _`O28`_ (PLAN-P4.3-serve.md) is taken up, in a segment of its own after _`P7`_; otherwise it stays open. Rejected: one Vite build per run with every `ts` showcase as an input (one failure can mask others, and shared chunks need splitting per showcase frame); taking up _`O28`_ before measuring.
- _`D256`_ (`live`; Q10; replaces _`D206`_ (PLAN-P4.3-serve.md); resolves _`O35`_ (PLAN-P7-ts-react.md)): **`serve` watches the ignored files showcases depend on** (option chosen: "B + custom modules (Rec.)"): the reads of every showcase built in the latest run, by any showcase adapter and failed builds included, and the custom showcase adapter modules listed in `showroom.json`, are watched even under ignored folders (never under `node_modules` or `.git`, which Vite's watcher always ignores). The watcher's `ignored` function lets them, and the folders leading to them, through; reads newly under an ignored folder are added to the watcher after the run; each run's set replaces the previous one. A change to one reruns the check and every showcase build, as any watched change does (_`D184`_ (PLAN-P4.3-serve.md)). Ignored files still never become documentation or code files. A `ts` build records its reads with a Vite plugin, as modules load (so a failed build has them too): virtual files as their documentation files, and real files under the host root outside `node_modules`; `buildShowcases()` keeps failed builds' reads. Rejected: keeping _`D206`_ and documenting the limitation (the host's own package, through its `dist/`, is the usual way a library demos itself, _`D236`_ (SPEC-S6-showcases.md)); watching only the files reached through the host's own package (needs tracking which reads came that way); watching reads without the custom showcase adapter modules (a module built into `dist/` would never rerun).
- _`D257`_ (`live`; Q11; resolves the `ts` part of _`O19`_ (SPEC-S6-showcases.md)): **No per-host setup for `ts` showcases**, as for React (_`D231`_ (SPEC-S6-showcases.md)): a showcase imports what it needs (global styles, polyfills) itself. Where a `ts` showcase's editable parts are found is left to the playground (_`D85`_, _`D101`_ (SPEC-S6-showcases.md)), as _`O16`_ left it for React. Rejected: a host-wide setup module loaded before every `ts` showcase.
- _`D258`_ (`live`; Q13; resolves the _`P7.1.1`_ part of _`O42`_ (PLAN-P7-ts-react.md)): **Two Glossary terms**, added to `CONTRIBUTE.md` with the code that introduces them: **Console panel**: the part of a `ts` or `react` showcase frame listing what the showcase writes to the browser's console, its uncaught errors and its rejected promises; hidden while nothing has been logged. **Showcase frame root**: the empty element (`#root`) in a showcase frame's page that a `ts` showcase may write to, and that the `react` showcase adapter renders the showcase into; above the console panel. Rejected: "page container" (doesn't say which page: the showcase frame's, the showroom's, or where the showcase frame is placed); "frame root" and "showcase root" (less tied to the showcase frame); "showcase frame console" for the console panel (longer, and the showroom has no other console panel).
- _`D259`_ (`live`; Q12; resolves _`O44`_, and _`K15`_ (SPEC-pitfalls.md)): **No resolve plugin for the host's own package**: Vite resolves a showcase's import of the host's own package by its name through its `exports`, as Node's self-reference does, so _`D236`_ (SPEC-S6-showcases.md) holds as written; a test in _`P7.1.1`_'s fixtures covers it.
  - Evidence: Spike 2026-11-13 (option chosen: "Spike now (Rec.)"): Vite 8.3.7, a fake host with `exports` for `.` and `./extra`, installed in no `node_modules`, built with _`D244`_'s inline configuration from a virtual module in its `docs/` folder. The package's name and its `./extra` subpath resolve, from the virtual module and from a real file it imports, with and without `resolve.preserveSymlinks`, and the chunk's `moduleIds` list every file read; a subpath `exports` doesn't list fails the build.
- _`D260`_ (`live`; Q14): **The build mode is in the request**: `ShowcaseBuildRequest` gains `mode`, `'development'` or `'production'` (_`D254`_); `buildShowcases()` takes it as an option, which `serve` sets to `'development'`. Additive to the experimental interface (_`D133`_ (SPEC-S6-showcases.md)); `README.md` › `# Usage` and `AGENTS.md` › Exports are updated. Rejected: giving the mode only to the built-in showcase adapters when the registry creates them (custom showcase adapters couldn't tell `serve` from `build`).

- _`D261`_ (`live`; refines _`D254`_; from review 2026-11-13 #1): **The mode is pinned in the configuration, never through `process.env.NODE_ENV`**: Vite sets `process.env.NODE_ENV` once per process and then prefers it over `mode` (and Vitest sets it to `test`), so each build's inline configuration sets, from the request's mode, `define` (`process.env.NODE_ENV`, `import.meta.env.DEV`, `import.meta.env.PROD`, `import.meta.env.MODE`), `resolve.conditions` (`development` or `production`), `build.minify` and `build.sourcemap` (`'inline'` in development); `showroom` never reads or sets `process.env.NODE_ENV`. Both modes are tested under `NODE_ENV=test`; `AGENTS.md` gets a gotcha.
- _`D262`_ (`live`; refines _`D244`_ (PLAN-P7-ts-react.md) for `ts`; from review 2026-11-13 #2): **`base: './'` and `root` (the host repository's root) are pinned too**, so asset URLs, the preload helper and dynamic chunks' CSS stay relative to the showcase frame's folder (`showcases/<…>/`, and GitHub Pages sub-paths), and nothing depends on the working directory. The `showcase-ts` fixture gets an asset and a dynamic import with CSS, served in the `serve` tier and built in `e2e`.
- _`D263`_ (`live`; refines step 6; from review 2026-11-13 #3): **How build errors are mapped**: a thrown error's `errors[]` is walked when present (rolldown's `BundleError`, oxc's "Transform failed with N errors"), else the error itself; ANSI codes are stripped and absolute paths in messages made root-relative (virtual files by their virtual path); the module id (without `\0` and queries) gives the path: a virtual file's virtual path, or a real file's root-relative path; the line comes from `loc`, else from `pos` in that module's source; an unresolved import (Vite's location-less `Error`) is caught by the resolve plugin, which knows the importer and finds the import's line in its source, and gets a message of `showroom`'s own (`Can't resolve "<specifier>"`). Each error shape gets a unit test.
- _`D264`_ (`live`; refines _`D256`_; from review 2026-11-13 #5, #8): **Where the watched files are kept**: `BuildShowcasesResult` gains `watched`, the root-relative paths of every showcase's reads (successful and failed builds) and of the custom showcase adapter modules listed in `showroom.json`; `serve`'s state carries it, and the host watcher takes a `watch(paths)` option, which `serve` wires to Vite's watcher. A failed check, or a run that throws, keeps the previous set. "Outside `node_modules`" is judged on the root-relative path (fixture copies live under `node_modules/.cache/`).
- _`D265`_ (`live`; refines _`D256`_; from review 2026-11-13 #7): **Watching details**: for each watched path under an ignored folder, the topmost ignored folder holding it is added to the watcher (so `rm -rf dist && tsc` is seen), and the `ignored` function lets through only the watched paths and the folders leading to them; paths dropping out of the set are unwatched (`unwatch()`) after the run. No automated test edits watched files (_`D190`_ (PLAN-P4.3-serve.md)), so the checkpoint asks the user to check by hand: `tsc --watch` alongside `serve` on a host importing itself by name, then a clean rebuild of its `dist/`.
- _`D266`_ (`live`; refines _`D252`_; from review 2026-11-13 #9): **Two more resolution cases, as on disk**: a `.js` specifier naming a `.ts` virtual file (TypeScript's convention, which Vite follows for real files), and a folder import reaching a virtual `index.ts` (or another extension); both tested.
- _`D267`_ (`live`; refines _`D247`_; from review 2026-11-13 #10): **Inline ` ```mts ` and ` ```mjs ` entry points are accepted too**, consistent with linked `.mts` and `.mjs` files.
- _`D268`_ (`live`; refines _`D249`_, _`D250`_; from review 2026-11-13 #4; option chosen: "Both"): **The console panel and the frame script's growth guard**: the console panel has a maximum height (about 12 lines) and scrolls inside it, following the newest line; and the frame script doesn't count the console panel's own growth towards `MAX_REPEATED_GROWTHS` (`src/frame/`): the console script tells it about each growth of the panel (e.g. a window event whose name reaches the frame script through its constants argument, as it must stay self-contained), and a growth matching it is not a repeated growth. Both tested. Rejected: only the maximum height; only adjusting the guard.
- _`D269`_ (`live`; refines _`D252`_; from review 2026-11-13 #6; option chosen: "Document, not support (Rec.)"): **A virtual CSS file is imported from TypeScript or JavaScript, not by a CSS `@import`**: Vite resolves CSS `@import` without the build's plugins, so `README.md` says so; real CSS files `@import` as usual. A fixture case imports a virtual CSS file from a module. Rejected: a `resolve.alias` entry per virtual CSS file (more to build and test).
- _`D270`_ (`live`; from review 2026-11-13 #11; option chosen: "Add it now"): **Build warnings reach the host**: `ShowcaseBuildResult` gains an optional `warnings` (`ShowcaseBuildError`s: a message, and optionally a path and line), on either outcome; `checkBuildResult()` validates it, and `buildShowcases()` reports each as a warning issue at its place (as `getBuildErrorIssue()` places errors), which `check --showcases` and `build` print and `serve` shows in its issues bar, without failing anything. The `ts` showcase adapter collects Vite's warnings through its logger (`logLevel` stays `'silent'` for the console), maps them as _`D263`_ maps errors, and leaves out the codes `build` already silences for dependencies (`SILENCED_WARNINGS`, `src/cli/build/`, e.g. `MODULE_LEVEL_DIRECTIVE`). Additive to the experimental interface (_`D133`_ (SPEC-S6-showcases.md)), documented in `README.md` › `# Usage`. Rejected: an open point, decided with _`P7.1.2`_'s interface change (_`O33`_ (PLAN-P7-ts-react.md)).
