# _`S12`_ Showcase views

approved 2026-11-15, after its zero-context review (option chosen: "Approve and commit (Rec.)")

How a showcase is presented, chosen by its author instead of detected: one or more **showcase views** (the Markdown behind it, its source, its showcase frame, its console), stacked in a block; the console and the errors moved out of the showcase frame into the showroom; status marks saying what was verified. From the user's proposal of 2026-11-15, motivated by `../tsstd` and `../tsschema` (and later `../dotnetschema`), whose showcases exist to be type checked in CI and render nothing (the user: "there are a number of showcases whose main purposes it for them to be tested during CI, but since they are documenting TS utility types, not TS/JS code, they don't really output anything"); critiqued and iterated on in the conversation, then settled (the user: "I am very happy with the concept as we have described it"). The discussion's record is `./.workflow/.temp/showcase-views/NOTES.md`.

## Decisions

### Views

- _`D495`_ (`live`, changed by _`D519`_, refined by _`D520`_, _`D523`_, refined by _`D526`_; refines _`D365`_ (SPEC-S10-presentation.md); the user's proposal: "let's add a parameter to all Showcase adapters which would allow the showcase author to specify how it should be presented"; the agent's critique #1, to make it a marker key handled by `showroom` rather than a showcase adapter option, "Fully agreed"): **The `view=` key** on a showcase's marker names its **showcase views**: one, or a comma-separated list (`view=source,console`), shown one below the other in the order given. The views are `markdown` (_`D496`_), `source` (_`D497`_), `demo` (_`D498`_) and `console` (_`D499`_). Like every key and value of the marker, they are case-sensitive (the user: "Marker keys and values are case sensitive"). A repeated view, an empty list (`view=`, `view=a,,b`, a trailing comma) and an unknown view are `check` errors (the user: "These are all syntax errors in how the `showcase` is invoked and need to report the error"), as is `view=` on a showcase resource (`file=`). `Showcase` gains the views it is shown with, after the defaults (_`D501`_), so a custom showcase adapter can see them.
- _`D496`_ (`live`; the user's proposal: "`markdown`: Markdown behind the showcase, either a link or a codeblock. If possible, it should still syntax-highlight the code within the code-block, treating the internals of the code-block as the code-block hinted language, not as markdown"): **The `markdown` view** shows the showcase as written in its documentation file: a code block showcase's fence, its inside highlighted as the fence's language and its two fence lines as Markdown; a linked showcase's paragraph, highlighted as Markdown. It is a code block (_`D366`_ (SPEC-S10-presentation.md)): line numbers, the copy button.
- _`D497`_ (`live`, refined by _`D540`_; the user's proposal: "`source`: Showcase code, syntax-highlighted"; the agent's critique #7, "Agreed!"): **The `source` view** shows the entry point's code, highlighted as a code block (_`D366`_ (SPEC-S10-presentation.md)), with the error lines marked (_`D506`_). A linked entry point that isn't text, or is over the code sidebar's limit, says so, with a link opening it, as its tab does (_`D378`_ (SPEC-S10-presentation.md)). It is how a showcase reads as an ordinary code block while still being built and checked in CI (the user: "displayed as if it were an ordinary code-block").
- _`D498`_ (`live`, refined by _`D529`_, _`D531`_; the user's proposal: "`demo`: Displays the showcase generated/compiled DOM (Console keeps working as it does now, displaying and fading with a button in the corner to open)"; the user's caveat: "no console is shown as part of `demo` if `console` is also included as a separate view"): **The `demo` view** is the showcase frame, as today (sized to its content, never reloading when the block changes, _`D376`_ (SPEC-S10-presentation.md)), with the console over it as today's hidden console panel (fading lines, the counter opening it, _`D505`_), unless `console` is also one of its views, in which case the `demo` view shows no console at all.
- _`D499`_ (`live`, refined by _`D523`_, refined by _`D529`_, _`D530`_; the user's proposal: "`console`: Displays the console alone, full-sized, with no way to toggle it off or view the showcase"; the user: "Keep at 8 lines, we can review and update easily later", "It can show a grayed out, placeholder 'no output'", "It clears when `serve` reloads"): **The `console` view** is the console panel (_`D505`_) on its own, always shown, with no toggle: 8 lines high, scrolling beyond them; a greyed "no output" placeholder while nothing is logged; cleared whenever `serve` reloads its showcase frame.
- _`D500`_ (`live`; the agent's critique #7 and the follow-up B, "Agreed"; the user: "There are multiple ways of making an iframe 'invisible'. If it turns out making it `display: none` has unwanted consequences, we can look for `opacity: 0`, or `width/height: 1px`, or similar"): **The showcase frame is loaded only when a view needs its page running**: `demo` or `console`. With `markdown` or `source` alone, the showcase is still built and checked (`check --showcases`, `build`, `serve`), but its page is never loaded in the showroom. With `console` and no `demo`, the page runs hidden, but laid out, so it behaves as when shown (e.g. `opacity: 0`, `pointer-events: none`, `aria-hidden`, at its real width, in a container with no height), rather than with `display: none`; the way is planning's, after _`K21`_ (SPEC-pitfalls.md).

### Defaults

- _`D501`_ (`live`, refined by _`D523`_; the agent's critique #2, the user: "Love it, especially the layered approach!"; the follow-up C, "Agreed"): **A showcase shown as a block has default views, in layers**: its showcase adapter's own default, overridden for that showcase adapter by `showroom.json` (_`D502`_), overridden by the marker's `view=`. The built-in showcase adapters' defaults are `demo` for `html`, `react` and `angular`, and `source,console` for `ts` (plain TypeScript is more often logic than UI: `../tsschema`'s showcases then need no key, and `../tsstd`'s one `showroom.json` default). A future C# showcase adapter's default would be `source`. A custom showcase adapter declares its default in its interface (_`D508`_). A showcase shown inline has no default views (_`D514`_).
- _`D502`_ (`live`, refined by _`D523`_, refined by _`D534`_; refines _`D501`_): **`showroom.json`'s `showcaseViews`** sets the default views per showcase adapter: an object from a showcase adapter's name (a built-in one, or one of `customShowcaseAdapters`) to a view or a list of views, validated as `view=` is (_`D495`_), e.g. `"showcaseViews": { "ts": ["source"] }`. A name no showcase adapter has is an error.
- _`D503`_ (`live`; the agent's critique #3, option (a), the user: "Agree with (a)"): **No more detecting what a showcase renders**: whether its console is shown on its own or hidden behind fading lines is no longer decided at run time from the showcase frame root's content; the views say it. A `demo` view whose showcase renders nothing is an empty showcase frame, by its author's choice.

### The console, out of the showcase frame

- _`D504`_ (`live`; refines _`D77`_ (SPEC-S6-showcases.md); the agent's critique #4, option (a), the user: "I think (a) is a better separation of showcase compiled demo (iframe) and showcase presentation (host page) and is more flexible for possible future updated"; #5, the user: "If we do a global `window.console` override inside all iframes, we get console to work regardless of the adapter"; the follow-up A, "Agreed on all points"): **The frame script captures the console**, in every showcase adapter's page (an `html` showcase's `<script>` too): every `console.log`, `info`, `warn`, `error` and `debug` call, uncaught errors and rejected promises. It formats the values as text inside the showcase frame, as the console panel does today (strings as they are, errors as their stack, objects and arrays as indented JSON), since many values can't be posted, and posts the lines to the showroom; every call still reaches the browser's console. It is in place before any of the page's own scripts run (_`K22`_ (SPEC-pitfalls.md)).
- _`D505`_ (`live`, refined by _`D530`_, _`D531`_; changes _`D233`_ (SPEC-S6-showcases.md); the agent's follow-up A, "Agreed on all points"): **The showroom renders the console panel**, never the showcase frame: as the `console` view (_`D499`_), or over the `demo` view's showcase frame (_`D498`_), where it behaves as today's hidden console panel (each new line showing briefly, then fading; the counter, red with the number of unseen errors, opening the whole console panel over the showcase; the first uncaught error or rejected promise opening it once). It keeps the newest 128 lines, its first line saying how many earlier ones were dropped, and follows the showroom's theme. The `ts` showcase adapter's console script, and the console panel's place in the showcase frame's page (and its layout workarounds), go away: the page holds the showcase alone.

### Errors and status marks

- _`D506`_ (`live`, refined by _`D523`_, changed by _`D527`_, refined by _`D528`_, _`D539`_; the agent's follow-up D, the user: "Agreed on all counts"; the user: "I like taking the errors out of the iframe. Same reasons as console, only even stronger here AND easier to implement!"): **The showroom shows a showcase's errors**, never its showcase frame: whenever a showcase has errors (in `serve`, as `build` fails on them), an **error list** under the block's header bar (_`D509`_), each error with its check (_`D508`_), its `path:line` and its message, collapsed or expanded by its ✗ status mark (_`D507`_); and markers on the error lines, in the `source` view and in each code pane tab showing the file. An error in a file that isn't a tab (e.g. a host file the showcase imports) is only in the list. `serve`'s error frame (_`D186`_ (PLAN-P4.3-serve.md)) goes away.
- _`D507`_ (`live`, refined by _`D523`_, refined by _`D527`_–_`D530`_; the agent's follow-up D, the user: "I like all showcases (when applicable) showing 'type check ✓', I would also preface it with 'build ✓' when ever a showcase was successfuly compiled ... maybe we even add a `runtime ✓` when/until there are no errors or warnings"; "I would only show status marks that make sense for an adapter"; "I forgot that C# would build, you're right it would show `build ✓`"): **Status marks** on the left of the block's header bar say what was verified, only those that mean something for the showcase adapter:
  - `build`: the showcase was compiled (✓), or failed to (✗);
  - one mark per check the showcase adapter performed (_`D508`_), e.g. `type check`, where it ran (not with `typeCheck: false`);
  - `runtime`, only while its page runs (a `demo` or `console` view): ✓ until something goes wrong, then ⚠ with the number of warnings, or ✗ with the number of errors.

  In a published showroom, `build` and the checks are always ✓ (`showroom build` fails otherwise): they tell readers the code is verified. Only `serve` shows them ✗.

- _`D508`_ (`live`, refined by _`D527`_, _`D537`_; changes the experimental showcase adapter interface, _`D365`_ (SPEC-S10-presentation.md); the agent's follow-up D, the user: "I like/approve your proposal with errors containing the check they belong to"; "If only typecheck fails, I absolutely still want to show not only the status mark, but the actual errors. Along side the errors, we can show the showcase since it did build"): **Showcase adapters report their checks**: a showcase adapter's build result lists the checks it performed (e.g. `checks: ['type check']`), and each error names the check it belongs to (`check: 'type check'`), or none, for a build error. `build` is derived by `showroom`: ✗ when an error names no check. A check's mark is ✗ when an error names it, ✓ otherwise. A build result may hold the showcase frame's files and errors together: errors that all name a check leave the files usable, so `serve` runs a showcase whose type check failed, with its errors shown beside it; an error naming no check means there are no files. `showroom build` and `check --showcases` still fail on any error. A showcase adapter also declares its default views (_`D501`_).

At half, the code pane is beside the whole stack of views (or below it, where the block is narrow, _`D355`_ (SPEC-S10-presentation.md)); the code sidebar state is as today.

### Named virtual files

Settled 2026-11-15 from the user's follow-up on choice 1 of the draft's choices (`./.workflow/.temp/questions-s12/QUESTIONS.md`): "Is there any real downside in allowing any showcase, regardless of the view type(s), being declared as a (virtual) file, and thus allowing including this into another showcase?", and "Maybe we need to have an explicit `view=none` mode".

- _`D517`_ (`live`, refined by _`D533`_; changes _`D89`_, _`D91`_ (SPEC-S6-showcases.md), _`D359`_ (SPEC-S10-presentation.md); refines _`D92`_ (SPEC-S6-showcases.md); the agent's assessment, the user: "I am fine with the 'Things to be aware of'", "Agreed" (gaps 2, 6)): **`file=<name>` names a code block's virtual file, with or without a showcase adapter**:
  - with an adapter (e.g. ` ```ts showcase=ts file=units.ts `), it is a code block showcase whose virtual file is named `<name>` instead of the generated `<documentation file's name>.showcase-<n>.<extension>`, so other showcases can import or include it by a name that doesn't change when a showcase is added above it; it goes with every other key a code block showcase takes;
  - without one (`showcase file=<name>`), it is a virtual file and nothing more, never built: a naked marker with `file=` doesn't mean `html` (_`D92`_'s one exception), and `showcase=html file=page.html` is a named `html` showcase;
  - `file=` stays a `check` error on a linked showcase, whose entry point is a real file already.

  Its consequences are the author's (the agent's "things to be aware of", accepted): a showcase imported as a library runs its top-level code in its own showcase frame and in every importer's, its console lines in each; an `html` showcase used as an Angular template shows its template syntax as text in its `demo` view.

- _`D518`_ (`live`, refined by _`D532`_; refines _`D517`_; the user: "Let's limit allowed extensions based on selected showcase adapter"; the user, first: "I don't want to police every possible file extension"): **A named showcase's name has an extension its showcase adapter accepts as an entry point**, validated as a linked showcase's file is (e.g. `showcase=ts file=lib.txt` is a `check` error), as the adapter builds and type checks it by that name. A virtual file with no adapter may have any name, and is treated by that name wherever it is used (e.g. a `.txt` is highlighted as text, and never type checked). Rejected: no check for showcases (a `ts` showcase named `.txt` could pass CI without being type checked).
- _`D519`_ (`live`, refined by _`D534`_; changes _`D495`_ (its `view=` on a showcase resource being an error); refines _`D390`_ (SPEC-S10-presentation.md); the agent's gap 4, the user: "If we're defining a resource as not having an adapter set (or implied) and only having a `file=`, then I agree"): **A virtual file with no adapter takes `view=` as its only other key**, with the views that need nothing built: `source`, the default (an ordinary code block, as today, _`D390`_), `markdown` (its fence as written, marker included), and `none` (_`D520`_). `demo`, `console` and `include=` on it are `check` errors.
- _`D520`_ (`live`, refined by _`D534`_; refines _`D495`_; the agent's gap 5, "Agreed"; the user: "it is for cases where that file resource will be shown/included elsewhere. In GitHub it won't be hidden there and won't be included elsewhere. This can be misused, but so can most things"): **`view=none` shows nothing in the showroom**: the code block takes no place there (on GitHub and npm the fence still shows). A showcase with `view=none` is still built and checked; a virtual file with no adapter can still be imported or included. `none` combined with any other view is a `check` error.
- _`D521`_ (`live`; changes _`D169`_ (PLAN-P4.4-html-resources.md); the agent's gap 3, "Agreed"): **An `html` showcase frame holds every virtual file of its documentation file's folder named by `file=`**, named showcases included, instead of only what were resources; the rules against a file landing on the page (`index.html`) cover them too.
- _`D522`_ (`live`; option chosen: "Retire it (Rec.)"; the user: "why the distinction between virtual files used as showcase resources and actual files used as showcase resources?"): **The Glossary term "Showcase resource" is retired**: whether a file is real or virtual only says where it is kept; whether it is a showcase says whether it has a showcase adapter. **Virtual file** becomes the content of a code block with a showcase marker, available to showcases as a file in its documentation file's folder, named by `file=`, or generated for a code block showcase without one; **Code block showcase** adds that `file=` names its virtual file; **Showcase marker** marks a showcase's entry point, or names a virtual file. With it, every identifier, comment, message and document using "resource" for these follows, the exported `VirtualFileKind` (`'resource' | 'entry'`) included (its replacement is planning's, _`O86`_), and `README.md`'s wording.

## _`S12.1`_ Showcases shown inline, in the sidebar
