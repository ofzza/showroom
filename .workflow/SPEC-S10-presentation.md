## Decisions

### The code pane

- _`D352`_ (`live`, refined by _`D413`_ (PLAN-P10.4-code-pane.md); the user's proposal 2026-11-13, #1; changes _`D101`_ (SPEC-S6-showcases.md), see _`D372`_): **A code block showcase, and a linked showcase shown as a block (_`D357`_), is shown beside its code**: the code pane (its entry point's code, highlighted, with its included files, _`D362`_) and the showcase frame side by side, and stacked when there isn't room, in place of the fence or the paragraph (_`D373`_). A linked showcase shown inline has no code pane (_`D358`_). The code pane has three states, toggled by a control that stays visible in every state: hidden (the showcase alone), half (the code pane and the showcase frame 50:50), and full (the code pane over the showcase frame, covering it). All three always apply, whatever the number of tabs, and for every showcase adapter. Rejected: the code shown after the showcase, as today for code block showcases (the user: "I would like to unify the 2 and integrate them with the actual rendered showcase better").
- _`D353`_ (replaced by _`D414`_ (PLAN-P10.4-code-pane.md); refines _`D352`_; the user: "Default state is 50:50 view and there is no need to persist state between navigation events or reloads"): **The code pane starts at half**, every time a page is shown; its state isn't kept across navigation or reloads. Rejected: starting hidden; remembering the state.
- _`D354`_ (`live`, refined by _`D405`_, changed by _`D416`_ (PLAN-P10.4-code-pane.md); refines _`D352`_; the user: "the showcase syntax display has its own minimal height regardless of how short the showcase render might be"; the review's Q5, "Yes, apply (Rec.)"): **The code pane's height**, with a minimum and a maximum number of lines set in planning (_`O63`_): side by side at half, the larger of the showcase frame and the minimum; stacked at half, below the showcase frame, from the minimum up to the maximum; at full, the larger of the showcase frame and the code, up to the maximum. Beyond its height the code pane scrolls. A short showcase sits in a block at least that tall; the showcase frame itself keeps its own height (_`D376`_).
- _`D355`_ (`live`; refines _`D352`_; the agent's re-evaluation, "As proposed (Rec.)"): **Stacked, when the documentation column is narrow** (not only on phones): hidden is the showcase alone, half is the code pane below the showcase frame at full width, full is the code pane over the showcase frame. The switch follows the column's width (a container query where possible, see _`K17`_), never script reading the width (`AGENTS.md` › the narrow layout is switched by CSS alone).
- _`D356`_ (`live`, refined by _`D408`_, _`D412`_, changed by _`D407`_, _`D421`_ (PLAN-P10.4-code-pane.md); refines _`D352`_; the agent's re-evaluation, "As proposed (Rec.)"): **Tabs**: the code pane shows a tab per file: the entry point first, then the included files (_`D362`_) in their order. A code block showcase's entry point is labelled by its language (e.g. "HTML"), never its virtual file's name; every other tab by its path relative to the documentation file. The tabs and the state control are FluentUI's (`TabList`, toggle buttons), usable by keyboard and screen readers.

### Link showcases: inline or block

- _`D357`_ (`live`; the user: "Maybe instead of making the code-block showcase be able to load outside resources as its main content, we should look to make the link showcase be able to declare that it wants to be rendered as a block"): **A linked showcase can be a block**: the marker key `block` (e.g. `[A clock](./clock.html 'showcase block')`) replaces the paragraph holding the link with the code pane and the showcase frame, as a code block showcase is shown; on GitHub and npm it stays a link to the file. Rejected: code block showcases loading their code from a file (` ```html showcase ./clock.html `), which GitHub and npm show as an empty code block, with no code and no link (the user: "I don't consider the loss of the functionality you identified as acceptable").
- _`D358`_ (`live`; refines _`D357`_; the user: "let's also support explicit ... 'showcase inline'. The default is still implicit inline"): **The key `inline` says the default**: a linked showcase without `block` is shown as today, its showcase frame before the paragraph holding it, the link opening the modal (_`D329`_ (SPEC.md)). `inline` and `block` together are a `check` error.
- _`D359`_ (`live`; refines _`D357`_, _`D358`_): **`inline` and `block` are for linked showcases only**: a code block showcase is always a block, so either key on a fence is a `check` error, as `file=` is on an entry point.
- _`D360`_ (`live`; refines _`D357`_; the agent's re-evaluation, "As proposed (Rec.)"; completed after the review): **A linked showcase shown as a block must be alone in its paragraph**, apart from whitespace; that paragraph may sit in a list item or a blockquote. A `block` link sharing its paragraph with anything else, or whose parent isn't a paragraph (e.g. a heading or a table cell), is a `check` error; `anchor=` (reserved) with `block` is an error too, for now. Rejected: making every linked showcase alone in its paragraph a block, without a key (implicit, and it would change how existing documentation renders).

### Included files

- _`D361`_ (`live`; the user's proposal 2026-11-13, #3: "I don't want to try and detect which files go into rendering/composing the showcase, but I do want to provide a way of being told which files to show"; the key named by the user: "How about include instead?"): **`include=<path>,<path>`** on a showcase's marker (a fence's or a link's) lists files shown with it, e.g. ` ```html showcase include=./figures.css,theme.css ` or `'showcase block include=./clock.css'`. Paths are relative to the documentation file's folder, comma-separated, without spaces or commas in them (details in _`D380`_); a virtual file is named the same way, as if on disk, whichever documentation file holds it (_`D375`_). `check` reports an included file that doesn't exist, is a folder or is outside the host repository, the entry point including itself, and a file listed twice. On a resource's marker (`showcase file=…`), `include=` is a `check` error. Rejected: `with=` (the user's choice of name).
- _`D362`_ (`live`, refined by _`D408`_ (PLAN-P10.4-code-pane.md); refines _`D361`_; changes _`D329`_ (SPEC.md); the user: "Yes it does add tabs in the modal, 'cos why not"): **Included files are tabs**: in the code pane, after the entry point (_`D356`_), and in the modal of a linked showcase shown inline, whose tabs each show their path (a virtual file's name) as their title, and a link opening the file directly for real files only.
- _`D363`_ (`live`; refines _`D361`_; the user: "All referenced files are made available to the build. Virtual files act the same way real files do", and "Include never prevents a copied file from being used ... it just adds additional files that wouldn't otherwise be copied and specifies which files (apart from the entry point file) are shown as syntax tabs"): **`include=` only adds, never restricts**: every included file is available to the showcase's build. The `html` showcase adapter still copies every resource of the documentation file's folder, as today, and also copies the included files (_`D374`_); `ts` and `react` already import anything, so there it only adds tabs. Included files are always among the files `serve` watches (`buildShowcases()`'s `watched`), and the `html` build lists them in its reads, imported or not. Tabs show only what is included, never what a showcase also uses or imports, which `README.md` says.
- _`D364`_ (replaced by _`D374`_; it refined _`D363`_; the user: "Agreed"): **An `html` showcase can't include a file outside its documentation file's folder** (a `..` path): a `check` error.
- _`D365`_ (`live`; refines _`D361`_; completed after the review): **Showcase adapters and the showroom see the new markers**: `Showcase` gains its included files (e.g. `include?: string[]`, as paths relative to the root) and how a linked showcase is shown (inline or block), so a custom showcase adapter can use them, and the shown host information carries what the code pane needs (its fields are planning's, _`O62`_). `Showcase` is a host information type, exported and in `check --json`, so this changes them: breaking changes need no mitigation for now (_`D381`_); `README.md` › Usage and `AGENTS.md` › Exports document them.

- _`D368`_ (`live`; the user's proposal 2026-11-13, #2: "A slight styling change to how the link showcases are rendered"; the review's Q8, the user: "I might prefer a \"code\"/\"syntax\" icon to a \"file\" icon. Otherwise agreed"): **Links to linked files are marked with a "code" icon** after the link, so they read differently from links to pages: every link to a linked file, including a linked showcase's shown inline; never an image.

### The console

- _`D369`_ (`live`, refined by _`D377`_, _`D424`_–_`D429`_, _`D431`_ (PLAN-P10.5-console.md); the user's proposal 2026-11-13, #4, with the agent's cautions agreed: "I agree with the cautions and your proposals on how to address them"): **The console no longer grows the showcase frame** (the `ts` and `react` showcase adapters' console panel; changes _`D233`_ (SPEC-S6-showcases.md) and _`D249`_ (PLAN-P7.1-ts.md); edge cases in _`D377`_):
  - a showcase that renders nothing (its showcase frame root empty) shows its console at a fixed height of several lines, scrolling beyond them;
  - a showcase that renders something hides its console: each new line shows briefly at the bottom of the showcase frame, translucent and ignoring the pointer, then fades; a counter in a corner shows how many lines were logged, and opens the whole console over the showcase from the bottom, at the same fixed height, scrolling;
  - errors (and uncaught errors and rejected promises) stay noticeable: e.g. the counter turns red, or their line doesn't fade;
  - which of the two is decided at run time: the console starts on its own, and switches for good once the showcase frame root gets content (never back, to avoid flicker);
  - opening the console over a short showcase grows its showcase frame once to fit the console, and shrinks it back on closing.

  Its details are planning's (_`O60`_).

## The syntax, as settled

| Syntax                                                                        | What it produces                                                                                    |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| ` ```html showcase ` + body                                                   | An `html` showcase: code pane (its body) beside the frame; its folder's resources copied next to it |
| ` ```ts showcase=ts({ typeCheck: false }) ` + body                            | A `ts` showcase with options: code pane beside the frame, the console in its new modes              |
| ` ```tsx showcase=react ` + body                                              | A `react` showcase: code pane beside the rendered component                                         |
| ` ```html showcase include=./figures.css,theme.css ` + body                   | The same `html` showcase, with two extra tabs; the real `figures.css` is copied too                 |
| ` ```ts showcase=ts include=./src/units.ts ` + body                           | A `ts` showcase with `units.ts` as an extra tab; it imports whatever it imports, listed or not      |
| ` ```css showcase file=theme.css ` + body                                     | A virtual file `theme.css`: a highlighted code block, usable by showcases as if on disk             |
| `[Clock](./clock.html 'showcase')` within text                                | Inline (the default): the showcase frame before the paragraph, and the link opens the modal         |
| `[Clock](./clock.html 'showcase inline')` within text                         | The same, said explicitly                                                                           |
| `[Clock](./clock.html 'showcase inline include=./clock.css')` within text     | Inline, with `clock.css` copied next to the page, and as a second tab in the modal                  |
| `[Clock](./clock.html 'showcase block')` alone in a paragraph                 | Replaced by the code pane (the file) beside the showcase frame; GitHub shows the link               |
| `[Clock](./clock.html 'showcase block include=./clock.css')` alone            | The same, with `clock.css` as a second tab, copied next to the page                                 |
| `[Counter](./Counter.tsx 'showcase=react block include=./Counter.css')` alone | A `react` block from a real file, with its CSS as a second tab                                      |
| `[clock.css](./clock.css)`                                                    | A linked file: a link with a "code" icon, opening the modal                                         |
| ` ```ts ` + body (no marker)                                                  | An ordinary code block, highlighted, always with line numbers                                       |
