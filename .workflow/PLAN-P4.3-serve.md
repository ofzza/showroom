# _`P4.3`_ Showcases in `serve`

approved 2026-11-12; reviewed 2026-11-12 (zero-context review, 2 agents); implemented 2026-11-12

Child of _`P4`_ (PLAN-P4-showcases.md). Planned after _`P4.4`_ (_`D177`_, PLAN.md). Its choices were settled 2026-11-12 (Q1–Q10 of the planning discussion, all as recommended; each decision names its question).

## Goals

- `serve` shows the showcases, like `build` (_`D82`_, SPEC-S6-showcases.md): every showcase frame served, and placed in the showroom as `build` places it (_`D142`_, PLAN-P4.2-showcase-frames.md).
- A change to a showcase's code updates its showcase frame only; documentation changes keep today's full reload (_`K13`_, SPEC-pitfalls.md, as far as the `html` and custom showcase adapters go). An inline showcase's code, and a resource, are part of their documentation file, which the showroom shows too, so editing them fully reloads (_`D196`_): the showcase frame alone updates for a linked showcase and the other files a build reads.
- The current issues (the check's, and the showcases' build errors) shown in the showroom, not only on stderr (_`D198`_).
- A showcase that doesn't build shows its build errors in its showcase frame, and `serve` keeps running (_`D102`_, SPEC-S6-showcases.md).
- The open points _`O22`_ (a changed custom showcase adapter), _`O24`_ (cached showcase frames) (PLAN-P4-showcases.md) and _`O25`_ (an `html` showcase frame's resources) (PLAN-P4.4-html-resources.md).

Not in _`P4.3`_: the `ts`, `react` and `angular` showcase adapters, whose showcase frames may need serving differently (_`K13`_ stays open for them); rebuilding only the showcases a change affects (_`O28`_).

## Decisions

### Serving showcase frames

- _`D181`_ (`live`, refined by _`D193`_; Q1): **`serve` hands out the showcase frames from memory**, through the showcase frames plugin (`src/vite/`): a middleware added in its `configureServer`, ahead of Vite's own, answers every request under `showcases/` from the latest showcase frames, at the same paths `build` writes them to (_`D141`_, PLAN-P4.2-showcase-frames.md), with the content type from the file's extension and `Cache-Control: no-store`; a path that matches no file is a 404. Same origin as the showroom; no folder written, no second server or port. An `html` showcase frame's resources are files of its showcase frame, so they are served with its page and updated with it (resolves _`O25`_). Rejected: writing the showcase frames to a temporary folder served statically; a dev server of their own, on another port.
- _`D182`_ (`live`, refined by _`D197`_, _`D199`_; Q6): **`serve` builds the showcases before it starts listening**, after the first check, so the first page already shows them. A showcase that doesn't build doesn't stop `serve` (_`D185`_); a failed first check still does, as today. Rejected: listening first, and showing a placeholder until the showcases are built.
- _`D183`_ (`live`; replaces _`D144`_, changes _`D159`_ (PLAN-P4.2-showcase-frames.md)): **The shown host information of `serve` has its showcases**, from the showcase frames (`getShownHostInformation(host, frames)`), as `build`'s has.

### Updating after a change

- _`D184`_ (`live`, refined by _`D194`_, _`D199`_; Q2): **After a change, every showcase is built again**: the host watcher reruns the check and, when it passes, `buildShowcases()` for all showcases, as one run (_`D149`_, PLAN-P4.2-showcase-frames.md); a failed check keeps the last showcase frames, as it keeps the last shown host information today. Rebuilding only the showcases a change affects is _`O28`_. Rejected: tracking each showcase's inputs (its documentation file's folder, its `reads`, its showcase adapter's module) now.
- _`D185`_ (`live`, refined by _`D195`_, _`D196`_; Q3; changes _`D51`_ (PLAN.md)): **Only changed showcase frames reload.** When the shown host information changed apart from its showcase frames' URLs (a documentation file, the project information, a showcase added, removed or moved), the page fully reloads, as today. When only showcase frames changed (their URLs, _`D187`_), `serve` sends a custom HMR event, `showroom:showcases`, with the new URL of each changed showcase frame, and invalidates the virtual module; the showroom (through `import.meta.hot`, guarded, so `build` leaves it out) remounts just those iframes with their new URLs, keeping the theme. Rejected: a full page reload for every change.

### Build errors

- _`D186`_ (`live`, refined by _`D197`_, _`D198`_, _`D200`_, _`D202`_; Q5): **A showcase that doesn't build gets an error frame in `serve`**: a page `serve` generates in that showcase's showcase frame folder, listing each of its build errors (the message, and the file and line, _`D163`_, PLAN-P4.2-showcase-frames.md), HTML-escaped, with the frame script inserted, so it is sized and follows the theme like any showcase frame. The errors are also written to stderr, as the check's issues are; every other showcase is shown as usual. When it builds again, its showcase frame replaces the error frame (_`D185`_). No new Glossary term: "the showcase frame showing its build errors" (Q10). Rejected: keeping the last good showcase frame and reporting on stderr only.
- _`D187`_ (`live`, refined by _`D197`_; Q9; changes _`D137`_, _`D159`_ (PLAN-P4.2-showcase-frames.md)): **`buildShowcases()` reports build errors per showcase**: it resolves to `{ frames, errors, issues }`, `errors` mapping each showcase that didn't build to its issues, and `issues` the rest (a custom showcase adapter that doesn't load, a failing `close()`). `check --showcases` and `build` fail on any of them, as today (_`D159`_, PLAN-P4.2-showcase-frames.md, changed). Internal: no public signature changes.

### Reloading custom showcase adapters

- _`D188`_ (`live`, refined by _`D204`_; Q4; resolves _`O22`_; changes _`D149`_ (PLAN-P4.2-showcase-frames.md)): **A changed custom showcase adapter module is reloaded**: it is imported with its content's hash in the URL's query (`<file URL>?v=<hash>`), so an unchanged module is reused and a changed one loaded once, for the check and `buildShowcases()` alike. Each version loaded stays in memory until `serve` exits (one per edit, accepted for a dev server). Modules it imports are not reloaded: `README.md` says to restart `serve` after changing them. Rejected: a worker thread per run (every module fresh, but showcase adapters and their results would cross a thread boundary); not reloading at all (a restart after every edit).

### Cached showcase frames

- _`D189`_ (`live`, refined by _`D201`_; Q7; resolves _`O24`_; changes _`D140`_, _`D155`_, _`D161`_ (PLAN-P4.2-showcase-frames.md)): **A showcase frame's URL carries its content's hash**: `getShowcaseFrameUrl()` adds `?v=<hash>` (the first 8 hex digits of the SHA-256 of its files' paths and contents), in `serve` and `build` alike, so a changed showcase frame gets a new URL (what _`D185`_ compares), and a browser never shows a cached earlier page. The themed URL adds its `theme` parameter to that query. Its assets keep their names: a static host may still serve a cached asset of an earlier build (`serve` sends `no-store`, _`D181`_). Rejected: only `no-store` in `serve`, leaving `build` as it is.

### Testing and documentation

- _`D190`_ (`live`, changed by _`D192`_, _`D203`_; Q8; replaces _`D52`_ (PLAN.md), changes _`D108`_ (PLAN-P4-showcases.md)): **Tests**:
  - unit: the middleware (on a map of showcase frames: content types, `no-store`, 404s), the error frame page (escaping, the frame script), the URL hash, the host watcher's decisions (a full reload or a `showroom:showcases` event, with a fake check, a fake build and a fake reload target), the reloading of a custom showcase adapter (a scratch copy of a fixture, edited between two loads), `buildShowcases()`'s per-showcase errors, the showroom's iframe remount (server-rendered, as far as it goes without effects);
  - serve (`*.serve.test.ts`, the tier's first tests, _`D108`_ (PLAN-P4-showcases.md)): `serve()` on fixture copies, on a free port, stopped through two internal options of `ServeOptions` (an `AbortSignal`, and a callback receiving the URL once it listens), never on the command line: fetching a showcase frame and its resources, an edited code block changing the fetched showcase frame, an error frame, an edited custom showcase adapter taking effect;
  - the user checks `serve` in a browser: a showcase frame updating without a page reload, and an error frame.
- _`D191`_ (`live`, refined by _`D205`_, _`D206`_; Q10): **Documentation**: `README.md` (`# Usage`: `serve` shows showcases and updates them, error frames, restarting after changing a custom showcase adapter's imports, the `?v=` in showcase frame URLs), `AGENTS.md` (Testing: `serve` tier and what is tested without a server; gotchas: the custom showcase adapter caching gotcha rewritten for _`D188`_; Layout if a file is added), `CONTRIBUTE.md` (architecture, if the flow of `serve` is described there). No Glossary change.

### From the review (2026-11-12)

Settled after the zero-context review (2 agents): RQ1 "C: Drop edit tests", F6 with the user's addition of an issues bar ("A: Issues bar (Rec.)"), the other fixes "Apply them (Rec.)".

- _`D192`_ (`live`; RQ1; changes _`D190`_, _`D108`_ (PLAN-P4-showcases.md)): **No `serve` tests edit files.** Vite's watcher always ignores `**/node_modules/**`, `**/.git/**` and `**/test-results/**`, and fixture copies live under `node_modules/.cache/`, so it never sees their changes; updates after a change are covered by the host watcher's unit tests and the user's browser check. `AGENTS.md` gets the gotcha: a host repository under such a path isn't watched either. Rejected: an internal option driving the host watcher from the tests; copies in a gitignored scratch folder outside `node_modules` (changes _`D106`_).
- _`D193`_ (`live`; F1; refines _`D181`_): **The middleware answers only showcase frames**: it strips the query, decodes each path segment (_`D161`_), and answers a path that is a file of a showcase frame; a missing file inside a known showcase frame's folder is a 404 it answers itself; any other path goes to Vite (`next()`), as the showroom's own modules are served from `showcases/` too (`src/app/showcases/` compiled to `dist/app/showcases/`). Unit cases: `/showcases/index.js` passing through, an encoded space and `#`, a query, a missing file.
- _`D194`_ (`live`; F2; refines _`D184`_): **Stopping waits for a running run**: `HostWatcher.close()` resolves once a running check and build are done, `serve()` awaits it before closing the server and removing its folders, and nothing is sent after it. Unit test.
- _`D195`_ (`live`; F3; refines _`D185`_, _`D155`_ (PLAN-P4.2-showcase-frames.md)): **How new showcase frame URLs reach the showroom**: `mount()` returns a function updating the shown showcases; `main.ts` listens with `import.meta.hot?.on('showroom:showcases', …)` (typed through a `vite/client` types reference in `main.ts`) and passes it every showcase's URL, sent in full with each event, so a missed event leaves nothing stale; `App` keeps the showcases in state; a showcase frame's iframe sets its `src` again when its URL changes, keeping its height until the next `resize` (no remount). A pure helper applying the URLs is unit-tested.
- _`D196`_ (`live`; F4; refines _`D185`_): **Editing an inline showcase or a resource fully reloads**, by design: it changes its documentation file, whose code blocks the showroom shows too. Only linked showcases and other files a build reads update by event. The user's browser check uses a linked showcase.
- _`D197`_ (`live`; F6; refines _`D182`_, _`D186`_, _`D187`_): **Failures outside a single showcase**: `buildShowcases()`'s run-level issues (a custom showcase adapter that doesn't load, a failing `close()`) are written to stderr with the check's issues, and shown in the issues bar (_`D198`_); `serve` keeps serving; the showcases of a showcase adapter that doesn't load get error frames, so they stay in place; a `buildShowcases()` that throws, or a `showroom.json` that can't be read, keeps the last showcase frames. The first run behaves the same: `serve` starts.
- _`D198`_ (`live`; F6, the user's addition): **The issues bar**: in `serve`, the showroom shows the current issues (the check's errors and warnings, and the showcases' build errors, each with its file and line) in a FluentUI message bar at the top of the page, collapsible, gone when there are none. `serve` sends the list in a custom HMR event, `showroom:issues`, after every run, and the virtual module carries it, so a page loaded later shows it too. A failed check, which keeps the last good data, shows its errors there. Error frames stay (_`D186`_). Not in `build`, which stops on errors; the shown host information of `build` has no issues. Server-rendered unit tests of the bar; the user checks it in a browser. Rejected: Vite's own error overlay (one error, covering the page, no warnings).
- _`D199`_ (`live`; F7; refines _`D182`_, _`D184`_): **One run**: the host watcher gets a `build(host)` option (a fake in its unit tests), which reads `showroom.json` again and calls `buildShowcases()`, so `customShowcaseAdapters` changes apply without a restart; the check and the build are one run of the existing serialized `update()` loop; the showcase frames, the shown host information and the issues are swapped together after the run, then the page is reloaded or the events sent.
- _`D200`_ (`live`; F8; refines _`D186`_): **Error frames** are generated in `src/showcases/` (`getErrorFrame()`), as an `index.html` in the showcase's showcase frame folder, put in the same map as the showcase frames (so the middleware and the shown host information find them), hashed like any showcase frame (_`D189`_); `build` and `check --showcases` never generate one.
- _`D201`_ (`live`; F9; refines _`D189`_): **The hash**: SHA-256 over the showcase frame's files sorted by path, after the frame script's insertion, each path and content preceded by its byte length; its first 8 hex digits, in a query parameter `hash` (not `v`, which Vite treats as a dependency version and serves as immutable). `getShowcaseFrameUrl()` and `getShownHostInformation()` take the files; `getThemedFrameUrl()` (`src/frame/`) joins `theme` with `&` when the URL has a query. Tests expecting URLs without a hash change: `src/app/index.test.tsx`, `src/app/showcases/index.test.tsx`, `src/vite/index.test.ts`, `src/showcases/index.test.ts`, `src/cli/build/index.e2e.test.ts`.
- _`D202`_ (`live`; F10; refines _`D186`_): **Build errors on stderr** are written with the check's issues, only when the formatted list changed (the host watcher's existing check), not after every run.
- _`D203`_ (`live`; F11; changes _`D190`_): **Test placement**: `buildShowcases()`'s per-showcase errors in the `integration` tier (it makes a temporary folder), on the `showcase-build-errors` fixture; the `serve` tier gets the compiled showroom (the `app.ts` global setup, `inject('appDir')`), listens on port 0, handles an already-aborted signal, and polls with deadlines; it fetches showcase frames, their resources and an error frame, and the virtual module's issues. The iframe updating after an event, and the issues bar, are browser-check items.
- _`D204`_ (`live`; F12; refines _`D188`_): **Two loads per run**: `check()` and `buildShowcases()` hash and import a custom showcase adapter separately; an edit between the two is picked up by the next run. The JSDoc of the registry ("loads each module once per process") and of `ShowcaseAdapter` (its lifetime in `serve`) are updated.
- _`D205`_ (`live`; F13; refines _`D191`_): **More documentation**: `README.md` › `# Development` (`test:serve` has tests), the showcase note and the `serve` bullets ("doesn't show showcases yet", "reloads when … documentation file changed"), the issues bar; `AGENTS.md` › Testing (the paragraph on testing `serve` without a server rewritten) and Gotchas (_`D192`_; Vite's root and `cacheDir`, if affected); `CONTRIBUTE.md`'s architecture (its `serve` flow); the comments on `ShownShowcase.url` and `ShownHostInformation.showcases`.

### From the discussion of resources (2026-11-12)

- _`D206`_ (`live`; the user: "No"): **Ignored files stay unwatched**: a file a showcase's build reads but the ignore patterns skip (e.g. under `dist/`) isn't watched, so `serve` doesn't pick up its changes; `README.md` says that showcases should not depend on ignored files in `serve`. A changed real file that is watched rebuilds every showcase (_`D184`_), and every showcase frame whose content changed updates (_`D195`_, _`D201`_), wherever its showcase is, without a full reload. Rejected: watching every file the latest run read, even if ignored. Not recorded (the user: "Only O28"): `build`'s caching gap, where a static host may serve a cached resource next to a newer page (_`D189`_).

## Steps

1. `buildShowcases()`'s per-showcase errors and error frames (_`D187`_, _`D200`_), the URL hash (_`D189`_, _`D201`_), the themed URL's query; `check --showcases` and `build` adjusted. Unit, integration and end-to-end tests.
2. Reloading custom showcase adapters (_`D188`_, _`D204`_), in the registry. Unit tests.
3. `serve`: the middleware (_`D181`_, _`D193`_), building before listening (_`D182`_), the host watcher's runs (_`D184`_, _`D194`_, _`D197`_, _`D199`_, _`D202`_) choosing between a full reload and the `showroom:showcases` event (_`D185`_), the `showroom:issues` event and the issues in the virtual module (_`D198`_); the internal stop and listening options. Unit tests.
4. The showroom: `mount()`'s updater and `main.ts`'s listeners (_`D195`_), the iframe following its URL, the issues bar (_`D198`_). Unit tests.
5. The `serve` tier's tests (_`D192`_, _`D203`_); documentation (_`D191`_, _`D205`_); `npm run ci`; a trial `serve` of a copy of a fixture (or of this repository), checked by the user in a browser: a linked showcase updating without a page reload, an error frame, the issues bar.
