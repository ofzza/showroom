# Pitfalls

Pitfalls of the specification (`./.workflow/SPEC.md`), tagged _`K…`_: risks that could make us backtrack or stall later, each with what resolved it, once resolved.

- [x] _`K1`_ **Showcases need the host's own code and framework.** A showcase imports host code, so it has to be bundled with the host's own React (two copies of React break hooks), its tsconfig and its dependencies. A showroom built once and shipped prebuilt can't do this. Why it matters: if the first version's architecture assumes no bundler, showcases could force a rewrite. Resolved by _`D2`_: the showroom is built with Vite against the host repository from the start. Making the host's own dependencies resolve correctly is still part of _`K7`_.
- [x] _`K2`_ (taken by _`P1`_, _`S6`_) **Other frameworks inside a React/FluentUI SPA.** An Angular (or other) component can't be rendered as a React component. Showcases for those frameworks would need iframes or web components. Why it matters: this shapes the stack adapter interface, even though it only bites later. Resolved by _`D76`_ (SPEC-S6-showcases.md): every showcase renders in an iframe.
- [x] _`K3`_ (taken by _`P3`_) **Hosts that don't use Node.** `../dotnetschema` has no `package.json`. The tool still needs Node to run (e.g. through `npx`), and its project information would come from `.slnx`/`.csproj`. Why it matters: "included into the host repository" means something different there. Resolved by _`P3`_'s _`D69`_: run through `npx --package`, documented; such hosts still need a stack adapter of their own (later).
- [x] _`K4`_ (taken by _`P2`_, _`P3`_) **Static hosting under a subpath.** GitHub Pages serves a site under `/<repo>/` and doesn't rewrite paths on the server. The SPA needs relative asset paths, and hash routing (or a `404.html` fallback). Why it matters: deep links break otherwise. Hash routing resolved by _`P2`_ (_`D37`_); relative asset paths by _`P2.2`_'s Vite configuration (`base: './'`), reused by _`P3`_'s build (_`D66`_).
- [x] _`K5`_ (taken by _`P2`_) **Links inside Markdown.** Relative links in a README (to other docs, source files or `LICENSE`) must be rewritten to SPA routes or repository URLs. Why it matters: otherwise they break in the showroom. Resolved by _`P2`_'s _`D38`_: links to documentation files become routes; any other relative link is shown as plain text (no repository URLs, which are the SCM adapters' job).
- [x] _`K6`_ **The example hosts aren't React projects.** `../tsstd` and `../tsschema` are plain TypeScript libraries, and `../dotnetschema` is .NET. Why it matters: a React-only first adapter might not cover any of the example hosts. Resolved by _`D1`_: the first stack adapter is a TypeScript one.
- [x] _`K7`_ (taken by _`P2`_, _`P3`_, _`S6`_) **Where the showroom's own dependencies come from (_`D2`_).** Building with Vite needs Vite, React and FluentUI. If they're `showroom` `dependencies`, every host repository installs them, including hosts without React (`../tsstd`) and without Node (`../dotnetschema`, through `npx`). If the host repository is asked to install them, it carries that setup. Later, showcases must use the host's own React and not a second copy. Why it matters: it decides how heavy and fragile installing and running `showroom build` is. Resolved for the showroom by _`P2`_ (_`D48`_, _`D57`_: `showroom`'s own `dependencies`, aliased so a host's React never mixes in); using the host's own React remains open for showcases. Resolved for showcases by _`D76`_ and _`D81`_ (SPEC-S6-showcases.md): showcase frames are built with the host's own framework and tooling, isolated from the showroom (the remaining risk is _`K10`_).
- [x] _`K8`_ **"`README` anywhere" needs exclusions (_`D6`_).** Taken literally, it includes every README in `node_modules/`, `dist/` and other generated folders. Why it matters: the showroom would fill up with third-party docs. Resolved by _`D10`_: the stack adapter lists what to skip, and the configuration can override it.
- [ ] _`K9`_ (from _`S6`_) **The Angular toolchain.** Compiling Angular showcases needs the Angular compiler. There are two routes: `@analogjs/vite-plugin-angular`, a community wrapper around the compiler that fits `showroom`'s Vite setup but is a third-party dependency tied to Angular's major versions; or driving the host repository's own Angular CLI (`@angular/build`'s application builder) through its `angular.json`, closer to official (this is what Storybook for Angular does). Either way: zone or zoneless, standalone or NgModule, and a supported version range. Why it matters: it decides how Angular showcases are built at all; it needs a spike before planning.
- [x] _`K10`_ (from _`S6`_; taken by _`P7`_ (PLAN-P7-ts-react.md); resolved for React by _`P7.2`_ (PLAN-P7.2-react.md): the host's React 18 and 19 bundled and type checked (_`D344`_, _`D349`_); resolved for bundling React by _`D244`_ (PLAN-P7-ts-react.md), after the spike of 2026-11-12; the host's TypeScript is open, _`O30`_, _`O31`_ (PLAN-P7-ts-react.md), planned by _`D273`_, _`D275`_, _`D276`_ (PLAN-P7.1-ts.md); resolved for the host's TypeScript 5.x and 6.x by _`P7.1.2`_ (PLAN-P7.1-ts.md): resolved as Node does from the documentation file's folder and loaded with `createRequire` (_`D276`_, _`D295`_), TypeScript 7 left to _`K16`_; Angular's tooling is _`K9`_) **Framework tooling loaded from the host repository (_`D81`_).** `showroom` has to load the host's compilers and plugins from the host's `node_modules`, next to its own Vite. Their versions may not match `showroom`'s Vite, and a global or `npx` install of `showroom` resolves modules from elsewhere than the host. Why it matters: it makes building showcases fragile across hosts; using the host's own React in a showcase frame needs a spike (a host on React 18, next to the showroom's React 19), in `serve` and `build`.
- [x] _`K11`_ (from _`S6`_; narrowed by _`D236`_ (SPEC-S6-showcases.md); taken by _`P7.1`_ (PLAN-P7-ts-react.md); resolved for `ts` by _`P7.1.1`_ (PLAN-P7.1-ts.md): what a showcase can import is _`D236`_'s list, the host's PostCSS configuration is ignored and its tsconfig applies as Vite's transform reads it (_`D253`_), and the host's own package resolves by its name (_`D259`_), each covered by the `showcase-ts` fixture; `react` adds nothing to it) **The host repository's build configuration.** Showcases import host code, which may rely on tsconfig `paths`, SCSS, assets, environment variables, monorepo workspaces, or the library's `dist` instead of its `src`. Why it matters: every host differs; without a small, well-defined way to extend the build, and host requirements (_`D80`_) narrowing it, host-specific problems never end.
- [ ] _`K12`_ (from _`S6`_; taken by _`P4`_ (PLAN-P4-showcases.md) for its own showcase adapters, _`D105`_–_`D109`_; the framework part is _`O20`_; taken by _`P7`_ (PLAN-P7-ts-react.md) for `ts` and `react`, React 18 fixtures by _`D245`_; resolved for `ts` by _`P7.1.1`_ (PLAN-P7.1-ts.md): `ts` showcases need no framework, so the `showcase-ts`, `showcase-ts-errors` and `showcase-ts-many` fixtures run real Vite builds in the `integration`, `e2e` and `serve` tiers; open for `react`) **Testing showcase builds.** Fixtures can't hold `node_modules` (they're gitignored), and today's tests never run Vite. Building real React and Angular showcases needs those frameworks installed: heavy new devDependencies, or an install step in CI. Why it matters: without a strategy, the showcase builds, and the "bring your own build" frames (_`D78`_), go mostly untested.
- [ ] _`K13`_ (from _`S6`_; taken by _`P4.3`_ (PLAN-P4.3-serve.md) for the `html` and custom showcase adapters, _`D181`_, _`D185`_; for the `ts` and `react` showcase adapters by _`D243`_ (PLAN-P7-ts-react.md), rebuilding on change, with hot updates deferred to _`L11`_ (PLAN.md)) **Watching showcases in `showroom serve` (_`D82`_).** Today `serve` reruns the check and fully reloads the page after a change. A showcase's code change should update its frame only, while documentation changes keep today's behaviour; the frames may need their own dev servers (and ports), or Vite's support for several environments. Why it matters: it shapes how `serve` is built.
- [ ] _`K14`_ (from _`S6.5`_; taken by _`P4.2`_ (PLAN-P4.2-showcase-frames.md) for the `html` and custom showcase adapters, _`D134`_; resolved for bundling with the Vite-based ones by _`D235`_ (SPEC-S6-showcases.md) and _`D244`_ (PLAN-P7-ts-react.md): Vite virtual modules at paths in the documentation file's folder; type checking them is open, _`O30`_ (PLAN-P7-ts-react.md), planned by _`D273`_ (PLAN-P7.1-ts.md): virtual files served from memory; resolved for type checking by _`P7.1.2`_ (PLAN-P7.1-ts.md): a compiler host serves them from memory, nothing is written (_`D273`_, _`D292`_)) **Inline files on disk (_`D91`_).** A build chain resolves files from disk, so virtual files have to be found in their documentation file's folder without dirtying the host repository. Ideas: Vite virtual modules (no file written) for Vite-based showcase adapters; writing them and deleting them after the build (failed or parallel builds leave them behind); copying the host repository to a temporary folder (slow); writing them elsewhere and rewriting the references to them. Why it matters: tooling that insists on real files (e.g. the host's Angular CLI, _`K9`_) can't use virtual modules.
- [x] _`K15`_ (from _`P7.1.1`_ (PLAN-P7.1-ts.md), 2026-11-13; taken by _`P7.1.1`_, _`O44`_; resolved by _`D259`_ (PLAN-P7.1-ts.md), after the spike of 2026-11-13: Vite resolves it) **The host's own package by its name (_`D236`_ (SPEC-S6-showcases.md)).** A showcase may import the host's own package by its name, through its `exports`, as Node's self-reference allows; nothing shows that Vite's resolver does the same, and the _`K10`_ spike didn't try it. Why it matters: without it, the usual way a library demos itself only works when the package is also linked into `node_modules`, and _`P7.1.1`_ needs a resolve plugin of its own.
- [ ] _`K16`_ (from _`P7.1.2`_ (PLAN-P7.1-ts.md), 2026-11-13; taken by _`P7.1.2`_, _`O45`_ (PLAN-P7.1-ts.md); TypeScript 7 deferred by _`D273`_, _`D274`_ (PLAN-P7.1-ts.md) to _`L12`_ (PLAN.md)) **TypeScript 7 has no classic compiler API (_`D234`_ (SPEC-S6-showcases.md)).** TypeScript 7 (the native port, npm's `latest` since 7.0) exports only `unstable/*` modules from its `typescript` package (e.g. `unstable/sync`, `unstable/async`, `unstable/fs`): no `ts.createProgram`, no custom compiler host. 6.0 is the last line with the classic API. Type checking with the host repository's own TypeScript, with virtual files served from memory (_`O30`_ (PLAN-P7-ts-react.md)), has no proven route on TypeScript 7: its unstable API, the host's `tsc` as a subprocess (with virtual files on disk, _`K14`_), or leaving TypeScript 7 unsupported for now. Why it matters: TypeScript 7 is the current release, so hosts on it are the common case to come; an API marked unstable may change in any release.
- [x] _`K17`_ (from _`S10`_ (SPEC-S10-presentation.md), 2026-11-13; taken by _`P10.4`_, with a spike first, _`D385`_ (PLAN-P10-presentation.md); resolved by _`D403`_ (PLAN-P10.4-code-pane.md), the spike's evidence) **Switching the code pane's layout by the column's width (_`D355`_ (SPEC-S10-presentation.md)).** A CSS container query is the right tool; the installed `@griffel/core` (1.21.4) handles `@container` rules (review 2026-11-13), but the tests' server-side rendering can only assert class names, so the layout itself is only checked in a browser. Why it matters: without it, the layout falls back to the viewport's width (`NARROW_VIEWPORT`), which stacks too late in a narrow documentation column.
- [x] _`K18`_ (from _`S10`_ (SPEC-S10-presentation.md), 2026-11-13; taken by _`P10.4`_, with a spike first, _`D385`_ (PLAN-P10-presentation.md); resolved by _`D403`_ (PLAN-P10.4-code-pane.md), the spike's evidence) **The showcase frame's height and identity beside the code pane (_`D352`_, _`D354`_, _`D376`_ (SPEC-S10-presentation.md)).** In a row, an iframe stretches to the block's height by default: a showcase sized to its viewport would then grow until the frame script's guard (`MAX_REPEATED_GROWTHS`) stops it, for good; and moving the iframe in the React tree when the code pane's state changes would remount it, reloading the showcase and losing its state. Toggling also changes the frame's width, so its content reflows and reports a new height (review 2026-11-13: a feedback loop is less likely than stretching or remounting). Why it matters: frames that keep resizing, settle at the wrong height, or reload.
- [x] _`K19`_ (from _`S10`_ (SPEC-S10-presentation.md), 2026-11-13; taken by _`P10`_, resolved by _`D382`_ (PLAN-P10-presentation.md)) **The size of _`S10`_.** It touches the marker grammar and `check`, the showcase adapter interface, the `html` build, the showroom's showcase and code rendering, the console and frame scripts, the Glossary, the documentation, the examples and many tests. Why it matters: one large segment risks a long, hard-to-review change; planning should split it.
