# AGENTS.md

Guidance for AI coding agents when working in this repository.

## Keeping documentation and tests current

**`README.md`, `CONTRIBUTE.md`, `AGENTS.md` and the tests are part of the deliverable of every task, not separate chores.** This holds whether or not the task mentions them. Whenever a change makes any of them inaccurate or incomplete, update it in the same change. Never leave it for later, and never finish a task by reporting only the code change. `PUBLISH.md` falls under the same rule whenever the release process changes.

- **`README.md`** is the user-facing documentation: what the project is, how to get it, how to use every export (`# Usage`), and how to develop it (`# Development`).
- **`CONTRIBUTE.md`** is the contributor-facing documentation: reporting issues, the contribution workflow and branching, and the architecture and glossary.
- **`AGENTS.md`** (this file, included by `CLAUDE.md`) is the agent-facing documentation: layout, commands, testing, conventions and gotchas.

Tests in particular: new or changed behaviour gets tests in the `*.test.ts` beside the changed file. Tests that a change breaks are handled as [WORKFLOW.md](./WORKFLOW.md) › "Documentation and tests" says. The purpose comments of the tests (see [Code style](#code-style)) are part of them, and must be kept current along with them.

## Project

`@ofzza/showroom`: build a showroom for a repository: its documentation, enriched by showcases. A CLI (`showroom`, the `bin` in `package.json`) and a library. It is MIT licensed, built from `src/` to `dist/`, and published to NPM as `@ofzza/showroom` (source: [github.com/ofzza/showroom](https://github.com/ofzza/showroom)).

## Commands

- `npm run clean`: deletes `dist/` (cross-platform, via `node -e`).
- `npm run build`: runs `tsc -p tsconfig.build.json`, compiling `src/` to `dist/` with declarations, then `copy-app`, then `build-mermaid`. `prebuild` runs `clean` first, so renamed or removed modules never leave stale output behind to be published.
- `npm run dev`: `copy-app`, then `build-mermaid -- --if-stale`, then the compilation in watch mode (a change to `src/app/index.html` needs a restart).
- `npm run build-mermaid`: builds the shared Mermaid bundle into `dist/mermaid/` (`build/mermaid/index.ts`'s `main()`, run by Node with `--experimental-strip-types`), and writes its stamp, the hash of `package-lock.json`, `build/mermaid/index.ts` and the stub (`getMermaidBuildHash()`); with `--if-stale` (after `--`), only when the stamp doesn't match. `ci:build` doesn't run it.
- `npm run copy-app`: copies `src/app/index.html`, which `tsc` doesn't emit, to `dist/app/`. `ci:build` only compiles, and doesn't run it.
- `npm start`: runs the built command line, `node dist/cli/bin.js`. Pass arguments after `--`, e.g. `npm start -- check --root test/fixtures/minimal`. `npm start -- serve --root <host>` previews the showroom of a host repository; with `npm run dev` running alongside, reload the page to see changes to `src/app/`. Never serve a fixture in `test/fixtures/` while editing its files: work on a copy in a working-files folder. Likewise, run `npm start -- build --root <host>` only on a copy, as it writes the output folder into the host repository; serve the result over HTTP (browsers won't run it from `file://`).
- `npm test`: runs every `test:*` script.
  - `npm run test:unit`: `vitest run --project unit`, a single invocation that both executes the tests and type checks them.
  - `npm run test:integration`, `npm run test:e2e`, `npm run test:serve`: `vitest run --project <tier>`, executing the other test tiers (see [Testing](#testing)); each passes with no tests.
- `npm run ci`: runs every `ci:*` script (`ci:build`, `ci:showroom`, `ci:eslint`, `ci:prettier`, `ci:test-unit`, `ci:test-integration`, `ci:test-e2e`, `ci:test-serve`). This is what GitHub Actions runs. `ci:showroom` dogfoods `showroom` on this repository: `node dist/cli/bin.js check --showcases --quiet --trust`, with what `ci:build` just compiled (so it comes right after `ci:build`: `npm-run-all ci:*` runs the scripts in `package.json`'s order).
- `npm run prepare`: builds. It is invoked automatically by a local `npm install`/`npm ci` and before `npm publish`, but **not** when the package is installed as a dependency.
- `prepublishOnly`: runs `npm run ci` before `npm publish`, so a failing build is never published.

**Script wiring matters when adding one.** `test` is `npm-run-all test:*` and `ci` is `npm-run-all ci:*`, so a new `test:<name>` joins `npm test` automatically. It will _not_ run in CI until a matching `ci:test-<name>` script exists, so add both.

## Testing

Vitest, with `describe`/`it`/`expect` imported explicitly (`globals` is not enabled). `vite.config.ts` defines five projects: four test tiers, told apart by file name suffix, and `debug`:

- **`unit`** matches `src/**/*.{test,unit.test,spec,unit.spec}.{js,jsx,ts,tsx}`, except the other tiers' suffixes, and runs each TypeScript test file through **both** Vitest pools in one invocation. The default pool executes it for its runtime expectations. `tsc` (via `typecheck.tsconfig: './tsconfig.json'`) type checks it for its compile-time assertions (`expectTypeOf`, `@ts-expect-error`), reporting type errors as failed tests.

  Two kinds of file only go through one pool. JavaScript test files (`.js`, `.jsx`) are only executed, as `tsc` does not check JavaScript. Type-only test files, Vitest's `*.test-d.{ts,tsx}` / `*.spec-d.{ts,tsx}` convention, are only type checked: put pure `expectTypeOf` / `@ts-expect-error` assertions there, with no runtime expectations.

  `tsc` only checks files `tsconfig.json` includes, whatever `typecheck.include` says. A test file outside its `include` is collected but never checked, so its type assertions pass silently. This is why `tsconfig.json` includes `.tsx` files.

  `include` and `typecheck.include` deliberately match the same TypeScript test files. Vitest globs the two independently and does not warn when they overlap, so **every test file is collected and reported twice**, with each test counted once per pool. That is expected, not a misconfiguration. It has two consequences:
  - A file change triggers two reruns in watch mode.
  - A file containing no runtime `test()`/`describe()` call fails the runtime pass with "No test suite found in file", unless `--passWithNoTests` is set (it is set in `test:unit`).

  Type errors in non-test sources are reported too. `tsc` runs over the whole `tsconfig.json` program with no file list, so an error outside a test file surfaces as an "Unhandled Source Error" and fails the run without being attributed to any test.

  `typecheck.spawnTimeout` is pinned to `10000`. Vitest 5 documents a default for it but never applies one, yet uses the value unguarded when spawning the checker, which leaves an intermittent race.

- **`integration`** (`*.integration.test.*`: real showcase adapter builds, `buildShowcases()` and `check()` with `showcases`, on the fixtures; the `ts` and `react` showcase adapters' Vite builds), **`e2e`** (`*.e2e.test.*`: the command line, `main()` called in-process, and `build()` with Vite, on fixture copies) and **`serve`** (`*.serve.test.*`: `serve()` with the dev server, on fixture copies) only execute their files, with a 60 s timeout; none of them type checks. Their files are still type checked by `unit`'s `tsc` run, which covers the whole `tsconfig.json` program, and `tsconfig.build.json`'s `*.test.ts` exclude keeps them out of the build.

  Their `TMPDIR`, `TMP` and `TEMP` point at a folder of each project's own, `node_modules/.cache/showroom-tests/tmp-<project>/` (`env` in `vite.config.ts`), and their `XDG_CACHE_HOME` at its `cache/`, which `src/testing/setup/temporary-folder.ts`, their global setup, creates and removes (with the folder), so the temporary folders `showroom` makes (the showcases' build, Vite's cache, recorded showcases' run folders) stay inside the repository. The `e2e` and `serve` projects' second global setup, `src/testing/setup/app.ts`, compiles `src/` once per run into a scratch folder (`compileApp()`: `tsc -p tsconfig.build.json --outDir <scratch>`, run with `process.execPath`, plus `index.html`), provided as `inject('appDir')`, so builds and dev servers never depend on, or write to, `dist/`. Each of them builds the shared Mermaid bundle with `src/testing/setup/mermaid.ts` (`buildTestMermaid()`: `build/mermaid/`'s build into `node_modules/.cache/showroom-tests/mermaid-<hash>/`, the hash `npm run build-mermaid`'s stamp holds, built into a sibling and renamed into place, kept across runs while the hash is unchanged), provided as `inject('mermaidDir')`, so no test depends on `dist/mermaid/`. The `integration` and `e2e` projects' last global setup, `src/testing/setup/installs.ts`, installs the fixtures that carry a lockfile (`INSTALLED_FIXTURES`: `showcase-react-18`, on React 18; `showcase-angular-20` and `showcase-angular-21`, on Angular 20 and 21, each with its own TypeScript) with `installFixture()`: a copy, with `npm ci --no-audit --no-fund --ignore-scripts`, in `node_modules/.cache/showroom-tests/installs/<name>-<lockfile hash>/`, kept across runs while the lockfile is unchanged (its fixture files copied over it again on each run, as they can change without the lockfile), and provided as `inject('installedFixtures')`; tests only read an install, or copy it to write.

- **`debug`** matches every file the `unit` project executes, plus files ending in `.debug.{js,jsx,ts,tsx}`. Type-only `*.test-d.*` files are not in it, as there is nothing in them to execute. It executes them at runtime only, with no type checking, and is driven by the "Debug Current Test File" config in `.vscode/launch.json`.

  It is **only defined when `VITEST_DEBUG=1` is set**, so an unfiltered run (plain `vitest`, "Debug ALL Test Files", or a tool that runs every project it finds) does not run every test a second time. "Debug Current Test File" sets the variable through its `env`. From a terminal, set it yourself, e.g. `$ VITEST_DEBUG=1 npx vitest run --project debug src/index.test.ts`. Without it, `--project debug` fails with "No projects were found". There is deliberately no npm script for this: setting a variable inline is not portable to Windows, and a `test:debug` script would join `npm test`.

  `.gitignore` excludes `*.debug.test.{js,jsx,ts,tsx}`. Those files also match the `unit` glob, so scratch debug tests run locally but are never committed.

**Fixture host repositories** live in `test/fixtures/<name>/`, one per area under test (the defaults, file name variants, duplicates, configured patterns, one per configuration error; and grouped by area where `check` reports every issue at once: `showcases`, `showcase-keys`, `showcase-errors`, `showcase-adapters`, `links`, `linked-files`). Tests reach them with `fileURLToPath(new URL('<relative path to test/fixtures>/<name>', import.meta.url))`, and never write to them. Being outside `src/`, they are neither type checked, linted, formatted by `ci:prettier`, built nor published. See [Gotchas and known issues](#gotchas-and-known-issues) for what they can't contain.

**Scratch folders**: a test that needs to write creates its own folder with `src/testing/`'s `createScratchFolder()` (or copies a fixture into one with `copyFixture()`), inside `node_modules/.cache/showroom-tests/` (ignored by git, ESLint and Prettier, and wiped by `npm ci`), and removes it afterwards (`remove()`, e.g. in `afterEach`). **`showroom serve` is unit-tested without starting a server, and served in the `serve` tier.** The unit tests cover the Vite configuration and its plugins (`src/vite/`, calling the plugins' hooks directly, and the showcase frames middleware with fake requests and responses), the watcher's `ignored` function, what a build serves (`runBuild()`: the showcase frames that built, a check's errors or not, and each showcase's checks and issues), and the host watcher's runs and decisions (`createHostWatcher()`, with a fake check, a fake build and a fake reload target, and fake timers for the debounce): a full reload, or the `showroom:showcases` (also for changed checks and issues, a showcase that stops building among them) and `showroom:issues` events. `main()`'s `serve` command is only run on a fixture whose first check fails. `src/cli/serve/index.serve.test.ts` calls `serve()` itself on fixture copies, on port 0, with the compiled showroom (`inject('appDir')`), stopped through its internal `signal` option (`onListening` gives the URL), and fetches the showroom, the virtual module (`/@id/__x00__virtual:showroom-host`, every showcase with its checks and issues, an unbuilt one with no URL), the showcase frames and their files. No `serve` test edits files (see the gotcha on Vite's watcher). The user checks updates after a change, and the issues bar, in a browser.

**`showroom build` is unit-tested without running Vite, and end to end with it.** The unit tests cover the output folder's resolution and ignore pattern (`src/cli/check/internal/`, and the `output-folder`, `out-dir-root` and `out-dir-outside` fixtures), the marker's decision (`getOutputFolderState()` on entry lists, as git can't hold an empty folder, and `readOutputFolderState()` on the `output-folder` fixture's folders), the build's Vite configuration (`getBuildConfiguration()`) and the plugin emitting showcase frames; `main()`'s `build` command is only run where it stops before building. `src/cli/build/index.e2e.test.ts` calls `build()` itself, with the compiled showroom (`inject('appDir')`), on fixture copies: a full build with showcase frames, and the cases that stop before Vite. The user still checks trial builds in a browser.

After adding or changing type-level assertions, sanity-check them: break one deliberately, confirm the run fails, then revert. Vitest prints an "experimental" warning for typecheck, which is expected.

## Code style

`ci:prettier` and `ci:eslint` enforce the style, but both only look at `src` and `build`. **Markdown files are not checked by CI**: format the ones you touch as [WORKFLOW.md](./WORKFLOW.md) › "Markdown formatting" says.

- Prettier: `printWidth: 160`, single quotes, 2-space indent, semicolons, trailing commas, always-parenthesised arrow params.
- Every file opens with a descriptive header comment.
- JSDoc on every exported symbol: a summary in third person ("Gets ...", "Checks if ...", "Represents ..."). Only `@param` and `@returns` are used, never `@example`, `@template` or `@see`.
- Internal, non-exported symbols are `_`-prefixed and still get JSDoc. ESLint's `no-unused-vars` ignores `_`-prefixed vars, args and catch bindings.
- Group sections with `// #region Name` / `// #endregion`.
- Generic parameters are `T`-prefixed and descriptive (`TArray`, `TObject`), including `infer` bindings, which must never shadow an outer parameter.
- In conditional type chains, put a `// comment` line before each branch saying what it handles, rather than a trailing comment.
- Each test file has one top-level `describe` named after its module. `it()` names are capitalised verb phrases: `it('Greets the world by default', ...)`.
- **Every `describe` callback opens with a purpose comment.** It is a `//` block on the first line inside the callback, saying _what_ is under test and _how_ it is tested. A nested `describe` says only what its parent's comment does not.
- **An `it` callback gets a comment only when its title and body do not explain why it exists.** Examples: a regression, an edge case, a test guarding a gotcha (link it: `See AGENTS.md › <gotcha title>`), or a non-obvious assertion. Never restate the title.
- Rules deliberately off: `@typescript-eslint/no-explicit-any`, `ban-ts-comment`, `no-empty-object-type`. `any` and `@ts-expect-error` are fine to use where they earn their place.

## Gotchas and known issues

- **`npm-run-all2`, not `npm-run-all`.** The original `npm-run-all@4` validates the package name and aborts on names it rejects (e.g. a leading `.`). Its maintained fork `npm-run-all2` installs the same `npm-run-all` binary without that check.
- **Relative imports in `src/` must carry an explicit `.js` extension.** `moduleResolution: bundler` lets TSC accept `./module`, and TSC does not rewrite specifiers on emit. The extensionless form then ships to `dist/`, and Node's ESM resolver rejects it (`ERR_MODULE_NOT_FOUND` / `ERR_UNSUPPORTED_DIR_IMPORT`). Write `./module/index.js`.
- **Every supported major of a framework is tested, the older ones on fixtures with an install of their own** (`installFixture()`, _`D349`_ in `.workflow/PLAN-P7.2-react.md`, _`D450`_ in `.workflow/PLAN-P11-angular.md`): the current major comes from this repository's own install, and each older supported major is an installed fixture (`showcase-react-18`; `showcase-angular-20` and `showcase-angular-21`). Their first run of `test:integration` or `test:e2e`, and every run after their lockfile changes, needs the npm registry; their `node_modules` is never committed (`.gitignore`), and Dependabot, which only watches the root, never bumps them. Their install runs `npm ci --ignore-scripts`, as React and Angular need no install scripts (unlike this repository's own install, below). A new one is added to `INSTALLED_FIXTURES`. When this repository moves to a new major (Dependabot proposes majors in pull requests of their own: `react`, `angular`, `typescript`), the majors guard fails until the major it replaces gets an installed fixture and `CURRENT_MAJORS` is updated, in the same change; a major dropped from support loses its fixture.
- **A `react` showcase's mount module is a virtual module beside its entry point** (`<entry>.showroom-mount.js`), so its bare imports resolve from the host repository (_`D244`_ in `.workflow/PLAN-P7-ts-react.md`); never give it a `\0` id. It is Vite's input, so the entry chunk is named after it; the shared build leaves generated modules out of the reads, and places their build errors (a missing default export) at the entry point, line 1.
- **The `cs` showcase adapter sets `dotnet`'s settings through the environment, never on its command line** (_`D778`_ in `.workflow/PLAN-P20-recorded.md`): any MSBuild switch (`-nodeReuse:false`, `-p:…`, `--tl:off`) makes `dotnet build <file>.cs` read the file as a project (`MSB4025`); `--artifacts-path` is a `dotnet` option, and fine. `DefaultItemExcludes` names every `.cs` virtual file by its absolute path in the host copy, escaped for MSBuild, or a project whose folder holds one compiles it, failing every showcase referencing that project with `CS9298` (_`K28`_). This repository needs the .NET SDK 10 for its tests and its `cs` example (_`D718`_ in `.workflow/SPEC-S16-csharp.md`), as CI's `actions/setup-dotnet` installs it. Its program is found after the build (`findCsProgram()`), never at a fixed path: the .NET SDK 10 writes it to `bin/debug/`, the .NET SDK 11 to `bin/<file>.cs/debug/`; CI's runner image has both SDKs, and `dotnet` picks the newest one installed (there is no `global.json`), so CI builds with 11 even though `actions/setup-dotnet` asks for 10, where a machine with only the SDK 10 passes.
- **Never use `npm ci --ignore-scripts` here.** `unrs-resolver` (`postinstall`) and `@parcel/watcher` (`install`) rely on their install hooks to link native bindings, and skipping them risks breaking ESLint. The CI workflow uses plain `npm ci` for this reason.
- **`prepare` builds during install**, so `npm ci` compiles once and `ci:build` compiles again. The duplicate build costs about a second and is accepted. `prepare`'s build also builds the shared Mermaid bundle, which takes about half a second (measured on 2026-11-18).
- **The real Node floor is 22.13.0 / 24.0.0**, not the bare major versions. It is set by `vitest@5`, `vite@8` and `eslint-visitor-keys@5`, and Node 20 is not supported. `actions/setup-node` with `node-version: 22` resolves to the latest 22.x and satisfies this.
- **Do not add an `engines` field for the dev-toolchain Node floor.** It would restrict consumers for no reason.
- **The shared Mermaid bundle is `showroom`'s own, built by `npm run build`, never at run time** (_`D832`_, _`D845`_, _`D848`_–_`D853`_ in `.workflow/PLAN-P21-jsonschema.md`): `mermaid` is a devDependency, and the package ships only the bundle in `dist/mermaid/`. Its build (`build/mermaid/`) is Vite's library mode (an application build may drop the entry's exports), whose ES output Vite never minifies the whitespace of, so it sets `rolldownOptions.output.minify` itself; `elkjs` and its subpaths are aliased to a stub that throws (elkjs is EPL-licensed, about 1.6 MB, and only Mermaid's `elk` layout uses it), so a page must initialise Mermaid with `layout: 'dagre'`; `base: './'` keeps its chunks' imports relative, so it works under any base path; Vite's `build.license` writes `THIRD-PARTY-NOTICES.txt`. It is run by Node's type stripping, so `build/mermaid/index.ts` imports no relative TypeScript module (its stub only by path) and uses only erasable syntax. A compilation alone (`ci:build`, `tsc`) leaves `dist/mermaid/` missing: `serve` and `build` then warn once, when a showcase frame uses it. `.gitignore` ignores `/build/*` but re-includes `build/mermaid/` (ESLint takes its ignores from `.gitignore` too).
- **A showcase frame reaches the shared Mermaid bundle through an import map** (_`D858`_ in `.workflow/PLAN-P21-jsonschema.md`): `buildShowcases()` reads `mermaid.js`'s hash once per run from its `mermaidDir` option (`serve`'s and `build`'s, the package's by default, so a test passes `inject('mermaidDir')`), and inserts, right after the frame script of each frame marked as using the bundle, an import map mapping `showroom-mermaid` (`MERMAID_SPECIFIER`) to `getMermaidUrl()` (no `?hash=` when the bundle is missing). The `jsonschema` page imports that specifier; its module (`JSONSCHEMA_MERMAID_SPECIFIER`) can't import `src/showcases/`, which imports the registry, so a test keeps the two equal.
- **`tsschema`'s traps are kept out of the `jsonschema` showcase adapter** (_`D840`_ in `.workflow/PLAN-P21-jsonschema.md`): definitions are walked by `definitionNames`, a reference followed by its target's `name`, never its `target` getter (a recursive schema would recurse forever, `toEqual` included); no `Type` getter is read (it throws); type descriptors are told apart by `kind`, never `instanceof` (its classes are types only); tests assert on the Mermaid source. Whether a `$ref` resolves is asked of `tsschema` (`reflect()` of that `$ref` beside the schema's `$defs`), as it decides (it resolves `#/$defs/List~T~` literally, not escaped names or `__proto__`). Mermaid shows one stereotype per class, so a node's stereotypes are joined (`«root · enumeration»`). A `jsonschema` build's issues name no check: its `build` status mark is the build's own (as `cs`'s), and an error ships no showcase frame.
- **The shared Mermaid bundle is handed out at `mermaid/<path>`, only while a showcase frame uses it** (_`D849`_, _`D853`_ in `.workflow/PLAN-P21-jsonschema.md`): `serve`'s middleware answers every request under `mermaid/` (a file the bundle's folder lists, never a dotfile; a 404 for anything else, and for everything while no current showcase frame uses it), so no folder of `src/app/` may be named `mermaid` (`src/vite/`'s tests guard it, as for `files`), and `build` emits the folder's files once, only when an emitted showcase frame uses it. Only a built-in showcase adapter's showcase frames can (`usesMermaidBundle()` in the registry, carried as `ShowcaseFrame`'s `mermaid`), never a custom one's. A page reaches it by `getMermaidUrl()`, relative, with `mermaid.js`'s hash as `?hash=`; the chunks are sent `immutable`, `mermaid.js` and the notices `no-store`.
- **`files: ["dist"]` is an allowlist.** Anything else that must ship has to be added there. Check with `npm pack --dry-run`.
- **The `exports` map seals deep imports.** Only `.` and `./package.json` resolve, so `<package>/dist/<module>/index.js` fails under `node16`/`nodenext`/`bundler`. A new module only needs re-exporting from `src/index.ts`. Add an `exports` subpath only if the module should be importable on its own.
- **Do not add a `paths` alias to the tsconfigs.** TSC does not rewrite aliased specifiers on emit, so they would ship to `dist/` unresolvable.
- **Anything in `dependencies` is installed for every consumer.** Keep build, lint and test tooling in `devDependencies`.
- **`@types/node` is pinned to the lowest supported Node major** (currently `^22`), so type checking cannot silently rely on APIs newer than the CI matrix floor. `.github/dependabot.yml` ignores its semver-major updates for this reason, so bump it by hand together with the matrix.
- **`@eslint/js` must be a direct devDependency.** `eslint.config.js` imports it, and since ESLint 10 `eslint` no longer pulls it in transitively.
- **`tsconfig.build.json` excludes test files**, so `npm run build` never reports a type error in a test, and never emits one to `dist/`. Its `exclude` lists each test suffix (`.test`, `.spec`, `.test-d`, `.spec-d`) for both `.ts` and `.tsx`, as tsconfig globs have no `{a,b}` braces. A new test naming convention must be added there, or its files ship in the package. It also excludes `src/testing/`, the test helpers. Use `npm test` (the `unit` project type checks them) or `tsc --noEmit -p tsconfig.json`.
- **Only `src/cli/bin.ts` and `src/app/main.ts` have side effects** (they run the command line, and mount the showroom, on import), which is why nothing imports them, and why `sideEffects: false` stays truthful: every other module, `src/index.ts` included, only declares.
- **`sideEffects: false` also applies to the bundled showroom**, so the app never relies on an import that is only there for its side effects: no CSS imports (styles are Griffel's `makeStyles`, with FluentUI tokens), no polyfills.
- **`types: ["node"]` applies to the showroom's browser code too**, so Node globals (`process`, `Buffer`, …) type check in `src/app/` although they don't exist in the browser. Don't use them there. The DOM types come from TypeScript's default `lib`.
- **`main()` loads `serve` and `build` with a dynamic `import()`, and the `ts` showcase adapter loads Vite with `import()` inside `build()`**, so `showroom check` without `--showcases`, and library users, never load Vite (`check` reaches the showcase adapter registry, and so the `ts` showcase adapter). Likewise, the `angular` showcase adapter loads the host's Angular compiler, its Linker and its Babel with `import()` inside `build()` only, and imports `@angular/compiler-cli` (a devDependency) only with `import type`. Never import `vite` (except `import type`), `src/cli/serve/`, `src/cli/build/` or `src/vite/` statically from anything `src/index.ts` reaches, and never re-export them: they are internal, like `src/cli/check/internal/` (`src/index.test.ts`'s export list guards this).
- **Vite's root is `dist/app/` inside the package, and its `cacheDir` a fresh `mkdtemp` folder** (`<tmp>/showroom-XXXXXX`), removed when `serve` exits. Nothing is generated into the host repository or the package, so a global install works. `getAppDir()` resolves `../app/` from the module itself, which is `src/app/` in the tests (holding `index.html`, but no compiled `main.js`).
- **`build` empties the output folder, guarded by the `.showroom` marker.** Vite's `emptyOutDir` deletes everything in it, so `build` only lets it when the folder is missing, empty or marked (`readOutputFolderState()`), and writes the marker after every build. Never bypass this check, and never let the output folder be the host root or outside it (`resolveOutputFolder()`, which the check enforces).
- **The build leaves out the bundler's warnings about the showroom's own dependencies**: `MODULE_LEVEL_DIRECTIVE` (FluentUI's and Griffel's `'use client'`, once per file, about 1900 lines) the chunk size (`CHUNK_SIZE_WARNING_LIMIT`, above the app's single chunk of about 810 kB), and `PLUGIN_TIMINGS` (the bundler's note that the plugins, `showroom`'s own, took most of a build's time, which comes and goes with the machine's speed: it once failed a `serve` test on a slow CI runner). A new warning of that kind goes into `SILENCED_WARNINGS` in `src/cli/check/internal/`, which the `ts` showcase adapter's build warnings leave out too; warnings the host can act on must still show. Angular's own packages warn about nothing in the `angular` fixtures' builds (a test asserts it, in both modes), so there is no list of Angular warnings; one that ever shows is silenced by its code together with its module's id under `node_modules/@angular/` (_`D461`_ in `.workflow/PLAN-P11.1-angular.md`), never by its code alone, which would hide the host's own.
- **React, React DOM and the scheduler are aliased to `showroom`'s own copies** in the Vite configuration (`getReactAliases()`), so a host's different React, next to a hoisted FluentUI, never mixes in ("Invalid hook call"). A new React package the application imports directly needs adding there.
- **A block's views never move, and its header bar holds its status marks and the code pane's button** (_`D575`_ in `.workflow/PLAN-P15.4-views.md`, _`D588`_ in `.workflow/PLAN-P15.5-status-marks.md`): the views are stacked in their own grid cell, under the header bar and the issue list spanning the block, so changing the code pane's state never remounts a showcase frame; the console's state lives in the block (`useConsole()`), shared by the `demo` view's showcase frame and the `console` view. A `demo` view is at least 32 px high (`SHOWCASE_BLOCK_FRAME_MIN_HEIGHT`), and the open console panel leaves no room at its top.
- **A container query's container needs its width given** (`container-type: inline-size`, the code pane's block): it never takes its width from its content, so in a flex parent that doesn't stretch it (FluentUI's drawer, for a linked showcase shown inline's block in the showcase sidebar) it collapses to 0 px wide. The tests' server-side rendering has no layout, so only a browser shows it; the block's sidebar style sets `width: 100%`. Its layout containment also makes it a stacking context of its own, so a `z-index` inside it never lifts anything over what follows the block: the block raises itself as a whole (see the overlays over the page gotcha).
- **A `console` view with no `demo` view runs its showcase frame hidden, never with `display: none`** (_`D570`_ in `.workflow/PLAN-P15.4-views.md`): at its real width and height, `opacity: 0`, `pointer-events: none`, `aria-hidden`, `tabindex="-1"`, not lazily loaded, in a box with no height that clips it; `display: none` or a 1 px frame would give the page no layout (sizes and media queries wrong, CSS animations stopped).
- **Every showcase is shipped, built or not, with its checks and issues** (_`D584`_–_`D586`_ in `.workflow/PLAN-P15.5-status-marks.md`): the shown host information carries each showcase's `checks`, `issues` (as its showcase adapter reported them, `getShownIssue()`: its own message, its own path and line, at the entry point with no line when its path isn't valid) and `buildMark` (false only for an `html` showcase without issues naming no check, decided in `src/vite/`, so the showroom knows no showcase adapter by name); one that doesn't build has no `url`, and shows "Not built". There is no error frame: a showcase whose check fails is served with its files. `serve` sends the checks, issues and build marks with the `showroom:showcases` event, never a full reload (`getShownChange()` ignores them, as it does the URLs).
- **A showcase frame nothing loads is never shipped** (_`D574`_ in `.workflow/PLAN-P15.4-views.md`): a showcase with neither a `demo` nor a `console` view (`loadsShowcaseFrame()`, `src/vite/`) is built and checked, but has no `url` in the shown host information (`LoadedShowcase`, `isLoadedShowcase()`), and `build` doesn't emit its showcase frame; `serve` still serves what it built.
- **The showroom's narrow (phone) layout is switched by CSS alone.** Every style that differs below the breakpoint (768 px) uses `NARROW_VIEWPORT` (`src/app/layout/`) as a `makeStyles` media query; never switch on `matchMedia` or the window's width, which the server-side rendering in the tests can't see and the first paint would get wrong. Both navigation drawers are in the markup: the inline one, hidden below the breakpoint, and the overlay one, which renders nothing while closed. The code pane is the one other width switch: it stacks below its showcase frame by a container query on its own block (`@container`, `src/app/code-pane/`, _`D403`_ in `.workflow/PLAN-P10.4-code-pane.md`), likewise never by a script reading a width.
- **Every highlight.js token class is coloured, or listed as deliberately not** (`COLOURED_TOKEN_CLASSES`, `UNCOLOURED_TOKEN_CLASSES`, `src/app/code/`; the test is in `src/app/markdown/`). A test highlights samples in several languages and fails on a class in neither list, as a class left out shows in the code block's own colour (e.g. `md` blocks, a single `hljs-code` token).
- **Every code block is a `CodeBlock`** (`src/app/code/`): Markdown's code blocks through a `pre` override wrapping `rehype-highlight`'s output (its lines counted from the code element's text), the showcase sidebar's through `HighlightedCode`. Never style `pre` in `src/app/markdown/`: the code block styles its own.
- **The copy button needs a secure context.** It writes with `navigator.clipboard`, which only exists over HTTPS or on `localhost`; `useSyncExternalStore` hides it in the browser where the clipboard is missing, and always renders it on the server (so the tests' server-side rendering shows it). There is deliberately no `document.execCommand('copy')` fallback (_`D387`_ in `.workflow/PLAN-P10.2-code-blocks.md`).
- **`src/app/` is browser code, not part of the library's API.** It is compiled to `dist/app/` (and so published) for Vite to bundle, but never re-exported from `src/index.ts`, and it never imports Node modules. It may import types from the rest of `src/` (e.g. `src/host/`).
- **Markers in this repository's own documentation files are live.** `showroom.json` makes this repository a host of its own, and its `README.md` is a documentation file, so a showcase marker written in it as an example must sit inside a code block (examples of fences inside a fence of four backticks), or `showroom check` on this repository reports it. Each demonstration of a showcase shown as a block is the live showcase itself, shown once, with no Markdown example: its code pane's Markdown tab shows it as written (first, and selected, as every showcase shown as a block in this repository's `README.md` and `examples/*/README.md` lists `include=markdown` first, _`D606`_ in `.workflow/PLAN-P15.6-included-keywords.md`; give a new one the same), and the prose names its marker as written, `include=markdown` included (_`D607`_), for GitHub and npm, which show neither a fence's info string nor a link's title (_`D422`_ in `.workflow/PLAN-P10.4-code-pane.md`, replacing the quoted copies of _`D173`_ in `.workflow/PLAN-P4.4-html-resources.md`); a linked showcase shown inline keeps its Markdown example in a code block, followed by it, live (`README.md`'s `view=demo`, so its showcase sidebar shows it running, _`D624`_ in `.workflow/PLAN-P16-inline-sidebar.md`). Their real files live in `examples/`. Keep the formatted number the first showcase in `README.md`, as the virtual files paragraph names it `README.showcase-1.html`. The syntax cheat-sheet (`README.md` › Showcases) is exempt: its markers are code spans, which `check` never reads as markers, and it holds no live showcases (_`D370`_ in `.workflow/SPEC-S10-presentation.md`). Each showcase adapter's part of `README.md` shows its showcase adapter example's first showcase, a linked showcase of a real file in `examples/<adapter>/` shown as a block, as in the example (_`D410`_ in `.workflow/PLAN-P10.4-code-pane.md`), and links to the example's other showcases by their headings, twice: relatively, and in the published showroom (`https://ofzza.github.io/showroom/#/examples/<adapter>/README.md#<id>`). The showcase adapter examples' own markers are live too, including the custom `number-table` showcase adapter's (`examples/number-table/number-table.js`, listed in this repository's `showroom.json`, so every `check` on this repository loads it); an error or a warning can only be shown there as text, as this repository's check must pass without issues. `src/cli/check/index.integration.test.ts` runs `check()` with `showcases: true` on this repository, so an edit that breaks a live showcase, or a showcase adapter example's type checking, fails `npm test`; it also checks that every link from `README.md` into an example names a heading the example has, and that its relative and published links match, so rename a heading together with the links to it.
- **Every new showcase adapter comes with its showcase adapter example** (_`D304`_ in `.workflow/SPEC.md`), `examples/<adapter>/README.md`, in its own segment: a mock project on the examples' shared theme, numbers and time (_`D312`_), using only this repository's own dependencies, with a `tsconfig.json` of its own where its showcases are type checked (`types: []`, as for fixtures) (_`D307`_), and its first showcase a linked showcase of a real file, shown in `README.md` too (_`D315`_).
- **Nothing of the host repository runs before trust is decided, nor without it** (_`D722`_, _`D740`_ in `.workflow/SPEC-S14-trust.md`): `check()` reads `showroom.json`, scans the documentation files and validates the built-in showcase adapters' showcases (plain parsing) first, then decides trust, and only then loads custom showcase adapters and runs host checks; `buildShowcases()` gets the decided boolean, and builds and loads nothing without it. A new piece of the host repository's code that `showroom` runs (a host package, a process, a configuration file Vite or a plugin reads) goes under the same gate, and is named in the `TrustRequest` where it can be (`getTrustTools()`, `src/adapters/showcase/registry/`). The showroom's own Vite reads nothing from its root up (`configFile`, `css.postcss`, `envDir`, `publicDir`). A test that builds showcases or loads custom showcase adapters passes `trust: true` (`--trust`), or it silently checks only sources.
- **A recorded showcase's processes run detached, and are killed by their process group** (_`D777`_, _`D790`_ in `.workflow/PLAN-P20-recorded.md`): `runProcess()` spawns each in a session of its own (no terminal, standard input ignored, never a shell), kills its group with `SIGKILL` at the time limit and once it exits (what outlives it), and waits at most 1 s for its pipes to close after it exits. On Windows, `taskkill /T /F` only while the process is known alive. `src/cli/bin.ts` installs the clean-up (`installCleanUp()`: on exit and on `SIGINT`, `SIGTERM` and `SIGHUP`, every group killed and every run folder removed, exiting with 128 plus the signal's number unless `serve` listens too); the library never installs signal handlers, and cleans up its run sessions in `finally`. A test that starts a process checks it is gone (`getLiveProcessCount()`).
- **The host copy is synced at the start of each run, on both sides** (_`D775`_, _`D787`_, _`D788`_ in `.workflow/PLAN-P20-recorded.md`): `HostCopy.sync()` walks the host repository and the copy without following links, copies a file again when its size or modification time changed on either side since it was copied, removes what the host repository doesn't have (except what the contents leave out, e.g. a build's `bin/`), and writes the virtual files; only regular files, folders and links are copied, and a folder on the way to a virtual file that is a link is refused. Runs are one at a time and builds one after another, so nothing reads the copy while it changes. It is only made with trust, and only when a showcase adapter declaring `hostCopy` has showcases to build; the run folder is made lazily, so a run without one writes nothing to the user's cache folder.
- **Custom showcase adapters are loaded with `import()`**, so Node caches each module for the life of the process. `loadCustomShowcaseAdapters()` imports each by a URL carrying its content's hash (`?v=<hash>`), so `serve` loads a changed module once more, and reuses an unchanged one; every version loaded stays in memory until the process exits, and the modules it imports are never reloaded (`README.md` says to restart `serve` after changing them). `check()` and `buildShowcases()` each load them, so an edit between the two is picked up by the next run. Their default export is a factory, called once per run, so each run gets fresh objects, closed at its end; never reuse an object across runs. Fixtures with custom showcase adapters set `"type": "module"` in their `package.json`, as their `.js` modules are ES modules.
- **Vite's watcher always ignores `**/node_modules/**`, `**/.git/**` and `**/test-results/**`**, whatever `server.watch.ignored` says, so `serve` never sees changes in a host repository under such a path. Fixture copies live under `node_modules/.cache/`, which is why no `serve` test edits files: updates after a change are unit-tested on the host watcher.
- **A showcase frame's URL carries its content's hash as `?hash=`, never `?v=`**: Vite's dev server treats a `v` query as a dependency's version, and serves it as immutable. In `serve`, the showcase frames middleware answers every request inside a showcase frame's folder before Vite does; any other path under `showcases/` (e.g. the showroom's own `showcases/index.js`) goes on to Vite.
- **A code pane or showcase sidebar tab of a text linked file carries its content's hash as `?hash=` too** (`getTabFileHashes()`, `src/vite/`; _`D406`_ in `.workflow/PLAN-P10.4-code-pane.md`): `build()` and each `serve` run compute it (`createHostWatcher()` gets it injected, as `hashFiles`, so its unit tests keep fakes), so a changed included file that no build reads gets a new URL, sent with the `showroom:showcases` event, and its tab fetches it again; `getShownChange()` ignores the tabs' URLs as it does the showcase frames'. A file that isn't text gets no hash, as its tab only links to it. The linked files middleware ignores the query.
- **The frame script captures the console from its start** (_`D559`_–_`D562`_ in `.workflow/PLAN-P15.3-console.md`): `insertFrameScript()` puts it first in every page, so it posts `start` synchronously, before any of the page's own scripts run, then wraps the console's methods (still calling the originals) and listens to uncaught errors and rejected promises. Each line is formatted at once, inside the showcase frame (a value changed after logging shows as it was), cut at `CONSOLE_MAX_LINE_LENGTH`, and posted in a batch at most every `CONSOLE_FLUSH_MS` (the newest `CONSOLE_MAX_LINES`, with the number dropped, and how many of those were warnings and errors, for the `runtime` status mark), and at once on `pagehide`. The showroom accepts only messages whose `event.source` is its own iframe's window, so a nested iframe or a window the showcase opens never posts into its console panel. Outside the showroom (no parent window), the console is left alone.
- **Type checking uses the host's TypeScript, never `showroom`'s own at run time.** `src/adapters/showcase/ts/typecheck/` resolves `typescript` as Node does from the documentation file's folder and loads it with `createRequire` (Node keeps it for the process); `showroom`'s own `typescript` is a devDependency, imported only with `import type` outside the tests. Only its classic compiler API is used, so TypeScript 7, which has none, is unsupported (skipped with a warning, _`L12`_ in `.workflow/PLAN.md`). The API's public typings lack a few things it relies on: the import graph comes from the compiler host's `resolveModuleNameLiterals` (there's no public `getResolvedModule`), a tsconfig's JSON syntax errors from its source file's internal `parseDiagnostics`, and paths are normalised by hand (`normalizePath` isn't public). The `angular` showcase adapter's compile also sets `suppressOutputPathCheck`, an internal compiler option (a host with `allowJs` and no `outDir` would otherwise fail, TS5055), and tells Angular's shims apart as the source files the TypeScript host can't find (`isShim()` isn't exported before Angular 21).
- **The `angular` showcase adapter compiles with the host's Angular before Vite, sharing one TypeScript instance with it.** `findAngular()` resolves `typescript` from `@angular/compiler-cli`'s own folder, and `loadAngular()` loads it with `require()`, which the compiler's own ES module `import` of it shares (Node's CommonJS cache), so the compiler host and the checker are of the same instance. The compile emits every module of the program, with source maps, and `buildTsShowcase()` gets them through `plugins` (`enforce: 'pre'`, like the plugins it sits between, or it runs after them) and `compiled`: Vite's Oxc transform filters by id, so it would transform the emitted JavaScript of a `.ts` id again (dropping imports whose bindings are unused), and the compiled ids are excluded through `oxc.exclude`, which replaces Oxc's default exclude (`/\.js$/`, kept). Vite's define plugin still reprints them, as production needs Angular's defines replaced. The Angular Linker runs on every JavaScript module that needs it (`needsLinking()`), not only under `node_modules`, so a host's own partially compiled library works.
- **Fixtures always resolve this repository's TypeScript and `@types`**, by walking up from `test/fixtures/`, so a fixture's tsconfig sets `types` explicitly (`types: []`), or every type check loads this repository's `@types` and takes seconds; the compiler host's current directory is pinned to the documentation file's folder (_`D293`_), so this doesn't depend on where the tests run. TypeScript 6's defaults (`strict`, `noUncheckedSideEffectImports`) apply to fixtures without a tsconfig, and to tsconfigs that don't override them: a CSS import needs a `declare module '*.css'`, and an untyped `.js` import fails (TS7016).
- **The `ts` showcase adapter's mode is pinned in its Vite configuration, never through `process.env.NODE_ENV`.** Vite sets `process.env.NODE_ENV` once per process and then prefers it over `mode` (and Vitest sets it to `test`), so `getTsBuildConfiguration()` sets `define` (`process.env.NODE_ENV`, `import.meta.env.MODE`, `DEV`, `PROD`), the resolve conditions, minifying and source maps from the request's mode. Never read or set `process.env.NODE_ENV` in `showroom`.
- **Vite's errors don't always name their module.** A transform's syntax error carries only a location and position, its file shown in its message's code frame (`╭─[ <path relative to the working directory>:<line>:<col> ]`), which `getBuildErrors()` reads; and an import nothing resolves is only a warning to the bundler (left external), so the `ts` showcase adapter's resolve plugin reports the host's own unresolved imports itself, at their line.
- **`serve` watches ignored files that showcases read.** `buildShowcases()` returns `watched` (every showcase's reads, built or not, and the custom showcase adapter modules); the watcher's `ignored` function lets them and the folders leading to them through, and `serve` adds the topmost ignored folder holding each to Vite's watcher after a run (`getWatchTargets()`), and unwatches those no longer needed. While any showcase fails to build, a run keeps the previous files to watch along with its own (`runBuild()`): a failed build only reads what it reached, so a deleted `dist/` would otherwise be unwatched, and its rebuild missed. Reads are judged outside `node_modules` on the root-relative path, as fixture copies live under `node_modules/.cache/`.
- **Vite's dev server prints a module again when it holds `import.meta.env` or `process.env`**, even inside a string: the virtual module serving the shown host information then spreads over several lines, so tests parse it without assuming its layout (e.g. the `showcase-ts` fixture's README).
- **The frame script is self-contained.** `frameScript()` (`src/frame/`) is inlined into every showcase frame page as its source text (`getFrameScript()`, `Function.prototype.toString()`), so it must reference no outer names (no imports, no module constants): everything comes from `window` and its constants argument. Its tests run the inserted string, which would fail on such a reference.
- **`src/frame/` is browser code that Node code imports.** `src/showcases/` imports it for the script, and the showroom for the message types, so it stays Node-free and side-effect-free, like `src/markdown/`.
- **The frame script stops reporting growth** after the content grows by the same amount 3 times in a row (`MAX_REPEATED_GROWTHS`): a showcase sized to its viewport (`100vh`) would otherwise grow its iframe forever, as would an overlay anchored to the window's bottom. Shrinking is still reported, and, opted into overlays over the page, its overhang too, at the held height. The console panel is the showroom's, over the iframe, so it never grows the page.
- **The frame script measures overlays, never fixed boxes** (_`D894`_–_`D900`_ in `.workflow/PLAN-P24-overlays.md`): besides `<body>` and its in-flow children, every absolutely positioned element that shows (not `display: none`, `visibility: hidden`, a `clip`, or an empty box) and isn't clipped, judged from its containing block upward as the browser clips (an absolutely positioned ancestor goes on from its own containing block, a fixed one escapes); a fixed element's own box (a full-viewport overlay layer, left in place empty) never, or the frame would never shrink back. It re-measures on the `ResizeObserver`, a `MutationObserver` on `<body>`, `transitionend`, `animationend` and `load`, batched to one measure per animation frame, as each walks every element's computed style; the first measure is immediate. A box filling the viewport inside a fixed layer (a backdrop) is a layer, never measured (_`D918`_ in `.workflow/PLAN-P25-overlay-overhang.md`): judged by its size alone, a showcase laid out absolutely with nothing in flow would fill the viewport it sizes, and shrink for good.
- **Overlays over the page** (_`S19`_, _`P25`_ in `.workflow/`; a showcase's `overlays` key, `overlays=1` in its showcase frame's URL): the frame script reports its overhang (`offset`, `flow`, `boxes`, `open`) with its height, and the showroom makes the iframe as high as its whole page, pulls it back with negative margins to its content's height, and clips it with a `clip-path` of its content and its overlays' boxes (`getOverhangClipPath()`, a very large constant width, as the box clips sideways), which clips hit-testing too. While its overlays are out, its box (`display: flow-root` always, so the margins never collapse through it) lets them out vertically and is raised, and its block, a container and so a stacking context of its own, is raised as a whole and opens its grid's `overflow`; the block whose overlay opened last is at level 2, the others at 1, the showcase sidebar's sticky header bar at 3. The page is pushed down (`padding-top` on `<html>`, over its own) for overlays above its top, and the push is only reset once the overlays that caused it are gone, or it would loop. Presses are relayed through a module-level registry in `src/app/showcases/` (on the page and in the showcase sidebar): the showroom's own real `pointerdown` and `click`, and every showcase frame's reported ones, go to every other opted-in showcase frame with an overlay open, in two phases; only `isTrusted` presses are reported or relayed, or two showcase frames would bounce them forever. A showcase frame collapsed in the showcase sidebar keeps its overlays in, and gets no presses.
- **`check`'s heading ids must be the showroom's.** The navigation's anchors are checked against the ids `scanMarkdown()` gives headings, with `github-slugger` (a dependency, the version `rehype-slug` uses) on the heading's text as the showroom renders it (text and code spans, without images and HTML, which `skipHtml` drops); `src/app/markdown/`'s test compares them with `rehype-slug`'s. A change to how the showroom renders headings must keep `_getText()` in step.
- **The showroom's placement of showcase frames relies on offsets.** `check` (`scanMarkdown()`) and the showroom's `react-markdown` must parse documentation files the same way (`remark-parse` with `remark-gfm`), or a showcase's offset matches no node and its showcase frame is skipped.
- **Linked files are handed out at `files/<path>`, and copied even when ignored.** `serve`'s linked files middleware answers every request under `files/` (a linked file, read from disk on each request, or a 404), so no folder of `src/app/` may be named `files` (Vite serves the showroom's modules unbundled from `dist/app/` in `serve`; `src/vite/`'s tests guard it, and `serve`'s load the showcase sidebar's `showcase-sidebar/index.js`), so `serve` never hands out a file `build` doesn't copy. A link resolves to a linked file only by its exact path, as `check` found it, never case-insensitively as documentation files do. `check` reads at most `LINKED_FILE_SIDEBAR_LIMIT` (1 MB) of each to decide `text`, and leaves out (with a warning; an error for an included file, `_checkIncludes()`) a file in the output folder, which `build` empties first, and one whose real path leads outside the root; a showcase's included real files are linked files too; the linked files are among `serve`'s files to watch (`runBuild()`), so an ignored one's change is seen.
- **The `dotnet` stack adapter never runs MSBuild or the .NET SDK** (_`D488`_ in `.workflow/SPEC.md`): it reads the project file and its `Directory.Build.props` as XML with `sax`, so what MSBuild only evaluates (conditions, other imports, the SDK's defaults) is never seen (_`K20`_ in `.workflow/SPEC-pitfalls.md`). `sax` ends a document without an error at a root element left open, or with none, so `_collectProperties()` checks both itself.
- **Fixtures can't hold `node_modules`, `dist` or `coverage` folders.** `.gitignore` ignores them at any depth, so they would never be committed. Tests of those default ignore patterns check the TypeScript stack adapter's list instead (see `src/adapters/stack/typescript/index.test.ts`), and fixtures exercise ignoring with other folder names (e.g. `vendor/`).
- **Fixture file names must differ by more than case within a folder**, or they collide on case-insensitive file systems (Windows, macOS). The case-insensitive matching is tested across folders (`test/fixtures/names/`).
- `.gitignore` ignores `.vscode/` but re-includes `settings.json`, `tasks.json`, `launch.json` and `extensions.json`. Any other `.vscode/` file must be re-included there before it can be committed.
- **`*.gitignore.*` files and `*.gitignore/` directories are local-only** (e.g. `TODO.gitignore.md`), a convention for keeping scratch files next to the code. `.gitignore` ignores them, so never commit them. They are for your own local notes: an agent's working files still go under `./.workflow/.temp/<topic>/` (see [WORKFLOW.md](./WORKFLOW.md) › "Working files").

## Continuous integration

`.github/workflows/ci.yml` installs the .NET SDK 10 (`actions/setup-dotnet`, for the `cs` showcase adapter) and runs `npm ci && npm run ci` on every pull request targeting, and every push to, `master` or `develop`. It runs across a Node matrix of `[22, 24]` with `fail-fast: false`, and cancels in-progress runs only for pull requests, never for `master`. Its checkout sets `persist-credentials: false`, as `ci:showroom` runs this repository's showcases with `--trust` (_`D755`_ in `.workflow/SPEC-S14-trust.md`). `ci:build` only compiles, so `dist/mermaid/` is only there from `npm ci`'s `prepare`; the tests use a bundle of their own (`inject('mermaidDir')`).

`.github/workflows/showroom.yml` installs the .NET SDK 10 too (its `cs` example's showcases are built), then builds this repository's own showroom with the command line `npm ci` just built (`node dist/cli/bin.js build --trust`: a package's own `bin` isn't linked into its own `node_modules`, so `npx showroom` doesn't resolve here) and publishes it to GitHub Pages, on every push to `master` and on demand (`workflow_dispatch`), in two jobs (_`D755`_ in `.workflow/SPEC-S14-trust.md`): `build`, with `contents: read` only and `persist-credentials: false`, uploads the showroom (`actions/upload-pages-artifact`); `deploy`, with `pages: write` and `id-token: write`, deploys it (`actions/deploy-pages`). It is `README.md` › Publishing to GitHub Pages' example, adapted (the example adds a build step for showcases importing the host's own package, which `npm ci`'s `prepare` makes unneeded here): keep the two in step (Dependabot updates the workflow's actions, not the README's). The repository settings it needs are in `PUBLISH.md`. It can't be tested before it runs on GitHub.

`.github/dependabot.yml` opens weekly npm and github-actions updates against `develop`. devDependencies are grouped into one pull request, except three groups listed before it (Dependabot puts an update into the first group that matches): `react` (`react`, `react-dom`, `@types/react`, `@types/react-dom`) and `angular` (`@angular/*`, `rxjs`, `zone.js`), for their majors only, and `typescript`, for every update, as a minor one can leave `@angular/compiler-cli`'s `typescript` peer range. `react` and `react-dom`'s minor and patch updates, as production dependencies, still come one pull request each. `@types/node` majors are ignored.

**A workflow alone does not block merges.** To make it mandatory, set up branch protection on `master` in the GitHub repo settings, with `CI / Node 22` and `CI / Node 24` as required status checks. That is a repo setting, not a file in this repository.

## Exports

Everything public is re-exported from `src/index.ts`:

- `check(root, options?): Promise<CheckResult>` (`src/cli/check/`): checks a host repository and collects its host information, its showcases included; `options.outDir` overrides the output folder, `options.showcases` also builds every showcase (`--showcases`), `options.trust` decides whether the host repository's code runs (`false` by default, `true`, or a function given a `TrustRequest`, with its `executables` and `recorded`; `CheckResult.trusted` carries the decision), and `options.passEnv` names the variables passed on to recorded showcases' build steps (`--pass-env`). Also the types `CheckOptions`, `CheckResult`, `CheckIssue` (with an optional `line`, and `check`, a showcase's check its issue belongs to), `CheckIssueSeverity`, `TrustRequest`.
- `main(args, output?, input?): Promise<number>` (`src/cli/`): runs the command line, resolving to its exit code; without `--trust` or `--no-trust`, it asks through `input` (`CliInput`, the terminal on standard input by default) whether to trust the host repository, and Ctrl-C ends it with `130`. Also `USAGE`, and the types `CliOutput`, `CliInput`.
- `readConfiguration(root)`, `validateConfiguration(value)` (`src/configuration/`): read and validate `showroom.json` (`stack` optional, a built-in stack adapter's name running it; `project` an object, `ProjectConfiguration`, every field optional and nullable, `name` required without a stack adapter, `path` refused there; `showcaseViews`, the default views by showcase adapter, is validated as `view=` is, its names checked by `check()`; `navigation`'s items recursively, its paths resolved by `check()`). Also `CONFIGURATION_FILE_NAME`, `DEFAULT_OUT_DIR`, `BUILT_IN_DOCUMENTATION` (here, so `src/adapters/stack/resolve/` imports nothing from `src/cli/`), and the types `Configuration`, `ProjectConfiguration`, `ConfigurationResult`, `NavigationEntry`.
- `getStackAdapter(name)`, `getStackAdapterNames()` (`src/adapters/stack/`): look up the built-in stack adapters. Also the type `StackAdapter` (its `readProject(root, project?)` gets `project.path`, or its own `defaultProject`, and resolves to `Partial<ProjectInformation>`, as `showroom.json` can give the `name`), `TypeScriptStackAdapter` (`src/adapters/stack/typescript/`) and `DotNetStackAdapter` (`src/adapters/stack/dotnet/`).
- Types `HostInformation`, `ProjectInformation`, `DocumentationFile`, `DocumentationKind`, `Showcase`, `ShowcaseKind`, `ShowcaseDisplay`, `ShowcaseView`, `ShowcaseTab`, `VirtualFile`, `LinkedFile`, `NavigationItem` (`src/host/`): the host information (`HostInformation.navigation`, resolved, only when `showroom.json` configures one; `DocumentationFile.heading`, its first heading; `Showcase.views`, after the defaults; `Showcase.overlays`, `true` when its marker has the `overlays` key, left out otherwise; `Showcase.tabs`, `include=`'s order with its `source` and `markdown` keywords, an unlisted source tab before the first included file, or last; `VirtualFile.offset`, and `views` on a virtual file with no showcase adapter).
- Types `ShowcaseAdapter`, `ShowcaseValidation`, `ShowcaseHostCheck`, `ShowcaseCheckContext`, `ShowcaseProject`, `ShowcaseBuildRequest`, `ShowcaseBuildResult`, `ShowcaseBuildFile`, `ShowcaseBuildIssue`, `ShowcaseHostCopyContent`, `ShowcaseHostCopy`, `ShowcaseRunOptions`, `ShowcaseRun`, `ShowcaseRecording`, `ShowcaseConsoleLine` (`src/adapters/showcase/`): the showcase adapter interface (its optional `defaultViews`, `['demo']` if left out; `recorded` and `hostCopy`; the request's and the context's `project` (`ShowcaseProject`, the merged project: its information, `path`, `sourceRoot` and every pattern that applies, a copy), `stack` (the configuration's `stack`, `custom` by default), `hostCopy` and `showcaseFolder`; the result's `recording`), exported and documented as experimental (it may change in any release until declared stable). The registry and the built-in showcase adapters are not exported.

The showroom (`src/app/`: `App`, `mount()`, `ShownHostInformation`) is deliberately not exported: it is browser code, bundled by Vite from `dist/app/`. Neither are `src/adapters/stack/resolve/`, `src/markdown/`, `src/navigation/`, `src/linked-files/`, `src/showcases/`, `src/processes/`, `src/host-copy/`, `src/frame/`, `src/testing/`, `serve()` (`src/cli/serve/`), `build()` (`src/cli/build/`), the Vite configuration (`src/vite/`) the check's internals (`src/cli/check/internal/`) and `checkHost()` (`src/cli/check/`, the check reporting the showcases of a check without trust as not built, for `serve` and `build`; `src/cli/index.ts` re-exports `src/cli/check/` by name, not with `export *`, to leave it out): `showroom serve` and `showroom build` are only available through the command line and `main()`, where their options' `trust` (`ServeOptions`, `BuildOptions`) is the check's.
